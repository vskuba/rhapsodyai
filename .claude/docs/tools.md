# Tools — два слоя: общие библиотеки и инструменты агентов

> В проекте два слоя переиспользуемого кода, и путать их нельзя.
> **`py_modules/`** — общие библиотеки: переносимы в любой проект, про этот ничего не
> знают, LLM их не видит. **`src/tool/`** — инструменты агентов и workflow: привязаны к
> проекту, автоматически попадают в реестр и предлагаются LLM. Инструменты **пользуются**
> библиотеками, наоборот — никогда.
>
> Универсальные правила написания инструментов, переносимые в другой проект, живут
> отдельно — `docs-common/tool_rules.md`. Здесь то же самое применительно к этой
> установке: конкретные пути, механика синка, грабли.

## 1. Чем слои различаются

| | `py_modules/` | `src/tool/` |
|---|---|---|
| Что это | общие библиотеки | инструменты для LLM |
| Привязка к проекту | нет, переносимы как есть | да, знают его таблицы и логику |
| Видит ли LLM | **нет** | **да**, выбирает по докстрингу |
| Реестр в БД | не заводится | таблицы `tool` / `tool_group` |
| Кто вызывает | код проекта, в том числе инструменты | движок workflow (шаг `tool_invoke`) и агенты |
| Git | **отдельный репозиторий** (submodule) | часть этого репозитория |
| Контракт возврата | обычный python, что удобно | `dict`, ошибки в результат |

Главное следствие: **`py_modules` инструментами не являются.** `ai_tool_sync()` сканирует
только `src/tool`, папки `tool/` в `py_modules` нет, и ни одна её функция в реестр не
попадает. Положить туда функцию, рассчитывая, что её увидит LLM, — не сработает.

Обратное правило жёстче: **в `py_modules` не должно быть ничего про этот проект.** Модуль
уезжает в соседние проекты целиком, и знание про таблицу `project_task` или про роли
конвейера сделало бы его непереносимым. Нужно и то, и другое — общая часть в библиотеку,
проектная в `src/tool`, который её импортирует.

### Как инструменты пользуются библиотеками

Обычным импортом, без обёрток:

```python
from mysql_.mysql_ import mysql_get_db_async     # py_modules/mysql_
from logging_.logging_ import logger_info        # py_modules/logging_
from config.config import config_get             # py_modules/config


async def fact_collection_add(name: str) -> dict:
    """..."""
    async with mysql_get_db_async() as db:
        ...
```

Живой расклад по `src/tool`: `mysql_` импортируют 22 файла, `logging_` — 5, дальше
`qdrant_`, `json_`, `datetime_`, `config`. То есть слой библиотек — фундамент, на котором
инструменты и стоят.

## 2. Именование: namespace = путь файла

Правило одно на оба слоя и на весь код проекта (`docs-common/code_rules.md`, §1): **имя
публичной функции начинается с namespace своего файла** — «папка + имя файла».

```
src/tool/fact/fact_collection_.py   ->  fact_collection_add()
                                        fact_collection_remove_by()
src/tool/mysql/tables_.py           ->  tables_mysql_find()
py_modules/mysql_/mysql_.py         ->  mysql_get_db_async()
```

Хвостовое подчёркивание в имени файла в префикс не входит — оно ставится, только чтобы не
конфликтовать с именем пакета или встроенного модуля (`json_`, `datetime_`, `logging_`).

**Перед созданием файла посмотри на соседей** (`code_rules.md`, §0) — повтори шаблон папки:

```bash
ls src/tool/<область>/*.py
grep -oP '^async def \K[a-z_0-9]+' src/tool/<область>/*.py | sort -u
```

Для инструментов у правила есть вторая, более жёсткая причина: **`tool.name` —
`UNIQUE CHAR(50)`**, имя глобально уникально по всей папке, а не внутри файла или группы.
Префикс по namespace эту уникальность и обеспечивает. Сейчас 113 инструментов, самое
длинное имя — 39 символов, запас есть.

Состояние на сегодня: в `src/tool` правилу следуют **113 функций из 113**. В `py_modules`
72 функции, шесть исторических исключений (`logger_info` вместо `logging_info`,
`translate_text`, `add_text_to_image`) — их не трогаем без нужды, переименование чужого
модуля ломает все проекты, которые его подключают.

## 4. Создание инструмента

**Путь:** `src/tool/<область>/<файл>.py`. Вложенность разрешена
(`src/tool/project/planning/planning_phase.py`).

Реальный пример — `src/tool/env/env_.py`:

```python
from config.config import config_get


async def env_is_prod() -> dict:
    """
    Проверяет, выполняется ли приложение на проде (APP_ENV содержит 'prod' -
    на проде выставлен в '_prod', см. docker-compose.yml). Используется для
    прод-заглушек в workflow (например workflow_shell_test - тестовые прогоны
    должны выполняться только локально).
    Returns:
        dict: Словарь с результатом, содержащий:
            is_prod (str): '1' - выполняется на проде, '0' - локально/иное окружение.
    """
    return {"is_prod": '1' if 'prod' in config_get('APP_ENV', '').lower() else '0'}
```

Требования к функции:

1. **Публичная** — имя без ведущего `_`. Приватные хелперы (`_github_auth`) в БД не попадают.
2. **`async def` или `def`** — движок сам разбирается через `inspect.iscoroutinefunction`.
3. **Аннотации у всех аргументов** — по ним `ai_tool_args_prepare()` приводит типы
   (без аннотации значение уходит в функцию как есть, строкой из workflow-переменной).
4. **Простые типы аргументов** (`str`, `int`, `bool`, `list`, `dict`): значения приходят из
   workflow-переменных, то есть почти всегда строками. Списки/структуры передаются
   JSON-строкой и парсятся автоматически.
5. **Возврат — `dict` с говорящими ключами.** Каждый ключ станет отдельной
   workflow-переменной. Не-dict тоже работает, но переменная будет одна.
6. **Ключи результата описаны в docstring** (секция `Returns:`) — иначе UI и Output Mapping
   не узнают, что вернёт инструмент (см. ниже).
7. **Инструменты узкие и составные.** Вместо одного «умного» — цепочка простых, соединяемых
   через переменные: `tables_mysql_find(tables)` даёт `tables_str`, который идёт на вход
   `mysql_export_to_migration(tables, migration_file)`.
8. **Валидация всего, что уходит в SQL/shell/пути.** Аргументы приходят от LLM
   (см. очистку имён таблиц в `src/tool/mysql/tables_.py`).
9. **Ошибки — в результат, а не в исключение,** если workflow должен продолжиться:
   `{"success": False, "error": str(e)}`. Проброшенное исключение валит весь шаг
   (движок пишет `status='error'` в trace и прерывает workflow).

**Докстринг — контракт для LLM, а не комментарий для человека.** По первой строке модель
выбирает инструмент: «Обрабатывает данные» выбрать не помогает, «Ищет пользователя по
email» помогает. Полные требования к докстрингу — `docs-common/tool_rules.md`, §3.

### Docstring: секция `Returns:`

`ai_tool_sync()` парсит `Returns:` только если аннотация возврата — `dict` или `tuple`.
Формат строки: `имя (тип): описание`, отступ любой. Секция обрывается на `Raises:`,
`Args:` или `Examples:`.

```python
async def tables_mysql_find(tables: list) -> dict:
    """
    Проверяет существование таблиц базы данных по точным именам.
    Returns:
        A dictionary with the found database tables.
        tables_str (str): Имена найденных таблиц через запятую.
        tables_qty (int): Количество найденных таблиц.
    """
```

Распарсенные ключи попадают в `tool.args` → `output.keys` и показываются в
деталях инструмента и в Output Mapping шага `tool_invoke`. Нет `Returns:` —
UI покажет только `{"type": "dict"}`, и маппинг придётся заполнять руками.

## 5. Как работает auto-discovery

`ai_tool_sync(force=False)` (`src/ai/ai_tool.py`):

1. `count_by({})` по таблице `tool`. **Если записей > 0 и `force=False` — синк молча
   пропускается** и возвращает текущее количество.
2. `rglob('*.py')` по `src/tool/`, `__init__.py` игнорируется. **`py_modules` не
   сканируется вовсе** — библиотеки инструментами не становятся.
3. AST-разбор файла → имена `FunctionDef` / `AsyncFunctionDef` без ведущего `_`.
4. Динамический импорт файла (`spec_from_file_location`), корень `src/` добавляется в
   `sys.path`. **Импорт файла выполняет его код на верхнем уровне** — тяжёлых side effects
   в module scope быть не должно.
5. Из каждой функции: `inspect.getdoc()` → `description`, `inspect.signature()` → `args`.
6. Группа = имя родительской папки через `.capitalize()`:
   `src/tool/github/github_.py` → `Github`, `src/tool/project/planning/…` → `Planning`.
7. Группы upsert-ятся в `tool_group` по имени, затем `tool` **полностью очищается**
   (`empty()`) и заполняется заново (`add_many`).

Формат `tool.args`:

```json
{
  "input": {
    "tables": { "type": "list", "default": "Required" },
    "limit":  { "type": "int",  "default": "10" }
  },
  "output": {
    "type": "dict",
    "keys": {
      "tables_str": { "type": "str" },
      "tables_qty": { "type": "int" }
    }
  }
}
```

Ошибка в одном файле (битый импорт, исключение на верхнем уровне) логируется и файл
пропускается — остальные инструменты синхронизируются.

### Грабли

- **Имя инструмента уникально глобально.** `tool.name` — `UNIQUE CHAR(50)`. Две одноимённые
  функции в разных папках → `add_many` падает целиком, а `empty()` уже выполнен: таблица
  `tool` остаётся **пустой**, `ai_tool_sync` вернёт `0`. Имя длиннее 50 символов — та же
  история.
- **`path` — абсолютный путь** (`CHAR(200)`), записанный тем процессом, который делал синк.
  После переноса кода в другой каталог/контейнер нужен новый синк.
- **Одинаковые имена папок сливаются в одну группу:** `src/tool/design/` и
  `src/tool/project/design/` дают группу `Design`.
- **`empty()` временно обнуляет таблицу.** Поэтому в `main_uvicorn.py` восстановление
  планирования (`planning_worker_recover`) идёт строго после синка — иначе job загрузит `{}`
  и упадёт с «инструмент не найден».
- **Локально простого рестарта недостаточно.** В `lifespan()` вызов зависит от окружения:
  на проде `ai_tool_sync(force=True)` (каждый рестарт подхватывает изменения), локально
  `ai_tool_sync()` — без force, то есть новый/переименованный/перемещённый инструмент в БД
  не появится. Нужен ручной sync.
- **Переименование инструмента задевает базу.** Имя функции — ключ в реестре и в шагах
  workflow, которые зовут его по имени. Правка кода обратима, правка базы — нет, поэтому
  SQL кладётся **миграцией** (`docs-common/tool_rules.md`, последний раздел).

## 7. REST API

Роутер подключён без префикса (`main_uvicorn.py`).

| Метод | Путь | Права | Назначение |
|-------|------|-------|-----------|
| GET | `/tool/list` | `tool:view` | Все инструменты + имя группы |
| GET | `/tool/group/list` | `tool:view` | Группы, сортировка по имени |
| GET | `/tool/{tool_id}` | `tool:view` | Один инструмент |
| POST | `/tool/sync` | `tool:update` | `ai_tool_sync(force=True)`, вернёт `synced_count` |
| POST | `/tool/test/{tool_id}` | `tool:test` | Запуск инструмента с произвольными аргументами |

`POST /tool/test/{tool_id}` — тот же путь исполнения, что и в workflow
(`ai_tool_args_prepare` → вызов), поэтому это честная проверка приведения типов.
Тело — словарь аргументов; ответ `{"status": "success"|"error", "result": …}`,
исключение не пробрасывается, а возвращается текстом.

## 8. Приведение типов (`ai_tool_args_prepare`)

Аргументы из workflow приходят строками, поэтому перед вызовом они кастуются по
аннотациям:

| Аннотация | Что делает |
|-----------|-----------|
| `bool` | строка → `True` для `true / 1 / yes / on` (регистр не важен), иначе `bool(value)` |
| `dict`, `list`, `list[...]`, `dict[...]` | строка → `json.loads`; не JSON → остаётся строкой |
| `str` | `dict`/`list` → `json.dumps(ensure_ascii=False)` (не python-repr с кавычками-апострофами) |
| `X \| None`, `Optional[X]` | берётся первый не-`None` тип и применяется как `X(value)` |
| прочее callable (`int`, `float`, …) | `expected_type(value)` |
| нет аннотации, значение `None`, аргумент не в сигнатуре | передаётся как есть |

Неудачный каст логируется и **не** прерывает вызов — уходит сырое значение.

⚠️ **Проверка «значение задано» через истинность ломается** на `0`, `""`, `False`, `[]`.
Различать «не передано» и «передано пустым» нужно явно, через `is None`.

## 9. Вызов из workflow

Шаг `tool_invoke`: `inputs_map` — соответствие «аргумент функции → **имя**
workflow-переменной». Полные правила, частые ошибки и чек-лист — `workflow.md`,
раздел «Тип шага `tool_invoke`».

⚠⚠ **Приставка `_const_` в `inputs_map` запрещена к новому применению.** Движок её
понимает (значение берётся текстом после приставки), и написать так можно — но
такого значения нет **ни в одном** списке переменных: ни во входящих, ни в
создаваемых шагами. Менять его нельзя ничем, кроме правки JSON шага, а на вопрос
«откуда здесь 10?» ответа не найти нигде. Нужно значение — заведите переменную и
передавайте её по имени.

⚠⚠ **И выражение в самой переменной запрещено тоже.** Заведя переменную, легко
положить в неё `[<if mail_mode>]mail[<else>]chat[<endif>]` — и вернуть ту же беду глубже:
выражение заново решает то, что уже решено переходами, а два решения одного вопроса
расходятся молча. Значение переменной — простой текст либо другая переменная;
условие живёт в переходах.

⚠ **Единственное место, где выражение законно, — промпт** (`prompt_user`,
`prompt_system`): там оно собирает текст для модели, а не принимает решение.

Полный разбор, примеры «как правильно» и оставшийся долг — `workflow.md`, §3.0.

Результат раскладывается в переменные автоматически:

| Что вернул инструмент | Переменные |
|---|---|
| `dict` | по одной на ключ: `{tool_name}_{step_id}_result_{key}` |
| `str` / `int` / `bool` / `float` / `list` / `tuple` | одна: `{tool_name}_{step_id}_result_{str\|int\|bool\|float\|list}` |
| прочий объект | `{tool_name}_{step_id}_result_{имя_типа}` |

`step_id` в имени делает переменные уникальными: два вызова одного инструмента в одном
workflow не перетирают друг друга. Вложенные `dict`/`list` внутри значений сериализуются
в JSON-строку. `outputs_map` задаёт короткие алиасы к этим автоименам.

Каждый вызов пишется в историю сессии (`ai_session_message`, `kind_type='tool-call'`)
и в trace шага — см. `workflow_trace.md`.

## 11. Общие библиотеки `py_modules`

Отдельный git-репозиторий, подключён submodule. **`M py_modules` в `git status` — это
сдвинутый указатель, а не правки файлов.**

| Модуль | О чём |
|--------|-------|
| `mysql_`, `qdrant_`, `sqllite3`, `redis_`, `redis_queue` | доступ к хранилищам |
| `logging_`, `event_`, `state` | журналы, события, состояние |
| `config`, `setting_`, `i18n_` | конфигурация, настройки, языки |
| `json_`, `datetime_`, `thread_`, `async_`, `queue_` | утилиты |
| `ai`, `mcp_` | база AI-фреймворка и MCP-клиент |
| `auth_`, `uvicorn_` | авторизация и обвязка сервера |
| `flux_schnell`, `microphone`, `translator` | внешние сервисы |

Правка библиотеки — правка **чужого** репозитория: она приедет во все проекты, которые
его подключают. Отсюда два следствия. Первое: коммитить в `py_modules` отдельно, и
указатель submodule обновлять сознательно. Второе: **менять сигнатуры и имена крайне
осторожно** — соседние проекты сломаются молча, их сюита здесь не гоняется.

## 12. Чек-лист нового инструмента

1. Файл — в `src/tool/<область>/`, имя по правилу namespace; посмотрел на соседей.
2. Функция публичная, аннотации у всех аргументов, необязательные — с дефолтами.
3. Докстринг: первая строка = критерий выбора для LLM; `Args:` со смыслом; `Returns:` со
   всеми ключами, которые нужны дальше в workflow.
4. Возврат — `dict`; ошибки — `{"success": False, "error": ...}` без исключений наружу.
5. Общая часть, которая пригодится другому проекту, вынесена в `py_modules`; проектная
   осталась здесь.
6. Проведён sync (`POST /tool/sync` или `force=True`), инструмент появился в `/admin/tool`,
   параметры разобраны верно.
7. Вызов проверен через `POST /tool/test/{id}` — с валидным и с заведомо плохим входом.
8. Опасные действия (удаление, отправка наружу, трата денег) названы в первой строке
   докстринга.

## 13. MCP как источник инструментов

Инструменты MCP-серверов регистрируются отдельным путём (`py_modules/ai/ai_mcp.py`),
в таблицу `tool` не попадают и в `src/tool/` не лежат — см. `ai_framework.md`.
