# Deploy — Blue-Green деплой

> Zero-downtime деплой для сервиса `uvicorn`. Во время обновления трафик переключается
> между двумя слотами (blue :8011 / green :8012); Caddy перезагружает конфиг без обрыва
> соединений. Остальные сервисы (mysql, redis, telegram, cronicle) деплой не трогает.

## Архитектура

```
Internet → Caddy (:80/:443) → uvicorn:8000  (blue,  host port 8011)
                             или
                           → uvicorn_green:8000  (green, host port 8012)
```

Два Docker-сервиса поочерёдно становятся активными:

| Слот  | Сервис          | Внутренний порт  | Порт на хосте   |
|-------|-----------------|------------------|-----------------|
| Blue  | `uvicorn`       | `uvicorn:8000`   | `127.0.0.1:8011` |
| Green | `uvicorn_green` | `uvicorn_green:8000` | `127.0.0.1:8012` |

⚠⚠ **Порты привязаны к петле, и снимать привязку нельзя.** До 2026-11-01 в
`docker-compose.yml` стояло голое `"8011:8000"` — без адреса Docker слушает все
интерфейсы, то есть API прода был открыт прямым обращением к `<адрес>:8011`,
**мимо Caddy**. Мимо него же шли и запреты Caddyfile: `/cronjob` на 80/443
отвечает 403, а на 8011 исполнялся. Нашёл аудит API.

⚠ Сам Caddy ходит к слотам по имени контейнера в сети Docker
(`reverse_proxy uvicorn:8000`), опубликованный порт ему не нужен вовсе. Петля
нужна своим: сюите (`BASE_URL`), `event-log` из выкладки
(`.github/workflows/on-deploy.yml`), ssh-туннелю админа. Соседние проекты ходят
сюда локально по имени контейнера, на проде — по публичному HTTPS.

Текущий активный слот хранится в файле `.deploy_slot` в корне репозитория на сервере.

## Файлы

| Файл | Назначение |
|------|-----------|
| `bluegreen.sh` | Скрипт переключения (вызывается из deploy.yml) |
| `.deploy_slot` | Текущий активный слот (`blue` / `green`); создаётся на сервере |
| `docker-compose.yml` | `uvicorn_green` определён с `profiles: ["green"]` |
| `docker/caddy/Caddyfile` | Строки `reverse_proxy <backend>:8000 {` меняются скриптом через `sed` |

> **Слотовых блоков в Caddyfile два, и sed правит оба.** Публичный
> (`92.5.17.195.sslip.io`) и внутренний вход для Cronicle (`:8090`, наружу не
> проброшен — у caddy опубликованы только 80 и 443). Второй появился потому, что
> события Cronicle звали контейнер по имени (`http://uvicorn:8000/cronjob`) и
> отваливались при каждом переключении слота: активен green, событие зовёт blue.
> Через Caddy адрес слота не касается.
>
> Шаблон sed привязан к отступу в четыре пробела и к имени слота
> (`^    reverse_proxy (uvicorn|uvicorn_green):8000 \{`) — **добавляя такой блок,
> держи строку ровно в этом виде**, иначе слот в ней замрёт навсегда, а поймается
> это только на втором деплое.
| `.github/workflows/deploy.yml` | CI/CD — вызывает `bluegreen.sh` |

## Процесс деплоя (bluegreen.sh)

```
1. Читает Caddyfile → определяет старый (blue) и новый (green) слот
   - Source of truth: grep reverse_proxy из docker/caddy/Caddyfile
   - Fallback: .deploy_slot файл
2. docker compose up -d --build --force-recreate --no-deps <new_service>
3. Polling http://127.0.0.1:<new_port>/ каждые 5с, до 90с
   - 2xx/3xx/4xx = готов; 000 = ждём (000 = нормально пока uvicorn стартует)
   - curl exit code 56 (connection reset) обрабатывается через || HTTP_CODE="000"
4. sed -i: меняет backend в Caddyfile (uvicorn:8000 → uvicorn_green:8000 или обратно)
5. docker exec caddy caddy reload  ← graceful, без dropped connections
6. echo <new_slot> > .deploy_slot
7. docker stop <old_service> && docker rm <old_service>
```

Если новый слот не поднялся за 90 секунд — контейнер удаляется, деплой завершается с ошибкой. Старый слот продолжает работать.

### Почему Caddyfile — source of truth

`git reset --hard origin/master` в deploy.yml восстанавливает Caddyfile из git (исходное `uvicorn:8000`), но **не перезагружает Caddy** — Caddy продолжает работать по runtime-конфигу. Поэтому state определяется из ФАЙЛА (что есть в git/на диске), а не из runtime Caddy. Это корректно: `sed` меняет файл → `caddy reload` синхронизирует runtime с файлом.

`.deploy_slot` защищён от `git clean -fd` через `.gitignore`.

## Первый запуск на свежем сервере

При отсутствии `.deploy_slot` скрипт считает активным `blue` и деплоит в `green`. Если `uvicorn` не запущен — `docker stop uvicorn || true` завершается без ошибки.

## Ручной запуск

```bash
cd ~/rhapsodyai
chmod +x bluegreen.sh
./bluegreen.sh
```

## Healthcheck endpoint

Скрипт проверяет `GET /` и считает приложение готовым при HTTP-коде 2xx/3xx/4xx.
Для надёжности рекомендуется добавить выделенный эндпоинт:

```python
@app.get("/health")
async def health():
    return {"status": "ok"}
```

И поменять в `bluegreen.sh` строку:
```bash
HTTP_CODE=$(curl ... "http://127.0.0.1:$NEW_PORT/health" ...)
```

## Сервисы, НЕ затрагиваемые Blue-Green

- `telegram` — перезапускается через `--force-recreate` (обновление образа из GHCR)
- `worker_task` — перезапускается с новым образом (downtime допустим, обрабатывает Redis-очередь)
- `caddy`, `redis`, `qdrant`, `mysql` — только `up -d` (запускаются если упали)

## ⚠⚠ Порядок шагов: сначала то, что не зависит от реестра

Порядок в `deploy.yml` выбран не по удобству чтения, и переставлять его не надо:

```
забор образов из GHCR      ← НЕ фатален, отказ запоминается
базовые сервисы (up -d)    ← нужны bluegreen.sh
bluegreen.sh               ← приложение переключается ЗДЕСЬ
воркеры, браузер
telegram                   ← последним: единственный образ из реестра
уборка
поднять запомненный отказ  ← выкладка краснеет, но прод уже обновлён
```

**Чем это куплено.** 25.09.2026 забор образов стоял **вторым** шагом и под `set -e`.
GHCR ответил `NotFound: content digest … not found` про наш же образ бота — и
выкладка встала целиком, хотя приложение собирается локально и в реестр не ходит.

⚠⚠⚠ **Дороже простоя оказалось половинчатое состояние.** `git reset --hard` идёт
**до** забора, поэтому новый код уже лежал на диске, а ни один контейнер не был
пересобран и миграции не применены. Прод при этом работал **прежним** кодом:
процесс держит прежний модуль в памяти, файл на диске уже новый.

⚠⚠ Отсюда правило диагностики: **версию кода на проде нельзя проверять чтением
файла.** `docker exec … grep /app/…` покажет новое, а исполняется старое. Смотреть
надо `docker compose ps` (время «Up») и таблицу `agent_workflow_trace`.

### ⚠⚠ У этого окна есть видимая сторона: страница новая, ручка старая

Та же половинчатость смотрит и наружу, а не только в диагностику. Репозиторий
примонтирован в контейнер (`./:/app`), и **шаблоны со статикой читаются с диска
на каждый запрос**, а маршруты FastAPI прочитаны один раз, при старте процесса.
Значит сразу после `git reset --hard` браузер получает **новую** вёрстку и
**новый** JS от **старого** процесса: кнопка на странице есть, ручки за ней ещё
нет, и нажатие отвечает `404 Not Found`.

Поймано 09.10.2026 на выкладке кнопки «Удалить все» (вкладка «Чат»): окно
подтверждения открылось и перечислило обмены, а подтверждение дало «Ошибка
удаления: Not Found». Правка была ни при чём — к концу выкладки та же кнопка
отработала.

⚠ Отличить это от настоящей поломки просто: `Not Found` **английскими словами**
— ответ FastAPI на неизвестный маршрут. Свои отказы этой установки написаны
по-русски («Обмен не найден», «Список обменов пуст»), и если в сообщении русский
текст — маршрут нашёлся, дело не в окне выкладки.

⚠ Лечения не требует: окно закрывается само, когда новый слот забирает трафик.
Но знать о нём надо — иначе первая же проба свежей кнопки читается как «выложили
сломанное», и начинается откат того, что исправно.

⚠ Отказ забора **не спрятан**: он поднимается последней строкой, и выкладка так же
краснеет. Разница в том, что к этому моменту приложение переключено, а контейнеры
поднялись на прежних локальных образах — рабочих, просто не свежих. Значит отказ —
повод повторить выкладку (`gh run rerun <id> --failed`), а не идти на сервер.

## ⚠⚠ Удаление из схемы едет ДВУМЯ выкладками

Из того же порядка следует правило про миграции, и оно не про эту одну таблицу.

Миграции накатывает **новый** контейнер uvicorn при старте — то есть до
переключения слота. В этот момент трафик держит ещё **старый** слот, а `telegram`
и `worker_task` перезапускаются строчкой ниже, уже после. Значит между накатом и
концом выкладки на установке живёт код, который схемы ещё не знает, — минуты, не
секунды.

Добавление это переживает: лишней колонки старый код просто не видит. **Удаление
— нет.** Снеси таблицу или колонку в той же выкладке, и всё, что её читает,
падает с «Table doesn't exist» до самого конца выкладки. Если читатель лежит на
горячем пути (`ai_workflow_load` спрашивают на **каждом** прогоне workflow), это
значит «все агенты молчат».

Поэтому расширение и сужение разносятся:

| Выкладка | Что делает |
|----------|------------|
| первая | заводит новое, переносит данные, **старое оставляет** |
| вторая | убирает старое — читателей у него уже нет |

⚠ Вторая миграция **не должна** уехать в том же коммите: yoyo применяет всё, что
лежит в папке, и порядок имён от этого не спасает.

⚠ Между выкладками обе картины обязаны быть верны на одних данных. Это
проверяется до прода: `mysql_rehearse` на копии боевой базы, затем один запрос,
сравнивающий старое чтение с новым. Пример — `20260929003100` и
`20260929134932` (владелец переменной workflow): старый `JOIN` по таблице связей
и новый по колонке дали один и тот же набор пар, 334 против 334.

## Откат

Перезапустить вручную предыдущий слот:

```bash
cd ~/rhapsodyai
# Если активен green, вернуть blue вручную:
docker compose up -d --build uvicorn
sed -i "s|reverse_proxy [a-zA-Z_]*:[0-9]* {|reverse_proxy uvicorn:8000 {|" docker/caddy/Caddyfile
docker exec caddy caddy reload --config /etc/caddy/Caddyfile
docker stop uvicorn_green && docker rm uvicorn_green
echo "blue" > .deploy_slot
```
