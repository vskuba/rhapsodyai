# Worker — фоновые исполнители в `src/worker/`

> Всё, что выполняет работу вне запроса пользователя, живёт в `src/worker/<модуль>/<имя>_worker.py`
> и нигде больше. Кто ставит задание — не выполняет его: cronjob и HTTP-роутер только кладут
> сообщение в очередь, работу разбирает воркер, и воркеров может быть несколько.

## 1. Правило размещения

```
src/worker/
├── __init__.py
└── project/
    ├── __init__.py
    ├── task_worker.py        # конвейер задач: Manager / Developer / QA
    └── planning_worker.py    # цепочка фаз планирования проекта
```

| Правило | Почему |
|---------|--------|
| путь `src/worker/<модуль>/<что>_worker.py` | воркеры ищут в одном месте, а не по всему `src/` |
| суффикс `_worker` обязателен | префикс функций равен имени файла (`task_worker_enqueue`), суффикс делает роль модуля видимой в любом импорте |
| подпапка повторяет модуль домена | `src/project/task/…` → `src/worker/project/task_worker.py` |
| в каждой папке пустой `__init__.py` | у самого `src/` его нет — это не пакет, а корень |
| доменная логика остаётся в домене | воркер поднимает окружение и зовёт `task_pipeline_action_run()`; машина состояний живёт в `src/project/task/` |

❌ `src/project/task/task_queue.py` — воркер спрятан внутри домена
✅ `src/worker/project/task_worker.py` — воркер в общем дереве, домен зовётся импортом

## 2. Контракт «триггер ставит — воркер выполняет»

Cronicle-тик и HTTP-эндпоинт обязаны возвращаться за секунды. Они проверяют статусы,
захватывают строки и ставят сообщения — и всё.

```
Cronicle (60s body timeout)          Redis queue `default`        контейнер worker
  task_orchestrator.py                                             rq worker
    task_pipeline_tick()      ──enqueue──▶  [action, action]  ──▶  task_worker_job_run()
      reclaim + claim + enqueue                                      task_pipeline_action_run()
      выход через секунды                                            менеджер, Developer, QA
```

Тик, который ходит к агентам, ломает две вещи сразу: Cronicle накладывает запуски друг на
друга, а масштабирование становится невозможным — один тик = один исполнитель. Из-за этого
запрет жёсткий: **в тике нет ни одного `await` к внешнему агенту**.

Проверить машинно:

```bash
grep -n "task_agent_manager_plan\|task_agent_developer_run" src/cronjob/task_orchestrator.py  # пусто
```

## 3. Очередь — Redis, по одной на профиль нагрузки

| | `task_worker` | `planning_worker` |
|---|---|---|
| Очередь / контейнер | `default` / `worker` | `planning` / `worker_planning` |
| Кто ставит | тик Cronicle (`task_pipeline_tick`) | инструмент, роутер, восстановление в lifespan |
| Что в сообщении | одно действие конвейера | id проекта — job прогоняет всю цепочку фаз |
| Длина работы | до часа (живой Claude Code в shell-оболочке) | до 13 часов (12 фаз по часу) |
| Защита от дубликатов | захват строки, single-flight по типу действия | single-flight по проекту |
| Восстановление | реклейм протухших блокировок на тике | `planning_worker_recover()` при старте uvicorn |

Очереди две, потому что профили нагрузки различаются на порядок: 13 часов против часа.
В общей очереди один запланированный проект занимал бы исполнителя на весь день, а
задачи стояли бы за ним — планирование в интерфейсе так и висело бы в `pending`, хотя
job давно поставлен. Это и есть критерий заводить новую очередь: **не новый домен, а
другая длина работы**. Одинаковые по профилю воркеры остаются в `default`.

Оба контейнера поднимают **пул**, а не одиночный процесс:

```yaml
worker:           rq worker-pool --url redis://redis:6379 -n 3 default
worker_planning:  rq worker-pool --url redis://redis:6379 -n 2 planning
```

`rq worker` без пула — один job за раз. Для конвейера это значит, что Manager одной
задачи держит Developer'а другой; три процесса дают три роли одновременно. Число
процессов — потолок параллельных живых Claude Code, а не пожелание: каждый занимает
свою shell-оболочку.

Новая очередь — это ещё и строка в `redis_queue_init([...])` в `main_uvicorn.py`
и сервис в `deploy.yml` (`docker compose up -d … worker worker_planning`).

Правило выбора для нового воркера: **очередь всегда Redis**. `asyncio.Queue` внутри
uvicorn не переживает рестарт и не масштабируется — один воркер на процесс, а планирование
и конвейер обязаны тянуться несколькими исполнителями.

Следствие рестарта: задание переживает перезапуск uvicorn, поэтому восстановление не имеет
права слепо сбрасывать `running` в `pending` — фазу может прямо сейчас выполнять живой job.
`planning_worker_recover()` отличает такие проекты по flight-ключу и обходит их.

## 4. Что job обязан сделать сам

`rq worker` — отдельный процесс, у него нет lifespan из `main_uvicorn.py`. Поэтому job
поднимает мини-инфраструктуру сам и обязательно убирает за собой:

```python
def task_worker_job_run(action: dict) -> str:   # синхронная: rq зовёт как обычную функцию
    return asyncio.run(_job_async(action))

async def _job_async(action):
    logging_init()
    queue_init([... 'ai_framework_model'])                  # без неё job виснет на ответе агента
    framework_task = asyncio.create_task(ai_thread_framework_run([AiFrameworkAgent()]))
    try:
        ...
    finally:
        framework_task.cancel()
        await mysql_pool_close()                            # свой процесс — свой пул
```

Функция job'а обязана быть импортируемой по полному имени модуля: rq хранит в Redis
**строку** `src.worker.project.task_worker.task_worker_job_run` и восстанавливает функцию по
ней. Отсюда следствие для переездов — см. чек-лист ниже.

## 5. Дубликаты и гонки

| Работа | Защита |
|--------|--------|
| действие с захватом строки (`manager_plan`, `developer`, `qa`, …) | сам захват: строка уже в переходном состоянии, следующий тик её не увидит |
| действие без захвата (`bug_scan`, `finalize`) | single-flight — ключ Redis `task_worker:flight:<kind>` с `nx=True, ex=JOB_TIMEOUT` |
| цепочка фаз проекта | single-flight по проекту — ключ `planning_worker:flight:<project_id>` |

Ключ берётся **при постановке в очередь**, а не внутри job'а: иначе второй вызов
`planning_worker_enqueue` успеет поставить дубль, пока первый job ещё ждёт свободного
воркера. Планирование зовут из трёх мест (инструмент, роутер, восстановление), захвата
строки у фазы нет — без ключа один проект спланировался бы дважды параллельно.

TTL ключа равен потолку job'а: умерший воркер не должен запереть работу навсегда.
Если постановка в очередь упала — ключ освобождается в `except`, иначе работа заперта до
истечения TTL. Освобождение в `finally` job'а обязательно и там, и там.

Умер воркер с захваченной строкой — блокировку вернёт `task_claim_locks_reclaim()` по
таймауту, и работа встанет в очередь на следующем тике. Умер воркер с цепочкой фаз —
фаза останется в `running` до `planning_worker_recover()` при следующем старте uvicorn
либо до пакетного прохода `planning_batch`.

## 6. Лестница таймаутов

Порядок обязателен: каждый следующий уровень длиннее предыдущего, иначе работу отберут
раньше, чем она успеет завершиться.

Конвейер задач:

```
claude_shell_call 300s (WF#55 передаёт 600s)   одно обращение к менеджеру
  < MANAGER_TIMEOUT           3600s            весь прогон планирования (до 13 обращений)
    < TASK_WORKER_JOB_TIMEOUT 3900s            потолок job'а в rq (дефолт rq — 180s!)
      < LOCK_TIMEOUT_SEC      4200s            когда блокировку сочтут протухшей
```

Разработчик — та же лестница со своим верхом: WF#56 передаёт 600s на разбор, 1800s на
реализацию и 600s на самопроверку, `DEVELOPER_TIMEOUT` тоже 3600s, дальше те же 3900 и
4200. Потолок прогона меньше суммы шагов не случайно: круг доработки её превышает, и
рвать прогон должен именно он, а не молчаливое переползание за блокировку.

Планирование — тот же принцип, но потолок job'а считается от **суммы** фаз: job один на
всю цепочку, и внутри него двенадцать последовательных фаз (шесть волн плюс шесть
supplements по одному).

```
PHASE_TIMEOUT_MAX             3600s            потолок одной фазы
  × 12 фаз                  = 43200s           худший случай цепочки
    < PLANNING_WORKER_JOB_TIMEOUT 46800s       потолок job'а, час запаса на запросы к БД
```

Занизили потолок job'а — rq снимет цепочку раньше, чем фаза сорвётся сама, и фаза
останется в `running` до восстановления. Правило общее: **потолок job'а больше суммы
вложенных потолков, а не одного из них.**

Тик Cronicle в лестницы не входит и длинных таймаутов не получает — он короткий по
построению (§2).

## 7. Чек-лист: новый воркер

1. Файл `src/worker/<модуль>/<что>_worker.py`, рядом `__init__.py`, если папка новая.
2. Префикс всех публичных функций и констант — имя файла (`<что>_worker_*`); приватные — внизу файла.
3. В докстринге модуля написать, что именно лежит в сообщении и кто его ставит — следующему это первый вопрос.
4. `job_timeout` задать явно по §6 (дефолт rq 180s почти всегда мал), плюс
   `result_ttl` / `failure_ttl`; в `finally` — `mysql_pool_close()`.
5. Триггер (cronjob или роутер) только ставит сообщение; работу зовёт воркер.
6. Работа без захвата строки — добавить single-flight (§5).
7. Проверить синтаксис и перезапустить **все** контейнеры воркеров: каждый держит свою
   копию кода в памяти.

```bash
docker restart uvicorn worker worker_planning
docker logs --tail 30 worker
```

## 8. Чек-лист: переезд/переименование модуля воркера

rq хранит функцию job'а строкой — переименование модуля обесценивает уже стоящие задания.

1. Убедиться, что очередь пуста — проверять **обе**:
   `docker exec redis redis-cli llen rq:queue:default` и `… rq:queue:planning` → `0`.
2. Переименовать модуль, обновить импорты (`grep -rn "<старое_имя>" --include=*.py .` → пусто).
3. Обновить документацию: `grep -rn "<старое_имя>" .claude/docs/` → пусто.
4. `docker restart uvicorn worker worker_planning`.

## Грабли

1. **Дефолтный `job_timeout` rq — 180 секунд.** Не переопределили — часовой прогон менеджера
   срывается на третьей минуте, а задача остаётся в переходном состоянии до реклейма.
2. **Job без `queue_init([... 'ai_framework_model'])` виснет молча.** Шаги агента уходят в
   очередь движка, которую в этом процессе никто не разбирает; job умирает по таймауту без
   единой ошибки в логе.
3. **Пул MySQL не закрыт в `finally`** — соединения текут по одному на job, и через сутки
   воркер упирается в лимит соединений.
4. **`docker restart uvicorn` без воркеров** — самая частая причина «код правильный, а
   поведение старое»: `worker` и `worker_planning` держат собственную импортированную
   копию модулей.
5. **Переименовали модуль воркера при непустой очереди** — rq не найдёт функцию по старому
   пути, задания уйдут в failed registry молча. Сначала §8, потом переименование.
6. **Long timeout повесили на Cronicle-событие** — лечение симптома: тик обязан быть
   коротким, а длинные таймауты живут на уровне job'а и блокировки (§6).
7. **Восстановление в lifespan отобрало живую работу.** Job переживает рестарт uvicorn,
   поэтому «сбросить всё `running` в `pending`» на старте перезапустит фазу, которую
   воркер выполняет прямо сейчас. Сбрасывать только то, за чем не стоит flight-ключ.
8. **Восстановление позвали до `ai_tool_sync`** — `ai_tool_sync(force=True)` очищает
   таблицу `tool` и наполняет заново; job, стартовавший в это окно, получит пустой
   список инструментов и упадёт с «инструмент не найден».
9. **«Job поставлен, а ничего не происходит»** — почти всегда очередь, а не код: job
   стоит за длинным соседом. Смотреть `docker exec redis redis-cli hgetall
   rq:worker:<id>` — поле `current_job_working_time` покажет, сколько уже занят
   исполнитель, а `llen rq:queue:<имя>` — сколько заданий за ним. Отсюда и разделение
   очередей по длине работы (§3).
