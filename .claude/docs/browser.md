# Browser — контейнер-браузер

> Отдельный сервис с одним Chromium внутри. Держит десятки изолированных сессий, каждая
> из которых — своя страница со своими cookie. Команды принимает по HTTP, живёт неделями.
> Есть пул сессий с API и живое окно на `/admin/browser` — картинка страницы и настоящий
> ввод в неё. Сценарии выполняются по шагам; пишет их LLM по снимку страницы либо
> записывает за человеком его же проход в живом окне. Наблюдатели DOM — дальше.

## 1. Зачем отдельный контейнер

У `uvicorn` и у браузера несовместимые ритмы жизни. `:8011` перезапускается на каждой
правке `.py` — это норма разработки. Страница, которая ждёт сообщения в чужом чате,
чужого рестарта не переживёт: сессия оборвётся, авторизация слетит, наблюдатель DOM
умрёт молча.

Поэтому Chromium вынесен в свой процесс со своим сроком жизни. Правки в `src/browser/`
требуют рестарта `browser` и убивают сессии — правки в остальном коде не трогают его.

Отдельный **язык** при этом не нужен, хотя MutationObserver и сценарии — это JavaScript.
JS выполняется внутри страницы Chromium, Playwright только доставляет его туда по CDP.
Node рядом с Python дал бы второй слой доступа к БД, конфигу и LLM — и ничего больше.

## 2. Состав

```
main_browser.py               # точка входа: lifespan поднимает Chromium
src/browser/
├── browser_pool.py           # один Chromium, сессия = BrowserContext
├── browser_memory.py         # замер памяти: cgroup контейнера + PSS процессов
├── browser_api.py            # HTTP-API: сессии, переходы, storage_state
├── browser_view.py           # вебсокет живого окна: кадры наружу, ввод обратно
├── browser_scenario.py       # схема шагов, подстановка `{{переменных}}`, маскировка
├── browser_scenario_run.py   # прогон шагов по странице → трасса
├── browser_record.py         # запись действий человека в живом окне → шаги
├── browser_inspect.py        # инспектор: подсветка элементов и выбор кликом
└── browser_snapshot.py       # дерево доступности + устойчивые селекторы для LLM

src/uvicorn/routers/browser/
├── browser_upstream.py       # один вход в контейнер: адрес, токен, перенос кода ответа
├── browser_proxy.py          # `/api/browser/*` — сессии и живое окно из админки
├── browser_record.py         # `/api/browser/session/{id}/record*` — запись → черновик
├── browser_scenario.py       # `/api/browser/scenario/*` — хранение, запуск, журнал
├── browser_site.py           # `/api/browser/site/*` — закладки: имя и адрес

src/mysql_/repository/browser/     # `browser_scenario`, `browser_scenario_run`, `browser_site`
data/uvicorn/template/admin/project/browser.html  # страница `/admin/browser`
```

Сессия — это `BrowserContext`, а не отдельный браузер. Контекст изолирует cookie,
localStorage и кэш полностью, но стоит единицы мегабайт против ~150 МБ на процесс.
Платят не за сессии, а за **открытые страницы**.

Реестр сессий живёт в памяти процесса, в БД его нет. Контейнер упал — сессий больше
нет, и строка в базе врала бы до первой уборки.

**Базы у контейнера нет и не будет.** Он ничего не хранит: сценарий приходит телом
запроса, трасса уходит ответом, а хранит и журналирует их `uvicorn`, у которого пул
MySQL уже есть. Второй потребитель базы дал бы контейнеру связность там, где он её
специально не имеет: упавшая база не должна ронять живые страницы.

## 3. API

Порт `8014` опубликован на `127.0.0.1` и только для отладки: сервис говорит с бэкендом
по внутренней сети `os-net`. `BROWSER_API_TOKEN` в `.env` включает проверку заголовка
`X-Browser-Token` на всех роутах, кроме `/browser/health` (на него смотрит healthcheck).

| Метод | Путь | Что делает |
|-------|------|-----------|
| `GET` | `/browser/health` | жив ли сервис, версия Chromium, занято сессий из предела |
| `GET` | `/browser/session` | список сессий + память контейнера |
| `POST` | `/browser/session` | завести сессию (`name`, `url`, `storage_state`, `viewport`) → 201 |
| `DELETE` | `/browser/session/{id}` | погасить; повторный вызов не ошибка |
| `POST` | `/browser/session/{id}/goto` | перевести страницу на URL |
| `GET` | `/browser/session/{id}/storage_state` | cookie и localStorage сессии |
| `POST` | `/browser/snapshot` | снимок дерева страницы с селекторами (раздел 6) |
| `POST` | `/browser/session/{id}/record/start` | начать запись действий (раздел 8) |
| `POST` | `/browser/session/{id}/record/stop` | закончить запись, отдать шаги |
| `GET` | `/browser/session/{id}/record` | идёт ли запись и сколько шагов набралось |
| `WS` | `/browser/view/{id}` | живое окно: кадры и ввод (раздел 4) |

Из админки в контейнер напрямую не ходят: те же маршруты продублированы на `:8011` под
префиксом `/api/browser/` (`src/uvicorn/routers/browser/browser_proxy.py`). Прокси
проверяет куку и права, передаёт тело как есть и возвращает код контейнера — схемы входа
он не повторяет, две копии разошлись бы на первой правке. Адрес контейнера — в
`BROWSER_URL` (`http://browser:8000`), имя сервиса из compose: петлевой `:8014` из
соседнего контейнера не виден.

`storage_state` замыкает круг: состояние авторизованной сессии снимается и передаётся в
`POST /browser/session` следующей — она открывается уже залогиненной, без прохода по форме.

Коды: `404` — нет такой сессии, `409` — предел сессий исчерпан или страница закрыта,
`422` — не прошла схема входа, `502` — страница не открылась (таймаут, мёртвый хост).

```bash
curl -s -X POST http://127.0.0.1:8014/browser/session \
     -H 'Content-Type: application/json' \
     -d '{"name":"чат","url":"https://example.com"}'
```

## 4. Живое окно

`/admin/browser` разделена на пять вкладок — **«Сайты»** (раздел 4.1), **«Сессии»**,
**«Сценарии»**, **«Workflow»** (раздел 5.2) и **«Ошибки»** (раздел 9.1). Сайты идут первыми и открываются по умолчанию: с закладки работа и
начинается — сессию заводят с её карточки. Полоска взята готовой у страницы задач
(`design.css`: `.page-tabs`, `.page-tab`, `.tab-panel`), своя копия правил разошлась бы
с ней на первой правке;
в подписи вкладки счётчиком (`.page-tab-n`) идёт число сайтов, сессий и сценариев.
Выбранная вкладка запоминается в `localStorage` (`browser_tab`) — сценарий правят подолгу
и возвращаться на него после каждого перехода по админке незачем. Неизвестное значение
ключа (осталось от прошлой раскладки вкладок) откатывается на «Сайты».

**Уход на другую вкладку окно не гасит.** Сессия живёт в контейнере и о вкладках админки
не знает; переключение только прячет панель — вебсокет остаётся открытым, страница
остаётся там, где была.

Вкладка «Сессии» показывает страницу сессии и пускает в неё мышь и клавиатуру. Это не
просмотр логов постфактум: видно ровно то, что видит Chromium, и любой клик уходит на
страницу настоящим событием.

**Сессии — вкладки второго уровня**, полосой под выбором сайта: одна страница на вкладку,
«+» рядом заводит следующую, крестик гасит её вместе со страницей. Списком карточек сессии
были раньше; карточками теперь заняты сценарии, а переключаться между страницами вкладки
умеют лучше — это один клик, а не выбор в списке. Живых сессий нет — полоса всё равно
показывает «Сессия 1»: контекст Chromium заводится первым действием («Открыть», «+»,
запуск сценария), а не заранее. Память и предел сессий стоят справа в той же полосе — они
про контейнер, который эти вкладки и расходуют.

**Левая колонка вкладки — сценарии этого сайта: то, что можно запустить прямо
отсюда.** У заголовка стоит счётчик, и он остаётся даже у пустого списка: пропадающий
заголовок читался бы как сбой. Аккордеона здесь больше нет — рядом жили цепочки, и списки
сворачивались по очереди; список остался один, сворачивать нечего.

**Набранные значения подстановок переживают перезагрузку** (`localStorage`,
`browser_play_values`, ключ «вид:номер»): их подбирают руками под конкретный стенд, и
терять их на каждом F5 дороже, чем хранить. Обратная сторона — они лежат на диске
браузера админа, поэтому рядом с полем записи стоит кнопка **🧹**: она забывает всё
введённое разом. Настоящему паролю в этих полях не место — для него есть `secrets`
на прогоне (раздел 5), который не уезжает никуда.

 У каждой карточки кнопка
«Запустить» и поля подстановок: шаги идут по странице открытой вкладки, ради того сценарий
отсюда и гоняют. Селекта выбора сценария больше нет — карточка **и есть** сценарий. Полоса
записи («новый сценарий» + «Старт») переехала над шапкой колонки: она заводит следующий
сценарий, а не управляет одним из списка, и пишет в открытую вкладку.

```
браузер админа ──ws──▶ uvicorn:8011 /api/browser/view/{id} ──ws──▶ browser:8000 /browser/view/{id}
                       (кука, права)                              (CDP-скринкаст, Playwright)
```

**Кадры даёт `Page.startScreencast`, а не цикл скриншотов.** Chromium присылает JPEG сам,
и только когда картинка изменилась. Отсюда главное свойство потока: **неподвижная
страница отдаёт ровно один кадр и замолкает** — навсегда, пока на ней ничего не
происходит. Проверка вида «дождаться трёх кадров» на статичной странице зависнет, и это
правильное поведение, а не сбой.

Каждый кадр **обязан** быть подтверждён `Page.screencastFrameAck`, включая выброшенный
из очереди: Chromium держит ровно один кадр «в полёте» и без подтверждения замолкает.
Очередь короткая (2 кадра): медленному клиенту нужен свежий кадр, а не полная лента.

Формат сообщения вниз — `{"type": "frame", "data": <jpeg в base64>, "url": <адрес>}`.
Адрес идёт с каждым кадром, потому что `page.url` — свойство, а не запрос в браузер.

Второй вид сообщения вниз — `{"type": "error", "text": <первая строка ошибки>}`.
**Неудачное действие не закрывает окно.** Опечатка в адресе, недоступный хост, не
успевшая загрузиться страница — обычное дело для живого окна, и терять из-за них
сессию вместе с выполненным в ней входом нельзя. Клиент показывает текст красным под
экраном, страница остаётся на месте, следующее действие работает.

Сообщения наверх — действия над страницей:

| `type` | Поля | Что делает |
|--------|------|-----------|
| `mouse` | `action` (`click`/`move`/`down`/`up`), `x`, `y`, `button`, `clicks` | клик, наведение, перетаскивание |
| `wheel` | `x`, `y`, `dx`, `dy` | прокрутка |
| `key` | `key` — `Enter`, `Control+a` | нажатие клавиши или сочетания |
| `text` | `text` | набор строки |
| `paste` | `text` | вставка строки одним событием ввода |
| `copy` | — | просит выделение страницы обратно (`clipboard` вниз) |
| `goto` | `url` | переход |
| `back` / `forward` / `reload` | — | история и перезагрузка |
| `tab` | `index` | перевести окно на вкладку |
| `tab_close` | `index` | закрыть вкладку (первую нельзя) |
| `inspect` | `on` | включить или погасить инспектор элементов |

**Координаты — доли (0..1), а не пиксели.** Клиент рисует картинку произвольного размера
и не знает, во что Chromium ужал её под `maxWidth`. Обратный пересчёт делают метаданные
последнего кадра: `deviceWidth`/`deviceHeight` — это viewport в CSS-пикселях.

Доля считается от `getBoundingClientRect()` элемента `<img>`, поэтому **прямоугольник
`<img>` обязан совпадать с картинкой пиксель в пиксель**. Размер ей задают собственные
пропорции кадра и пара `max-width: 100%` / `max-height: 100%`; растянуть картинку по
контейнеру и вписать её `object-fit: contain` нельзя — поля по краям войдут в
прямоугольник, и каждый клик уедет на их ширину. Высоту экран забирает остатком: страница
админки не прокручивается (`.page-content { overflow: hidden }`), и фиксированный
`aspect-ratio` на широком окне срезал бы низ окна сессии без всякой возможности до него
добраться.

Адресная строка прощает пропущенную схему: `example.com` уходит как `https://example.com`.
REST-ручки (`/browser/session`, `/browser/session/{id}/goto`) наоборот отвергают такой
адрес — там его шлёт программа, и угаданная схема скрыла бы её ошибку. Кнопка «Открыть»
без выбранной сессии **заводит новую** на введённый адрес: слать `goto` некому, а адрес
набран именно для того, чтобы его открыли.

Ввод идёт через `page.mouse` / `page.keyboard`, а не через `element.click()`: страница не
должна отличать наблюдателя от человека. Так работают hover, фокус, перетаскивание и
обработчики, которые смотрят на `isTrusted`.

### Буфер обмена

**У чужого Chromium свой буфер, и он пуст.** `Control+v`, переданный клавишей, уходит в
контейнер и вставляет там ничего: то, что человек скопировал у себя, в тот браузер
никогда не попадало. Поэтому обмен идёт текстом через сокет, в обе стороны.

Вставка: обработчик `paste` на документе админки перехватывает событие, берёт
`clipboardData.getData('text')` и шлёт его сообщением `paste`; в странице текст
вставляет `keyboard.insert_text()` — одним событием ввода, как настоящая вставка.
Посимвольный `keyboard.type()` тут не годится: на каждом символе срабатывают подсказки,
автодополнение и маски полей.

Ловушка обработчика: `Control+v` — единственное сочетание, которое `keydown` **не** должен
перехватывать. `preventDefault()` на нём отменяет и само событие `paste`, после чего брать
текст неоткуда. Слушать `paste` нужно на документе, а не на `<div>` экрана: событие
браузер шлёт в активный элемент, и на нередактируемом `div` до обработчика на нём самом
доходит не везде — отсюда проверка `document.activeElement === screenEl`, чтобы не
перехватывать вставку в соседние поля страницы.

Копирование: `Control+c` уходит в страницу как есть (её собственный обработчик копирования
должен отработать), а следом окно шлёт `copy`. Сервер отдаёт `{"type": "clipboard",
"text": …}` — результат `window.getSelection().toString()`; в системный буфер человека его
кладёт уже `navigator.clipboard.writeText()` на стороне админки. Доступ к буферу браузер
даёт только по жесту пользователя и на защищённом соединении — отказ показывается строкой
состояния, а не молча.

### Вкладки

Сессия — это `BrowserContext`, и дочерние окна сайта открываются в нём же: `context.pages`
уже возвращает их в порядке появления, отдельного учёта в пуле не требуется. Первая
страница — сама сессия, дальше идут дочерние; полоска вкладок над экраном показывает их
все, крестик есть только у дочерних.

Список приходит сообщением `{"type": "tabs", "tabs": [{"index", "url"}], "active": N}` —
при открытии окна, при появлении и закрытии страницы, при переходе между вкладками.
**Заголовка страницы в нём нет намеренно**: `page.title()` — вызов в страницу, и занятый
своим JavaScript сайт заставил бы окно ждать его ответа; подпись вкладки собирается из
адреса, полный адрес лежит в `title` элемента.

Всплывшее окно **становится активным сразу** — так делает настоящий браузер, и иначе
форма входа, открытая сайтом в popup, осталась бы невидимой, а страница под ней —
замершей. Скринкаст всегда идёт ровно с одной вкладки: поток со всех сразу утроил бы
трафик ради картинок, на которые никто не смотрит. Переключение гасит старый скринкаст,
чистит очередь кадров и заводит новый.

Закрытие текущей вкладки возвращает окно на первую: страница присылает `close`, обработчик
переводит просмотр. Первую вкладку закрыть нельзя — на ней держится сама сессия, и
попытка отвечает обычной строкой ошибки.

**Проверка вебсокета — сначала сессия, потом права.** `Depends(AuthChecker(...))` к
вебсокету не подходит: он ждёт `Request`, которого здесь нет. Кука доступна
(`SessionMiddleware` обслуживает и websocket-scope), но одной проверки прав мало —
`auth_role_permissions('')` возвращает набор view-по-умолчанию, в котором `BROWSER_VIEW`
есть. Без проверки `user_id` окно открывалось бы вообще без входа в систему.

Коды закрытия: `4403` — нет входа или прав, `4404` — нет такой сессии, `4502` —
контейнер-браузер недоступен. Прокси переносит код контейнера как есть: свой код стёр бы
причину, и «не тот идентификатор» выглядел бы как «браузер лежит».

## 4.1 Сайты

Закладки контейнера: **имя и адрес** того, с чем работают, — личный кабинет, чужая
админка, стенд. До них адрес жил в голове или в истории живого окна, а история умирает
вместе с контейнером.

Хранит их `uvicorn` (таблица `browser_site`, `src/uvicorn/routers/browser/browser_site.py`):
у контейнера базы нет, а закладка обязана пережить и его рестарт, и падение. **Вход в сайт
здесь не лежит** — cookie и `storage_state` это состояние сессии со своим сроком жизни и
своими секретами, а закладка отвечает только на вопрос «куда идти».

| Метод | Путь | Что делает |
|-------|------|-----------|
| `GET` | `/api/browser/site` | список в порядке раскладки (`position`, затем `id`); `?tag=dating` — только помеченные; чтение — `BROWSER_VIEW`; **виден в `/docs`** |
| `POST` | `/api/browser/site` | завести (`name`, `url`, `tags`) → 201, встаёт в конец; правки — `BROWSER_CREATE` |
| `POST` | `/api/browser/site/order` | новая раскладка: `ids` сверху вниз |
| `PUT` | `/api/browser/site/{id}` | переписать имя, адрес и метки |
| `DELETE` | `/api/browser/site/{id}` | удалить карточку; живые сессии не трогает |

**Метки (`tags`) разделяют закладки по принадлежности.** Строка через запятую
(`dating`, `dating,vip`), поле в окне правки карточки. Нужны соседям: DatingAi
спрашивает `GET /api/browser/site?tag=dating` и получает только сайты знакомств —
до этого в селекте анкет висела и эта самая админка, завести на которой учётку
нельзя ничем. Отбор строгий: закладка без меток не попадёт ни в один `?tag=`.
Запрос **без** параметра отдаёт всё — вкладка «Сайты» показывает все карточки,
иначе непомеченная пропала бы и оттуда, и пометить её было бы негде. Метки
приводятся к строчным без пробелов при записи (`browser_site_tags_normalize`), так
что `Dating` и ` dating ` — одна и та же. `?tag=` принимает ровно одну метку;
список через запятую — 422, а не молчаливый пустой ответ.

Строкой, а не отдельной таблицей меток: их единицы, живут они полминуты в окне
правки карточки, и связка ради двух слов стоила бы дороже пользы. Отбор идёт
`FIND_IN_SET`, индекса по `tags` нет — закладок десятки, полный проход по ним
дешевле любого разговора об индексе.

**Адрес принимается только со схемой** (`http://` или `https://`) — как и у REST-создания
сессии: угаданный `https://` скрыл бы опечатку программы. Адресная строка живого окна
наоборот прощает её, и форма вкладки тоже дописывает схему до отправки — там адрес набирает
человек. Имя уникально (409 на занятое): карточки различают по нему, и два «личного
кабинета» с разными адресами человек не разберёт. `file://` и `data:` не берутся: первый
ведёт в файловую систему контейнера, второй даёт opaque-origin страницу, на которой
обработчики ведут себя не как на настоящем сайте.

Вкладка — сетка карточек: имя, адрес и кнопка «Открыть». Первой в той же сетке стоит
карточка **«+ Добавить сайт»** — «плюс» на месте, где человек ищет новый сайт, а не
кнопкой в шапке, которой на этой вкладке нет; она же сообщает пустой вкладке, что сайт
вообще можно завести.

Заводят и правят **одним окном** (`.modal-overlay`, `#siteModal`): у сайта два поля, и
вторая форма была бы копией первой. Заголовок говорит, что происходит («Новый сайт» либо
«Сайт «имя»»), фокус сразу в поле названия, Enter сохраняет, Escape и клик мимо окна
закрывают — клик по самому окну не закрывает, иначе промах по полю стирал бы набранное.
Окно открывают карандаш в углу карточки и клик по карточке; крестик рядом с карандашом
удаляет с подтверждением по имени. Инструменты проступают под мышью: в покое карточка
показывает то, ради чего заведена, а не три кнопки.

**Порядок карточек человек раскладывает мышью** (drag-and-drop, `position` в базе).
Алфавит для этого не годился: рабочий стенд не обязан начинаться на «А», а порядок решает
не только вид вкладки, но и что предложат селекты соседних вкладок. Куда встанет карточка,
показывает полоса по краю соседа — вставка идёт до или после него по половине, над которой
курсор, а не «вместо него». Отпустили — страница перерисовывается сразу и только потом
шлёт `POST /api/browser/site/order`: перетаскивание обязано выглядеть мгновенным, а порядок
всё равно перечитывается следом. Позиции переписываются целиком по присланному списку, а
не сдвигаются по одной: страница знает весь порядок, а частичные сдвиги оставляли бы дыры
и совпадения. Пропавший id ничего не сдвигает и не отвечает 404 — соседняя вкладка могла
удалить сайт, пока карточку тащили. Новая карточка встаёт в конец: заведение сайта не
должно менять то, что человек уже выбрал.

**Отказ сервера показывается в самом окне, и окно не закрывается** — набранное надо
поправить, а не набирать заново. Занятое имя приходит человеческим текстом («сайт с
названием «…» уже есть»): `(1062, "Duplicate entry … for key")` из драйвера в окне правки
не говорит ничего.

Кнопка **«Открыть»** переводит страницу на вкладку «Сессии» и уводит живое окно на адрес
сайта; окна нет — заводит сессию с именем сайта. Закладку жмут, чтобы оказаться на
странице, а не чтобы узнать, что сессию сперва надо создать самому.

### Сессии и сценарии принадлежат сайту

Сайт — единица работы, поэтому и сессии, и сценарии к нему привязаны, но **по-разному, и
иначе быть не может**:

- **сценарий** — колонкой `browser_scenario.site_id` (FK на `browser_site`, `ON DELETE SET
  NULL`): удаление сайта не уносит сценарии, только отвязывает их. Пишут её и форма вкладки
  «Сценарии», и запись за человеком (`record/stop` принимает `site_id`);
- **сессия** — меткой `site_id` в записи пула, **в памяти контейнера**. В базе сессий нет и
  не будет: они умирают вместе с контейнером, и строка в базе врала бы до первой уборки.
  Контейнер эту метку не проверяет и ничего о ней не знает — по ней админка отбирает
  вкладки своей закладки.

Выбранный сайт фильтрует и полосу вкладок, и колонку сценариев. **Ничьи видны всегда**:
сессии и сценарии без `site_id` заведены до появления сайтов, и прятать их значило бы
потерять уже сделанную работу.

### Инспектор элементов

Кнопка со значком выбора — за «Погасить». Включённый инспектор подсвечивает элемент под
курсором, а клик по нему показывает компактный попап в углу окна: тег, **список вариантов
селектора** и начало разметки. Клик по варианту копирует его в буфер.

**Вариантов несколько, потому что «правильный» селектор зависит от того, что переживёт
правку вёрстки, — а это решает человек.** Страница считает их сама:

| Вариант | Когда осмыслен |
|---------|----------------|
| устойчивый | пометка элемента: `id`, `data-testid`, `name`, `aria-label` (тот же алгоритм, что у снимка) |
| по тексту | `li:has-text("Logout")` — у элемента свой короткий текст; переживает перестановку пунктов |
| первый / последний в родителе | `ul > li:last-child` — элемент на краю списка |
| последний из всех | `ul li >> nth=-1` — список разбит на несколько родителей, и `:last-child` дал бы несколько совпадений |
| через двух предков | `div.p-3 > ul > li` — сам элемент ничем не помечен, отличает только место |
| в родителе | `ul li` — самый широкий, обычно неуникален |

Рядом с каждым — **сколько элементов страницы с ним совпадёт**: `1` зелёным годится для
клика, большее число красным означает, что строгий `page.locator` на таком шаге упадёт
(раздел 5), а `?` — что браузер этот селектор не разбирает: псевдоклассы Playwright
(`:has-text`, `>> nth=`) он и не должен понимать, их проверит только прогон.

Текстовый вариант не предлагается элементу, внутри которого больше двух вложенных: у
`div`-обёртки «свой текст» — это текст всех потомков разом, и `:has-text` по нему совпал
бы с половиной страницы. Позиционные — только края списка: «третий» ломается от любой
вставки выше, а «первый» и «последний» переживают добавление в середину.

Работает всё **внутри страницы** (`src/browser/browser_inspect.py`): окно показывает
картинку, и «что это за элемент» на стороне админки вычислить нечем — там пиксели. Обводка
рисуется своим элементом поверх содержимого, а не `outline` на самом элементе: чужой
`outline` меняет вёрстку, а внутри `overflow: hidden` его не видно. **Клик в этом режиме
смотрит, а не нажимает** (`preventDefault`) — иначе выбор ссылки уводил бы страницу раньше,
чем человек прочитал селектор.

Устройство то же, что у записи: `expose_binding` и `add_init_script` ставятся один раз на
сессию (снять их нечем), уже открытые страницы вооружаются отдельным `evaluate`.

**Страниц у сессии больше одной, и это не мелочь.** Сайт открывает дочерние окна, живое
окно само переходит на всплывшее (раздел «Вкладки»), и человек смотрит уже на него.
Поэтому режим включается **во всех страницах контекста**, а подписка `context.on('page')`
догоняет те, что всплыли позже: `add_init_script` даёт новому окну сам скрипт, но не
включённость — она живёт флагом в Python (`entry['inspect']`). Полагаться на
`sessionStorage` тут нельзя: у окна чужого origin своё хранилище, от родителя оно ничего
не наследует. То же исправление сделано и в записи — к началу записи у сессии уже может
быть всплывшее окно, и показывают проход часто именно в нём.
Включённость держит сама страница в `sessionStorage`, поэтому режим переживает переход по
ссылке — ради этого его обычно и включают. Выбранное уходит в очередь записи сессии, откуда
его забирает окно сообщением `{"type": "inspect", "selector", "html", "tag"}`; вверх идёт
`{"type": "inspect", "on": true|false}`.

Селектор считается тем же кодом, что у снимка и записи (`BROWSER_SNAPSHOT_SELECTOR_ONE_JS`):
показать человеку один селектор, а в сценарий записать другой — верный способ чинить
сценарий вслепую.

### Селект сайтов на соседних вкладках

Закладки нужны не только своей вкладке, поэтому полосой сверху (`.scenario-head`) селект
сайтов стоит и на «Сессиях», и на «Сценариях»: на первой выбранный адрес подставляется в
строку адреса (`#urlInput`), на второй — в «Старт» сценария (`#scenarioStartUrl`).

По умолчанию выбран **первый сайт раскладки**: порядок карточек человек задал сам, и
верхняя — та, с которой он чаще всего начинает. Адрес при этом подставляется только в
**пустое** поле: в строке адреса живого окна стоит адрес открытой сессии, и затирать его
нельзя. Если поле уже содержит адрес одной из закладок, селект просто показывает её.

**Выбор подставляет адрес, но никуда не идёт**: «Открыть» и «Запустить» человек жмёт сам,
а выбор из списка — ещё не команда открыть. Селект собирается из того же ответа, которым
живёт вкладка сайтов, — второго запроса за те же адреса нет, и заведённый сайт появляется
в обоих селектах сразу. Выбранное держится по адресу, а не по индексу: список
перечитывается после каждой правки, и порядок в нём меняется вместе с именем.

## 5. Сценарии

Сценарий — последовательность действий над страницей: зайти, заполнить, нажать,
дождаться, забрать текст. Устройство одно на все три способа завести сценарий —
руками в форме, автором по цели словами (раздел 7) или записью за человеком
(раздел 8): детерминированный набор шагов, который можно проверить прогоном.

Обязанности разделены пополам: **шаги выполняет контейнер** (там живут страницы),
**хранит и журналирует `uvicorn`**. Схема шагов при этом одна на двоих —
`src/browser/browser_scenario.py` не импортирует ни Playwright, ни MySQL, поэтому
её одинаково видят обе стороны, и сценарий проверяется схемой уже при сохранении.

**Действия шага** (`action` + обязательные поля):

| Действие | Поля | Что делает |
|----------|------|-----------|
| `goto` | `url` | переход, ждёт `domcontentloaded` |
| `click` | `selector` | клик |
| `fill` | `selector`, `value` | вписать значение целиком |
| `type` | `selector`, `value` | набрать посимвольно (20 мс на клавишу) |
| `press` | `key` | нажать клавишу; с `selector` — по элементу, без него — в окно |
| `select` | `selector`, `value` | выбрать вариант списка |
| `wait_for` | `selector` | дождаться видимого элемента |
| `wait_url` | `url` | дождаться адреса; шаблон в стиле glob (`**/admin`) |
| `wait_ms` | `value` | пауза |
| `scroll` | `value` | прокрутка на пиксели |
| `extract` | `selector`, `name` | забрать текст под именем `name`; `value: "@src"` — атрибут вместо текста |
| `extract_rows` | `selector`, `name`, `fields` | список записей: `selector` — строка, `fields` — что взять внутри неё |
| `assert_text` | `selector`, `value` | проверить, что текст содержит значение |

У шага есть `timeout_ms` (по умолчанию 10 с) и `optional` — шаг, который может не
сработать: баннер согласия либо есть, либо нет, и его отсутствие не сбой.

**Значения полей формы читаются `@value`, и это не атрибут.** У `<input>`,
`<textarea>` и `<select>`, заполненных скриптом, атрибута `value` в разметке нет
вовсе — `getAttribute` отдаёт пусто, хотя значение на экране видно. Текста у них
тоже нет. Поэтому имя `value` разбирается особо: читается свойство узла. Живьём это
единственный способ снять имя, город и описание с карточки анкеты LadaDate.

**`extract` умеет атрибуты.** `value: "@src"` возвращает атрибут вместо текста —
без этого адрес картинки не достать: у `<img>` текста нет, и шаг молча отдавал бы
пустую строку. Совпадений может быть несколько, они склеиваются переводом строки,
как и у текстового `extract`.

**`extract_rows` собирает список записей, а не параллельные строки.** Отдельными
шагами `extract` поля приходят двумя списками — имена и номера, — и сшивать их клиенту
приходится по позиции. Пропущенное значение сдвигает всё, что после, и заметить это
нельзя: пустые значения из склейки выбрасываются, а перенос строки внутри ячейки
неотличим от разделителя записей. На живой панели LadaDate две разные анкеты носят имя
«Diana», так что неверную пару не отличить и глазами.

Здесь поле привязано к своей строке разметкой, и сшивка структурная:

```json
{"action": "extract_rows", "selector": "main .card", "name": "анкеты",
 "fields": [
   {"name": "имя",    "selector": "h5", "mandatory": true},
   {"name": "номер",  "selector": "p",  "mandatory": true},
   {"name": "ссылка", "selector": "a",  "attribute": "href"},
   {"name": "фото",   "selector": ".gallery", "fields": [
      {"name": "адрес", "selector": "img", "attribute": "src"}]}]}
```

Ответ уходит в `extract["анкеты"]` списком объектов.

| Поле | Смысл |
|------|-------|
| `selector` | **относительный** — ищется внутри своей строки |
| `attribute` | снять атрибут вместо текста; у `extract` для этого служит `@`-метка |
| `mandatory` | нет значения — строка не запись: так отсеиваются шапка таблицы, разделитель, рекламный блок |
| `fields` | вложенный список: поле само по себе список записей |

Глубина вложенности ограничена (`BROWSER_SCENARIO_FIELDS_DEPTH`), число записей —
тоже (`BROWSER_SCENARIO_ROWS_LIMIT`): каждый уровень умножает число обращений к
странице на число найденных строк.

**Внутри найденной строки ожидания нет.** Строку дождались, разметка отрисована;
поля, которого нет сейчас, не будет и через десять секунд. Ожидание здесь
складывалось бы: отсутствующее поле, умноженное на число строк, давало шаг длиной в
часы — поймано живьём, пробный сбор не уложился и в две минуты.

**В трассу записи не кладутся** — там остаётся их счёт. Трасса и данные уезжают в
разные колонки (`trace` и `extract`), и список в обеих задвоил бы строку журнала.

**Всё идёт через `page.locator`.** Он строгий: два совпадения селектора — это ошибка,
а не «возьмём первое», — и сам ждёт появления элемента до таймаута. Отдельный
`wait_for` перед кликом поэтому не нужен и только удлиняет сценарий.

**Первый упавший шаг останавливает прогон.** Следующие шаги рассчитывают, что
предыдущий сработал; продолжать — значит получить лавину ошибок вместо одной настоящей.

### Переменные и секреты

В `selector`, `url`, `value` и `key` подставляются `{{имена}}`. Значения приходят
двумя раздельными словарями:

- `variables` — попадают в журнал (адрес стенда, имя проекта). Значения по умолчанию
  лежат в столбце `variables` сценария, переданные на запуске их перекрывают;
- `secrets` — **не попадают никуда**: ни в базу, ни в журнал, ни в лог.

Отсюда два правила. Шаги журналируются **до** подстановки — в трассе остаётся
`{{password}}`. И весь текст ошибок и значений проходит через `browser_scenario_mask`:
Playwright цитирует введённое в собственных сообщениях (`fill("hunter2")`), и без
маски секрет попал бы в базу через текст ошибки. Маскируются значения от 4 символов —
короткие превратили бы в `***` обычные слова.

Нехватка переменной проверяется **до первого шага**: иначе сценарий входа падал бы
только на пароле, потратив полминуты.

### API

Под префиксом `/api/browser/scenario` (`:8011`, кука и права: чтение —
`BROWSER_VIEW`, правки и запуск — `BROWSER_CREATE`):

| Метод | Путь | Что делает |
|-------|------|-----------|
| `GET` | `` | список сценариев |
| `GET` | `/parser` | только те, что отдают данные, — с моделью каждого (для клиентов) |
| `POST` | `` | завести; шаги проверяются схемой → 201 |
| `GET` | `/{id}` | сценарий целиком + `variables_used` — какие подстановки он ждёт |
| `PUT` | `/{id}` | переписать целиком — так же это сделает агент самопочинки |
| `DELETE` | `/{id}` | удалить вместе с журналом (каскад) |
| `POST` | `/{id}/run` | прогнать: `session_id`, `variables`, `secrets`, `keep_session` |
| `GET` | `/{id}/run` | журнал прогонов с трассой |
| `POST` | `/author` | написать сценарий по цели словами (раздел 7) |

Внутри контейнера тот же прогон доступен как `POST /browser/scenario/run` — сценарий
целиком в теле, без базы.

**`GET /parser` — вход для соседних проектов.** Клиент (DatingAi) не должен знать ни
селекторов, ни разметки: он берёт отсюда список того, что вообще может получить, и
зовёт обычный `POST /{id}/run`. Разметка чужого сайта меняется — правится сценарий
здесь, клиента это не касается и его выкладки не требует.

```json
{"id": 84, "name": "анкеты: список", "goal": "…", "status": "active",
 "returns": [{"name": "анкеты", "kind": "rows",
              "fields": ["имя", "город", "номер", "ссылка", "фото"]}]}
```

`kind` различает форму ответа: `rows` — список записей, `text` — строка (несколько
совпадений склеены переносами, старое поведение `extract`). Имена вложенных полей
идут через точку (`фото.адрес`). Селекторы наружу не отдаются намеренно — иначе
клиент снова прирос бы к разметке, от которой его и уводят.

**Код ответа — про запрос, а не про результат сценария.** Не тот `session_id` — 404,
нехватка переменной — 422, закрытая страница или исчерпанный предел сессий — 409,
а сценарий, упавший на третьем шаге, — **200 со `status: "error"`**. Иначе журнал
прогонов пришлось бы собирать из кодов HTTP.

Трасса возвращается всегда, и на ошибке тоже: без неё ответ «не сработало» бесполезен,
а с ней видно, на каком шаге и с чем встали — из этого агент самопочинки и напишет
задачу на переписывание сценария.

### Журнал

`browser_scenario_run` пишется и на успехе тоже: «сценарий сломался» видно только в
сравнении с тем, как он работал раньше — сколько шагов проходил и за сколько. Метка
`status` самого сценария ставится по итогу прогона: `active` — прошёл, `broken` —
упал, и по метке видно, что чинить, без чтения журнала.

Сессию прогон берёт свою (временную, гасится после) либо чужую по `session_id` —
чужую он не гасит никогда: сценарий часто крутят на странице, которую человек в этот
момент смотрит в `/admin/browser`. `keep_session` оставляет и свою — посмотреть, где
сценарий оказался.

```bash
# вход в админку: пароль уходит `secrets`, в шагах остаётся `{{password}}`
curl -s -X POST http://127.0.0.1:8011/api/browser/scenario/1/run \
     -H 'Content-Type: application/json' -b cookie.txt \
     -d '{"secrets":{"username":"…","password":"…"}}'
```

### Страница «Сценарии»

Вторая вкладка `/admin/browser`: сверху шапка с выбором сессии, ниже слева список сценариев
с метками `draft` / `active` / `broken`, справа — сам сценарий. Имя, цель и стартовый адрес
идут строкой и парой полей, ниже две колонки: шаги, переменные по умолчанию и подстановки
слева, прогон и его трасса справа.

Порядок работы — завести кнопкой «+», вписать шаги JSON и «Сохранить»; либо «Написать по
цели» — тогда шаги пишет автор (раздел 7) по цели и стартовому адресу, и сохраняет их сам.

Удаляют сценарий крестиком в его карточке — сразу за меткой состояния; крестик проступает
под мышью и спрашивает подтверждение с именем. Кнопки «Удалить» в форме нет намеренно:
чтобы стереть чужой сценарий, его пришлось бы сперва открыть, потеряв несохранённые правки
текущего. Удаление соседа форму не трогает, удаление открытого — обнуляет её.

**Сессия выбирается один раз на всю вкладку**, а не у каждой кнопки. Селект в шапке по
умолчанию показывает ту сессию, которую человек открыл на вкладке «Сессии»: сценарий почти
всегда пишут по странице, которую и так держат перед глазами и где вход уже сделан руками.
Выбрал другую — селект запоминает выбор и за соседней вкладкой больше не следует. Погашенная
сессия из селекта пропадает и молча не подменяется временной: гнать шаги не туда, куда
человек смотрел, — худший вид сюрприза. Пусто — заведётся временная; галка «оставить сессию»
держит её живой после прогона, и где сценарий встал, видно на вкладке «Сессии». Подпись
рядом с селектом говорит, что именно сейчас произойдёт.

**Переменные по умолчанию — тоже поля, а не JSON**: строка «ключ — значение», «+ переменная»
добавляет её, крестик убирает, иконка дискеты рядом с заголовком сохраняет сценарий целиком
(та же кнопка «Сохранить» сверху — просто под рукой у того блока, который правят). JSON
здесь стоил дороже, чем помогал: забытую запятую страница за человека не разберёт, и отказ
приходил на сохранении, когда правка уже сделана. Строка без ключа в базу не уезжает —
начатую и брошенную строку сохранять нечем. Ключ решает, чем станет подстановка (переменной
или секретом), поэтому список справа перерисовывается прямо во время набора.

Подстановки — **список полей, а не JSON**. Ключи собираются из сырого текста шагов
регуляркой по `{{имя}}`: отдельный список ключей был бы вторым источником правды и разошёлся
бы с шагами на первой же правке, а по сырому тексту поля появляются, пока JSON ещё дописан
наполовину. Человеку остаётся вписать значения.

**Корзина определяется по одному признаку — есть ли у ключа значение в «Переменных».**
Есть — уйдёт как переменная: в базу вместе со сценарием и в журнал. Нет — уйдёт секретом:
только в этот запрос, ни в базу, ни в журнал; такие ключи в списке подписаны рыжим. Поэтому
отдельного поля «Секреты» больше нет — признак и так однозначный, а два поля заставляли
держать одно и то же имя в двух местах.

Кнопка «+ ключ» добавляет подстановку, которой в шагах ещё нет: автору сценария логин с
паролем нужны до того, как появится первый шаг с ними. Такие ключи снимаются крестиком,
выведенные из шагов — нет. Набранные значения живут только в форме и при переходе на другой
сценарий стираются: перенести чужой пароль в чужую форму хуже, чем набрать его заново.

Трасса рисуется таблицей: номер, действие, цель шага, время, упавшая строка подсвечена.
Цель показывается **до подстановки** — там, где в шаге стоит `{{password}}`, в трассе
стоит он же. «Журнал» показывает прошлые прогоны того же сценария в том же виде.

## 5.2 Что из браузера видно в `/docs`

Схема OpenAPI на `/docs` — витрина для внешних потребителей, а не полный список ручек.
Показываем то, чем работает сосед: **сайты, сценарии, сессии и ошибки**. Ими DatingAi
заводит вкладку, гоняет по ней сценарии входа и переписки, снимает `storage_state`.

Скрытым остаётся то, что делают руками со страницы `/admin/browser`: запись сценария
(`/session/{id}/record/*`) и его переписывание агентом (`/scenario/author`). Снаружи их
никто не зовёт, и в витрине они были бы шумом.

Долгое время всё было наоборот: сценарии и сессии прятались, а видны были цепочки,
которыми не пользовался никто. Правится это флагом `include_in_schema` при регистрации
роутера в `main_uvicorn.py` — он перекрывает настройку отдельных маршрутов.

Права не ослаблены: обе ручки закрыты `BROWSER_VIEW`. Авторизация — либо кука сессии
админки, либо заголовок `X-API-KEY` с токеном из `user_access_token` (`auth_get_current_user`);
без того и другого — `401`.

## 6. Снимок страницы для LLM

Сценарий пишет модель, а не человек с мышью. Значит, ей нужно видеть страницу — но ни
скриншот, ни HTML для этого не годятся: по картинке нельзя написать шаг (там нет ни ролей,
ни селекторов), а разметка админки — сотни килобайт, из которых значимы полтора десятка
строк. `POST /browser/snapshot` (`src/browser/browser_snapshot.py`) отдаёт дерево
доступности в режиме `ai` — то же, что читает скринридер: по строке на элемент, роль,
подпись, состояние.

```
- textbox "Имя пользователя / Email" [ref=e9 sel="#username"]
- button "Войти" [ref=e13 sel="#loginBtn"] [cursor=pointer]
```

**`ref` и `sel` — разные вещи, и путать их дорого.** `ref=e9` приписывает Playwright; он
живёт **до следующей навигации** и годится, чтобы осмотреться и потыкать здесь и сейчас
(`page.locator('aria-ref=e9')`). В сохранённый сценарий кладут `sel` — селектор, вычисленный
на самой странице и проверенный на единственность (`querySelectorAll(css).length === 1`).
Завтра тот же элемент будет `e17`, а `#username` останется.

Порядок предпочтений — от долгоживущего к хрупкому: `id`, `data-testid`/`data-test`/`data-qa`,
`name`, `aria-label`, `placeholder`, прочие `data-*`, класс, и лишь в конце `role=…[name=…]`.
Селектор с индексом (`div:nth-child(3)`) не выдаётся никогда: он ломается от любой вставки
выше по дереву, и сценарий на нём молча начинает кликать не туда — это хуже честного падения.
Классы состояния (`active`, `open`, `disabled`, …) из цепочки выбрасываются: `button.page-tab.active`
перестанет совпадать в тот момент, когда вкладку переключат, — а элемент остался тем же.

| Поле | По умолчанию | Смысл |
|------|--------------|-------|
| `session_id` | — | снять с живой сессии; иначе заводится временная |
| `url` | — | куда перейти перед снимком; с `session_id` — навигация той же сессии |
| `selector` | `body` | корень поддерева: `form` вместо всей страницы |
| `interactive_only` | `true` | только то, что можно нажать и заполнить, — без `generic`-обёрток |
| `depth` | `0` | глубина дерева; `0` — без предела |
| `keep_session` | `false` | не гасить свою временную сессию |

Нужен либо `session_id`, либо `url`. Ответ: `snapshot` (текст с приписками `sel`), `elements`
(разобранный список), `url`, `title`, `truncated`, `session_id`, `session_kept`. Пределы —
60 элементов и 20000 символов: больше модели всё равно не помогает, а контекст съедает.

Коды те же, что у остального API, и описывают запрос, а не результат: `404` — нет такой
сессии, `422` — не задан ни `url`, ни `session_id`, либо корневой селектор совпал с
несколькими элементами, `409` — страница сессии закрыта, `502` — страница не открылась.

```bash
curl -s -X POST http://127.0.0.1:8011/api/browser/snapshot \
     -H 'Content-Type: application/json' -b cookie.txt \
     -d '{"url":"http://uvicorn:8000/login"}'
```

## 7. Автор сценариев

Здесь сценарий не показывают руками, а задают целью словами: шаги пишет модель, глядя на
снимки живой страницы. `POST /api/browser/scenario/author`
(`src/uvicorn/routers/browser/browser_author.py`, логика — `browser_author_run.py`) живёт на
стороне `uvicorn`: здесь LLM, база и журнал, а в контейнере — только страницы. Правка автора
требует рестарта `uvicorn`, но **не** `browser`: живые сессии её переживают.

Виток цикла всегда один и тот же:

```
снимок страницы → LLM предлагает следующие шаги → шаги проходят схему BrowserScenario
   → выполняются в живой сессии → снимок нового состояния → следующий виток
```

Первый шаг автор не придумывает: переход на `start_url` задан заданием, и смотреть на
страницу нужно уже после него. Дальше модель пишет по тому, что видит, а не по тому, что
помнит о вёрстке, — между витками страница меняется.

| Поле запроса | По умолчанию | Смысл |
|--------------|--------------|-------|
| `name` | — | имя будущего сценария, уникальное |
| `goal` | — | цель словами; по ней сценарий перепишут, когда вёрстка поедет |
| `start_url` | — | с какой страницы начинать |
| `variables` | `{}` | подстановки; попадут в базу и журнал |
| `secrets` | `{}` | пароли и токены; ни в базу, ни в промпт — модель видит только имена |
| `session_id` | — | писать в этой сессии; пусто — завести свою и погасить в конце |
| `node_id` | — | LLM-нода; пусто — catchall |
| `save` | `true` | сохранить результат в браузерные сценарии |

Ответ приходит с кодом 200 и на недостигнутой цели: `status`, `reason`, `steps`, `iterations`
(журнал витков: адрес, мысль модели, предложенные шаги, ошибка), `verify`, `extract`,
`scenario_id`, `scenario_status`. Неудачный заход тоже ценен — по журналу видно, на каком
шаге модель застряла, а написанное до срыва ложится в черновик и правится руками. Код 502
означает сбой окружения: контейнер не ответил, LLM не настроена.

**Цикл ограничен с двух сторон.** `BROWSER_AUTHOR_ITERATION_LIMIT = 8` витков и
`BROWSER_AUTHOR_BUDGET_SECONDS = 600` на всё вместе. Модель, которая не понимает страницу,
иначе крутила бы цикл до конца квоты, каждый раз предлагая тот же не работающий клик. За
ответ — не больше `BROWSER_AUTHOR_BATCH_LIMIT = 8` шагов: чем длиннее пачка, тем дальше
модель уходит от того, что видела, — после первой же навигации остальные селекторы выдуманы.

**`drop: N` — отказ от написанного.** Тупик (открыл несуществующий раздел, кликнул не ту
вкладку) выполняется без ошибки и потому оседает в сценарии навсегда. `drop` вычёркивает
столько последних шагов; страница при этом остаётся где была, и следующие шаги пишутся от
неё. Первый шаг не трогается никогда — без перехода на стартовый адрес сценарий начинался бы
с пустой вкладки.

**`active` только после проверки с нуля.** Готовый сценарий прогоняется ещё раз в чистой
сессии, и `active` он получает, только если автор признал цель достигнутой **и** проверка
прошла. Сценарий, который работает лишь там, где вход уже выполнен и раздел открыт, завтра
не воспроизведётся, — такой сохраняется как `draft`. Отдельно это ловит оборванный на первом
витке заход: в нём один переход на стартовый адрес, и проверку он проходит всегда — перейти
по адресу получается сколько угодно раз.

```bash
curl -s -X POST http://127.0.0.1:8011/api/browser/scenario/author \
     -H 'Content-Type: application/json' -b cookie.txt \
     -d '{"name":"задачи в работе","goal":"Войти в админку и вернуть список задач в работе",
          "start_url":"http://uvicorn:8000/admin/task","node_id":4,
          "secrets":{"username":"…","password":"…"}}'
```

Правила автора лежат в коде (`_prompt_system`), а не в базе: они про схему шагов и меняются
вместе с ней. Справка по действиям собирается из самой схемы `BROWSER_SCENARIO_ACTIONS`,
чтобы промпт не разошёлся с ней. Смысл правил:

- селектор для `click`, `fill`, `wait_for` — только из `sel="…"` снимка, `ref=eNN` в сценарий
  не кладут никогда; для `extract` селектор модель составляет сама — он должен совпадать со
  всеми элементами списка сразу;
- адреса не угадывать: `goto` — на стартовый адрес или на видимую в снимке ссылку, до
  остальных разделов доходить кликами;
- в снимке только то, что видно сейчас: пункт свёрнутого подменю сначала раскрывают кликом,
  а потом смотрят новый снимок;
- сценарий потом проигрывают с нуля — шаги входа нужны, даже когда нужная страница уже
  открыта прямо сейчас.

## 8. Запись сценария за человеком

Обратный ход к автору: человек показывает проход руками в живом окне, а на выходе получает
готовый черновик. Так дешевле всего описать то, что трудно объяснить словами, — незаметная
кнопка, порядок полей, промежуточная страница.

Внизу карточки сессии, за разделителем, — поле имени (по умолчанию «новый сценарий») и
кнопка **«Старт»**. Нажали — кнопка становится красной «Остановить», в шапке карточки
загорается мигающая точка, и живое окно этой сессии открывается само: записывать нечего,
пока человеку негде действовать. Дальше он просто работает — кликает, заполняет формы,
переходит по ссылкам. «Остановить» → уведомление «Сценарий записан: «имя», шагов N», и
черновик появляется на вкладке «Сценарии».

**Слушатели живут на самой странице** (`context.expose_binding` + `context.add_init_script`,
`src/browser/browser_record.py`): только там видно, на какой элемент пришёлся клик и что
оказалось в поле, — из CDP-события мыши не вывести ни того, ни другого, там одни координаты.
Ни привязку, ни init-скрипт Playwright снять не умеет, поэтому ставятся они **один раз на
сессию**, а «идёт запись или нет» решает флаг на стороне Python: страница шлёт события
всегда, лишние выбрасываются. Init-скрипт достаётся только новым документам, так что уже
открытая страница вооружается отдельным `page.evaluate` — запись начинается там, где человек
стоит, а не со следующего перехода.

**Состояние записи лежит в записи сессии пула** (`entry['record']`), а не в отдельном реестре:
так оно гаснет вместе с сессией само, и `browser_record` не приходится импортировать из
`browser_pool` — круговой импорт разорван по месту.

Селектор считается тем же кодом, что и у снимка (`BROWSER_SNAPSHOT_SELECTOR_ONE_JS`): шаг,
записанный за человеком, и шаг, написанный автором по снимку, обязаны адресовать элемент
одинаково — иначе один сценарий чинился бы двумя способами.

**Что превращается в шаги.** Клик (`click`), ввод в поле (`fill`), выбор в списке (`select`),
Enter и Escape (`press`), переход, набранный в адресной строке живого окна (`goto`). Переходы
по ссылкам в шаги не идут: их уже записал клик, и `goto` рядом с ним только увёл бы страницу
до того, как клик сработал.

Сырой поток событий приводится к сценарию по дороге:

- **`event.isTrusted`** отсекает клики, которые страница сделала сама: клик по `<label>`
  подставляет второй клик по полю, и в сценарий попал бы лишний шаг;
- **Enter над формой сворачивается в клик по кнопке отправки.** Браузер на Enter сам кликает
  кнопку, и приходят оба события; на прогоне это два действия — Enter уводит страницу, и
  кнопку следом искать негде. Различает их `event.detail`: у клика от клавиатуры он ноль.
  Остаётся клик — он говорит, по чему именно нажали, а Enter об этом умалчивает;
- **поле дописывается, а не копится.** Правку по буквам и возвраты к полю склеивает
  последний `fill` с тем же селектором: в сценарии должно остаться итоговое значение;
- **Enter сбрасывает поле до себя.** `change` набранного поля придёт уже после нажатия, а то
  и не придёт вовсе, если страница успеет уйти, — значение снимается прямо в обработчике
  клавиши;
- **пустое значение выбрасывается целиком**: схема требует непустой `value`, и одно случайно
  стёртое поле обрушило бы проверку вместе со всей записью;
- **флажки и переключатели не пишутся как `fill`** — у них меняется состояние, а не значение,
  и повторяет его именно клик.

**Пароль в сценарий не попадает.** Значение `input[type=password]` подменяется на
`{{password}}` ещё на странице, до отправки в Python: сценарии лежат в базе и видны в
админке. Дальше это обычная подстановка — значение подставят на прогоне из «Секретов»
(раздел 5).

Сохраняет запись сторона `uvicorn` (`src/uvicorn/routers/browser/browser_record.py`): у
контейнера базы нет. Шаги проходят ту же схему `BrowserScenario`, что и написанные руками —
предел в 100 шагов и длина значений часть контракта сценария, а не свойство записи. Первым
шагом дописывается `goto` на стартовый адрес: сценарий прогоняют на чистой сессии, и без
него он начался бы с `about:blank`.

Сохраняется **черновиком** (`draft`): человек показал проход, но имена подстановок, цель и
лишние шаги правит уже в форме — до того, как сценарий пойдёт в расписание.

Коды: **409** — «записывать было нечего: ни одного действия» (считаются снятые действия, а не
шаги: дописанный `goto` сделал бы состоявшейся пустую запись), **422** — запись не сложилась
в сценарий. Имя сценария уникально в базе, а по умолчанию оно у всех записей одно, поэтому
занятое имя получает хвост ` (2)`, ` (3)`: иначе вторая запись падала бы на ограничении, а
человек терял бы вместе с ней все свои действия.

Набранное в поле имя хранится в JS-карте, а не в самом поле: список сессий перерисовывается
каждые десять секунд, и вместе с карточкой имя пропадало бы на полуслове. По той же причине
состояние кнопки берётся из флага `recording` в ответе сервера, а не из клика по ней.

### Прогон из карточки

Под полосой записи, за вторым разделителем, — селект существующих сценариев и кнопка
**«Запустить»**. Записанное здесь же и проигрывается, в той самой сессии, которую человек
видит в окне: пройти руками, остановить запись, выбрать черновик в соседнем селекте и
посмотреть, как он идёт сам, — весь круг, не уходя с карточки.

Выбрали сценарий — под полосой сразу проступают его подстановки строками «ключ: значение»
(`GET /api/browser/scenario/{id}` → `variables_used`). Умолчания из «Переменных» подставлены,
ключи без умолчания подписаны рыжим — это будущие секреты. Корзина считается тем же
признаком, что и на вкладке «Сценарии» (раздел 5): есть умолчание — уйдёт `variables`, нет —
`secrets`, мимо базы и журнала.

**Кнопка серая, пока заполнено не всё.** Пустое поле — это не «значение по умолчанию»,
а несобранный вход: сценарий с пустым паролем дошёл бы до формы входа и упал на ней, потратив
минуту и оставив в журнале ложную поломку. Отсутствие подстановок пустотой не считается —
сценарий без ключей запускается сразу.

Прогон уходит в `POST /api/browser/scenario/{id}/run` с `session_id` карточки и
`keep_session: true`: сессия человека не наша, гасить её после прогона нельзя (флаг вообще
касается только временных сессий, `browser_scenario_run.py`). Живое окно открывается до
запроса — шаги смотрят, а не угадывают по итоговому уведомлению. Пока идёт прогон, кнопка
читается «Идёт…» и остаётся серой.

Состояние полосы — выбор, значения, признак «идёт» и разобранные подстановки — лежит в
JS-картах по `session_id`, а не в DOM: перерисовка списка раз в десять секунд иначе стирала
бы набранный пароль и возвращала кнопку в исходное. Сверх того перерисовка целиком
пропускается, пока фокус стоит в поле или селекте списка, — она уводит каретку на середине
слова. Селект собирается из того же ответа, которым живёт вкладка «Сценарии» (второго запроса
за те же имена нет), а разобранные подстановки сбрасываются при сохранении сценария: правка
меняет ключи, и кэш спрашивал бы прошлую редакцию.

## 9.1 Журнал ошибок

Ошибку живого окна видел только тот, кто в ту секунду смотрел в строку состояния:
сокет показал её и забыл. Разбираться потом было не с чем — оставалось воспроизводить
наугад. Теперь всё сломавшееся ложится в `browser_error` и видно на вкладке «Ошибки».

Пишет `uvicorn` (`src/uvicorn/routers/browser/browser_error.py`), а не контейнер: базы у
контейнера нет и не будет. Источники:

| `source` | Кто пишет | Что попадает |
|----------|-----------|--------------|
| `view` | прокси вебсокета по дороге к клиенту | неудачное действие в живом окне + адрес страницы из последнего кадра |
| `proxy` | он же | обрыв самого прокси |
| `scenario` | `browser_scenario_run` | упавший шаг: номер, имя сценария |
| `page` | страница админки (`POST /api/browser/error`) | её собственный сбой: отказ запроса, неразобранный ответ |

Внешних ключей у таблицы нет намеренно: сессия живёт в памяти контейнера, а сценарий к
моменту разбора могли удалить — ошибка обязана пережить и то, и другое. Контекст лежит
столбцом JSON (`action`, `selector`, `step_no`, `scenario_id`): без «что делали» запись
превращается в текст без применения.

**Сбой журнала не роняет работу** (`observability_rules.md`): `browser_error_write` ловит
собственные исключения — упавшая запись превратила бы одну понятную ошибку в две
непонятных. Чистка ручная, кнопкой на вкладке: TTL нет, потому что «само удалилось перед
тем, как я посмотрел» — худшее свойство для отладки. Список отдаётся и в `/docs`
(`GET /api/browser/error`), запись и очистка скрыты.

## 9. Память и предел сессий

`GET /browser/session` отдаёт два разных числа, и путать их нельзя:

- `container_mb` — сколько с контейнера спрашивает ядро (cgroup). Именно оно упирается
  в `mem_limit` и приводит к OOM.
- `chromium_pss_mb` — сколько занимают процессы Chromium с честным делением общей памяти.
  RSS рядом приведён для сравнения и **завышает вдвое**: рендереры делят код и данные,
  а RSS считает их каждому целиком.

Замер на 10 сессиях (`mem_limit: 4g`):

| Состояние | container | chromium PSS | chromium RSS |
|-----------|-----------|--------------|--------------|
| пустой контейнер | 203 МБ | 109 МБ | 249 МБ |
| 10 сессий, `about:blank` | 347 МБ | 255 МБ | 986 МБ |
| 10 сессий, статья Википедии | 1180 МБ | 1076 МБ | 2233 МБ |

То есть пустая сессия стоит ~14 МБ, страница обычного сайта — ~83 МБ. 4 ГБ — это ~45
таких страниц. `BROWSER_SESSION_LIMIT` по умолчанию **25**: половина расчётного максимума,
запас на то, что долгоживущая SPA растёт со временем и стоит дороже статьи.

## 10. Настройки compose

| Параметр | Почему именно так |
|----------|-------------------|
| `shm_size: 1gb` | 64 МБ `/dev/shm` по умолчанию Chromium не хватает — тяжёлая страница падает с «Target crashed». Флаг `--disable-dev-shm-usage` лечит то же, но уводит браузер на диск |
| `init: true` | Chromium плодит процесс на вкладку; без reaper-а PID 1 зомби копятся неделями, а контейнер столько и живёт |
| `mem_limit: 4g` | утечка страниц должна убивать один контейнер, а не машину вместе с базой |
| `image: rhapsodyai-uvicorn:latest` | тот же образ, что у сервера: Chromium в нём уже стоит, второй сборки не будет |
| `ports: 127.0.0.1:8014:8000` | наружу публиковать нечего |

## Грабли

1. **Считать память по RSS** — цифра завышена вдвое, предел сессий выйдет вдвое меньше нужного.
2. **`page.title()` в списке сессий** — уходит в браузер и ждёт ответа; занятая своим JS
   страница подвесит весь список. В списке только `page.url` — это свойство, а не запрос.
3. **Рестарт `browser` ради правки в остальном коде** — сессии умрут зря. Контейнеру
   нужен рестарт только на изменения `src/browser/` и `main_browser.py`.
4. **Память не возвращается сразу после закрытия сессий** — аллокатор держит арены;
   через несколько минут число оседает. Утечкой это считать рано.
5. **Ждать поток кадров от неподвижной страницы** — его не будет. Кадр приходит на
   изменение картинки; после действия ждут *новый* кадр, а не «ещё несколько».
6. **Снимать слушателей записи** — `expose_binding` и `add_init_script` не снимаются.
   Ставить их на каждый старт записи значит получить дубли событий: гасит запись флаг
   в Python, а не удаление слушателей.
6. **Не подтвердить кадр** — скринкаст замолкает навсегда, и выглядит это как «браузер
   завис». Подтверждать нужно каждый кадр, даже тот, который выбросили из очереди.
7. **Проверять на вебсокете только права** — пустая роль проходит: у неизвестной роли
   набор view-по-умолчанию. Сначала `user_id` в сессии, потом право.
8. **Проверять ввод по `data:`-адресу** — REST-создание сессии такой URL не примет
   (только http/https), а на opaque-origin странице обработчики ведут себя иначе.
   Тестовую страницу проще отдать `python3 -m http.server` внутри самого контейнера.
9. **Класть пароль в шаги сценария** — он уедет в базу и в журнал. Пароль передаётся
   на запуск полем `secrets`, в шагах остаётся `{{password}}`.
10. **Селектор, совпадающий с двумя элементами** — у `click`, `fill`, `assert_text` не
    «возьмётся первый», а упадёт шаг. Так и задумано: молча кликнуть не туда хуже, чем
    остановиться. У `wait_for` и `extract` строгость снята — они работают со списком,
    и селектор строки совпадает со всеми строками сразу.
11. **Ждать поток кадров или адрес после прогона своей сессии** — временная сессия
    гасится в `finally`, у закрытой страницы `page.url` уже не спросить. Адрес
    снимается до закрытия; нужна живая страница — `keep_session`.
12. **Класть `ref=e12` из снимка в сценарий** — ссылка живёт до первой навигации, и
    сохранённый шаг перестанет находить элемент уже на следующем прогоне. В сценарий
    идёт `sel`, `ref` — только для разговора «здесь и сейчас».
13. **Селектор с классом состояния** — `button.page-tab.active` перестаёт совпадать при
    переключении вкладки. Снимок такие классы выбрасывает сам, но написанный руками
    селектор их не фильтрует.
14. **Роль с подписью как основной селектор** — `role=button[name="Разработка"]` ломается
    от счётчика внутри кнопки: подпись становится «Разработка 12». Снимок сначала ищет
    `data-*`, и только потом падает на роль.
15. **Резать `.sql` по `;` своим сплиттером** — точка с запятой встречается внутри
    `COMMENT '…'`, и оператор развалится на середине. Файл скармливают клиенту
    `mysql` целиком.
16. **`companion_id` по умолчанию у автора** — `framework_model_create` ставит `0`, а у
    `agent_session.companion_id` внешний ключ на `companion`. Запись хода автора в журнал
    падает уже **после** ответа модели, и ответ пропадает зря. Передаётся `None`.
17. **Ждать от автора ссылку, скрытую от его роли** — меню админки показывает группу
    «Проекты» только роли `admin`, а тестовая учётка `qa` её не видит. Модель не найдёт
    раздел и начнёт угадывать адреса. Такой цели дают прямой `start_url`.
18. **Пустой текст у `asyncio.TimeoutError`** — `str(e)` отдаёт пустую строку, и причина
    в журнале выглядит как «LLM не ответила: ». По ней не отличить таймаут от отказа
    провайдера; текст берётся через `_exception_describe`.
19. **Ждать от автора живую catchall-ноду** — нода 6 начинается с локальной `gx10/*`, и
    пока та не отвечает, весь виток уходит в таймаут фоллбэка. На прогонах задаётся
    `node_id` с внешними провайдерами.
20. **Кнопка окна при закрытом вебсокете** — `send()` молча ничего не делает, и «Открыть»
    выглядит сломанной кнопкой. Действию, у которого есть осмысленный запасной ход,
    его прописывают: «Открыть» без сессии заводит сессию.
21. **`object-fit: contain` на картинке окна** — поля по краям попадают в прямоугольник
    `<img>`, по которому нормируется клик, и весь ввод смещается. Картинку вписывают
    размерами (`max-width` / `max-height`), а не обрезкой содержимого.
22. **Высота во всю страницу в админке** — `.page-content { overflow: hidden }` запрещает
    прокрутку, и всё, что не влезло, недостижимо. Полноэкранной странице высоту раздают
    сверху вниз: `height: 100%` контейнеру, `min-height: 0` колонкам, `flex: 1` тому
    элементу, который должен забрать остаток.
23. **Юникодная стрелка вместо значка** — `←` рисуется шрифтом, а в минимальном образе
    нужного шрифта может не быть: кнопка выглядит пустым белым квадратом. Значки в
    проекте — вставленный `<svg>` с `stroke="currentColor"`.
24. **`preventDefault()` на `Ctrl+V`** — отменяет и событие `paste`, из которого только и
    берётся текст. Это единственное сочетание, которое `keydown` окна пропускает мимо.
25. **`lambda` в `page.on('close', …)`** — снять такую подписку нечем: `remove_listener`
    сверяет объект функции. Контекст живёт дольше сокета, и оставленный обработчик копит
    задачи для давно закрытого окна при каждом всплывшем окне. Обработчики именуются, а
    пары «страница — обработчик» хранятся до `finally`.
26. **Флаг «уже вооружено» на `window`** — у всплывшего окна `window` переживает
    навигацию, а `document` нет. Скрипт считал окно вооружённым и выходил, тогда как
    слушатели остались на предыдущем документе (обычно `about:blank`, с которого
    начинается popup), и клики в дочерней вкладке не записывались вовсе. Флаг живёт
    на `document`.
27. **`float(message.get('x', 0))` на данных клиента** — умолчание применяется к
    отсутствующему ключу, а не к присланному `null`. А `null` приходит буднично:
    клиент делит координату на размер картинки, и пока кадра нет, деление на ноль
    даёт `NaN`, который `JSON.stringify` превращает в `null`.
28. **Вооружать только `entry['page']`** — это первая страница сессии, а не та, что
    перед глазами. Инспектор и запись обязаны обойти `context.pages` целиком и
    подписаться на новые окна: всплывшее окно человек воспринимает как ту же сессию.
29. **`send_json` из двух мест сразу** — кадры идут из своей задачи, список вкладок из
    обработчика событий контекста, и без общего замка два вызова успевают перемешать
    байты одного кадра. Все отправки идут через один `emit()` под `asyncio.Lock`.
