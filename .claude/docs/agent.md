# Agent — агенты и их заведение

> Две дороги заведения: обычная — запись в `agent` по номерам узла и workflow;
> и «workflow заводит сам» — когда у workflow есть шаг с инструментом
> `agent_create_or_update`, агента создаёт прогон через `POST /chat/ask`, а
> не прямая вставка. Плюс список с видимость по ролям и точечный поиск по имени

`agent` — записи «кто отвечает»: связка `name` (системное имя, глобально
уникальное — это же `document_id` в Qdrant и заголовок фактов), `title`
(отображаемое), `node_id` (узел LLM, см. node.md), `workflow_id`
(сценарий, см. workflow.md), `llm_id` (модель по умолчанию, см. llm.md),
`prompt_system`, `greeting`,
`workflow_variable`, `agent_variable` (§6). Привязка «агент ↔ роль» — таблица
`agent_role`, меняется полем `role_ids` в `POST`/`PUT /agent`; через неё
не-админы видят подмножество агентов и сессий (session.md).
> для внешних сервисов (DatingAi).

## 1. Роуты

Роутер подключён в `main_uvicorn.py` без префикса. Контракт `{result}` —
`docs-common/api_rules.md`. Часть точек скрыта из схемы (`include_in_schema=False`)
— они для внутренней админки, не для публичной OpenAPI.

| Метод | Путь | Право | Что делает |
|-------|------|-------|-----------|
| GET | `/agent/list` | `AGENT_VIEW` | Список; `find_by` — телом, query-параметром или `user_id`; не-полноправная роль — свои агенты |
| POST | `/agent/list` | любой залогиненный | Агенты владельца токена, `find_by` — тело |
| POST | `/agent/create` | `AGENT_CREATE` | Создание **по именам** узла и workflow (`node`, `name`, `workflow`, `site`, `group_name`, `variables`, `agent_variable`); `201` |
| GET | `/agent/name/{name}` | `AGENT_VIEW` | Агент по системному имени; нет — `404` |
| GET | `/agent/{agent_id}` | `AGENT_VIEW` | Агент целиком + `role_ids` |
| GET | `/agent/{agent_id}/prompt_system/{collection_name}` | `AGENT_VIEW` | Собранная системная инструкция: `%переменные%` уже раскрыты (§6) |
| POST | `/agent` | `AGENT_CREATE` | Создание **по номерам** (`node_id`, `workflow_id`, `role_ids`, …) |
| PUT | `/agent/{agent_id}` | `AGENT_UPDATE` | Частичное обновление; `role_ids` — полная замена |
| GET | `/agent/{agent_id}/user/{user_id}/session_last_entry` | `AGENT_VIEW`+`SESSION_VIEW` | Последний `session_uuid` пары агент/пользователь |
| DELETE | `/agent/{agent_id}` | `AGENT_DELETE` | Удаление агента |

## 2. Заведение по именам vs по номерам

`POST /agent/create` — для внешних клиентов: он не знает номеров `node`/
`agent_workflow` (они разные на стенде и на проде), а имена одинаковы и видны
в админке. Узел и workflow ищутся по имени; неизвестное имя — `422` с
перечнем известных. `POST /agent` — внутренняя точка для админки: номера
приходят готовые, плюс `role_ids` и `workflow_variable`.

Уникальность `name` проверяется в обеих: занятое имя — `409`. `name` —
системный идентификатор (Qdrant `document_id`, заголовок фактов), поэтому
глобально уникальный; отображаемое имя — `title`.

`/agent/create` требует ещё `site` — сайт-владелец агента, только строчная
латиница и цифры (`^[a-z0-9]+$`, `agent.site`): поле проверяется схемой,
несовпадение — `422`. `group_name` — факультативная папка группировки в меню;
не передан — без группы. На workflow-дорожке (`§3`) их дописывает сама точка
после прогона: у `agent_create_or_update` таких полей нет.

## 3. «Workflow заводит сам»

Перед вставкой `agent_create_by_name` смотрит, есть ли у workflow шаг с
инструментом `agent_create_or_update` (`_workflow_creates_agent`, по `metadata`
шага). Если да — не дублирует запись, а гоняет прогон:

- создаёт временного исполнителя `<workflow>_runner` (агент, который умеет
  гонять этот workflow — его и создаст прогон);
- кладёт `agent_name` в переменные — чтобы workflow задал имя именно то,
  что просил вызывающий;
- шлёт `POST /chat/ask` с `question` = `title`/`name`;
- после прогона находит агента по `name` и отдаёт его `id`.

Обязательные `input`-переменные workflow проверяются **здесь** (422 с
перечнем), а не выше: они нужны работе workflow, у обычного агента те же
переменные задаются в `workflow_variable` и требуются в первом разговоре.

## 4. Self-вызов через `127.0.0.1`

`AGENT_CREATE_CHAT_URL` по умолчанию `http://127.0.0.1:8000/chat/ask` — свой же
процесс, а не имя контейнера. Имя контейнера здесь ловушка: Blue-Green
переключает активный слот между `uvicorn` и `uvicorn_green` (deploy.md), а
умолчание указывало на `uvicorn` — на проде с активным green заведение падало
«Temporary failure in name resolution». Настройка `UVICORN_URL` оставляет
запасной путь увести вызов на другой адрес. Таймауты: `AGENT_CREATE_TIMEOUT`
300 с (прогон с LLM идёт минуты), `AGENT_CREATE_CHAT_TIMEOUT` 240 с (умолчание
`/chat/ask` 60 с на создание не укладывается).

## 5. Видимость списка

`GET /agent/list`: неполноправная роль видит только агентов, чей `node_id` в
нодах пользователя (`user_node`) и у которых в `agent_role` есть роль
пользователя. Полноправная роль без `user_id` — всех; с `user_id` — превью
«как видит этот пользователь». `POST /agent/list` всегда от владельца токена.

## 6. Переменные агента — шаблон промпта вместо сотни записей

`agent.agent_variable` — JSON-словарь `{"girl_name": "Natalia"}`. Его значения
подставляются в `%плейсхолдеры%` **системного промпта и приветствия** перед
отправкой в модель.

**Зачем.** Агенты одного вида отличаются не логикой, а одним словом внутри
промпта. Живой пример — знакомства: `dating_talk` один на всех, текст промпта у
всех анкет совпадает до буквы, и разнится ровно имя — «You are a girl Diana»
против «You are a girl Renata». Пока промпт был мёртвым текстом, каждое такое
отличие стоило отдельной записи: сотня анкет — сотня копий одного текста, правка
формулировки — сотня правок, а заведение анкеты — прогон workflow с LLM ради
копии. С шаблоном запись одна, а различие — значение переменной.

### Две колонки, два смысла

| Колонка | Владелец | Куда попадает | Кто читает |
|---------|----------|---------------|-----------|
| `workflow_variable` | вход workflow | scope прогона | движок шагов; **только `/chat/ask`** |
| `agent_variable` | чем агент отличается от соседа | scope прогона **и** промпт с приветствием | движок шагов и рендер промпта; **все точки входа** |

Разница в последней колонке не косметическая. `workflow_variable` подмешивает
только `chat.py`; телеграм-бот, cron-задачи и роли конвейера зовут движок
напрямую и этой колонки не видят. `agent_variable` живёт в
`ai_workflow_variables_base()` — единственном сборщике базовых переменных, общем
для всех точек входа, — и поэтому доезжает отовсюду.

### Приоритет значений

```
переменные агента  →  базовые (prompt_user, agent_*, …)  →  workflow_variable  →  variables запроса  →  переменные ноды
```

Слева умолчания, справа — то, что перекрывает. Практический вывод: значение из
записи агента — умолчание, а конкретный разговор шлёт своё в `variables` запроса
`POST /chat/ask`. Базовые имена (`agent_title`, `prompt_user`, `session_uuid`)
переменная агента **не** подменяет — они одинаковы во всех workflow, и шаги на
них рассчитывают.

### Универсальный агент DatingAi

`dating_girl_universal` (title «Девушка») — та самая запись, ради которой
колонка заведена (миграция `20260911180558`). В её промпте `%girl_name%`, а
текст взят из переменной узла `girl_prompt_system` — того же шаблона, по
которому `dating_girl_create` лепит промпт каждой анкете.

```json
POST /chat/ask
{"agent_id": <id>, "question": "hi",
 "variables": {"girl_id": "natalia_1430119", "girl_name": "Natalia"}}
```

`girl_name` уходит в промпт, `girl_id` — в фильтры фактов Qdrant (шаг
«Переменные» workflow `dating_talk`). Оба обязательны: без `girl_id` в контекст
приедут чужие факты, без `girl_name` собеседница представится умолчанием записи.

Старые агенты анкет работают как работали — их промпт не шаблон, а готовый
текст, и рендер в нём ничего не находит.

### Где править

- **Админка** — `/admin/agent`, блок «Переменные агента» над блоком переменных
  workflow.
- **API** — `agent_variable` в `POST /agent`, `PUT /agent/{id}` (частичное: не
  прислали поле — значение остаётся) и `POST /agent/create`.
- **Из workflow** — аргумент `agent_variable` инструмента `agent_create_or_update`.

## 7. Что здесь не делать

- Не дублировать создание агента в `agent_create_or_update` прямой вставкой —
  workflow, который умеет заводить агента сам, заводит сам; вторая дорога
  разошлась бы.
- Не хранить ссылку на агента по `id` в внешних сервисах — DatingAi ищет по
  имени, потому что агента могли удалить или переименовать, и хранимый номер
  соврал бы.
- Не полагаться на `workflow_variable` как обязательную — в создании по именам
  она ставится `None`. `site` с `group_name` приходят параметрами: `site` обязателен,
  `group_name` без передачи остаётся `None`.

## Грабли

1. **Self-вызов через имя контейнера падает на green.** Замена
   `127.0.0.1` на имя контейнера ломает заведение агента, когда активен
   другой слот. **Симптом** — `502` / «Temporary failure in name resolution»
   при `POST /agent/create` только в одном из слотов Blue-Green.
2. **`422` при создании — это не «плохой запрос», а список полей.**
   `variables` не заполнил — `422` перечисляет недостающие `input`-переменные
   workflow; узел/workflow не нашли — `422` с известными именами. Читать
   `detail` как подсказку, а не гадать.
3. **`201` на повторный запрос к «workflow-заводящему».** Имя-то свободно —
   заняло другое (workflow задал `agent_name` из запроса). Повторный вызов
   с тем же `name` снова создаст запись, если предыдущая под другим именем.
   Проверять наличие агента по `name` перед повтором.
4. **Пустой список у не-админа — не баг точки, а отсутствие `agent_role`.**
   Агент без строки в `agent_role` для его роли невидим. **Симптом** —
   «агента есть, в списке нет» у служебной учётки: назначьте агенту роль
   через `POST/PUT /agent` с `role_ids`.
5. **`GET /agent/{id}` для не-существующего отдаёт `{"result": null}`**, а не
   `404` (в отличие от `/agent/name/{name}`). Клиенту проверять `null`.
6. **Переменные ноды перекрывают переменные агента — и это ловушка имён.**
   Они применяются последними (`update`, а не `setdefault`). У узла Dating есть
   `girl_title` типа `proxy` со значением `%prompt_user%`: назови переменную
   агента `girl_title` — и имя собеседницы в промпте подменится текстом
   входящего сообщения. **Симптом** — «You are a girl привет, как дела».
   Поэтому универсальный агент зовёт свою переменную `girl_name`.
7. **Нераскрытый `%плейсхолдер%` в ответе модели — не сбой рендера, а пустая
   переменная.** Рендер подставляет только известные имена и молчит о
   неизвестных. Битый JSON в колонке даёт тот же симптом: разбор не роняет
   запрос, а пишет в журнал «`agent_variable` агента … не разобран как JSON».
   Проверить собранный текст — `GET /agent/{id}/prompt_system/{collection}`.
