# Тесты: группы по подсистемам

> Прогоняй то, что задето правкой, а не всё подряд. Полная сюита идёт больше трёх
> минут, и роль конвейера платит это время на каждом круге — даже поправив одну
> строку в чужом углу проекта.

## Группы и что в них

Семь групп по подсистемам плюс два признака стоимости. Объявлены в `pyproject.toml`,
раздел `[tool.pytest.ini_options]`, ключ `markers`.

| Группа | Что покрывает | Тестов | Время |
|---|---|---|---|
| `pipeline` | конвейер задач: состояния, отбор работы, роли, worktree, метрики, вопросы | 532 | ~69 с |
| `ai` | движок LLM: провайдеры, workflow, агенты, инструменты, факты, коллекции | 230 | ~55 с |
| `team` | команда и оболочки: карточки, пулы моделей, сессии, heartbeat | 177 | ~54 с |
| `core` | общее: настройки, cronjob, журналы событий, ошибок и запросов к базе, планирование | 250 | ~39 с |
| `browser` | контейнер-браузер: сайты, сценарии, переменные, ошибки | 81 | ~65 с |
| `auth` | доступ: вход, права, роли, пользователи, сессии, кабинет | 79 | ~56 с |
| `telegram` | мини-приложение и чат-компаньон | 47 | ~34 с |

Всего 1419 тестов, полный прогон — **без малого четыре минуты**.

⚠ Счёт `telegram` и `team` просел не от удаления: 84 теста с живым Chromium
уехали в `tests_browser/` (см. ниже). Считать их здесь значило бы обещать
покрытие, которого обычный прогон не даёт.

⚠⚠ **Группа `browser` — не про живой браузер.** Она про ручки контейнера: сайты,
сценарии, переменные, ошибки — обычные проверки кода. Chromium поднимают тесты в
`tests_browser/`, и их в группах нет вовсе.

Два признака поперёк групп, ими помечены отдельные тесты, а не файлы:

| Признак | Что значит |
|---|---|
| `integration` | нужен поднятый сервер на `BASE_URL` и живая БД |
| `slow` | живой браузер (playwright) — **только в `tests_browser/`**, вне `testpaths` |

## Как запускать

```bash
.venv/bin/python3 -m pytest -m pipeline -q          # одна группа
.venv/bin/python3 -m pytest -m "pipeline or team" -q  # две сразу
.venv/bin/python3 -m pytest -m "team and not slow" -q # без браузерных: 13 с против 38
.venv/bin/python3 -m pytest tests/test_task_log.py -q # один файл
.venv/bin/python3 -m pytest tests/ -q                 # всё, ~3.5 минуты
```

Против сервера ветки — тем же способом, адрес из переменной окружения:

```bash
./task_server.sh up <задача>
BASE_URL=http://localhost:8013 .venv/bin/python3 -m pytest -m pipeline -q
```

**Сюжеты, ходящие по HTTP, гонятся только так.** Общий `:8011` поднимает `master`, а не
правки из выкладки, и тест без `BASE_URL` проверяет чужой код: проходит молча, когда
ветка сломана, и падает, когда сломан чужой `master`. Подстановка по умолчанию сама
тыкается в `:8011` (`tests/test_task_qa_mode.py`, `tests/test_task_metadata.py`),
поэтому пропущенная переменная — не ошибка, а тихая проверка не того, что писал.

**Здесь это правило (`docs-common/testing_rules.md`, раздел 5, пункт 5) выглядит так:**
база стенда общая, сессионная уборка `cleanup_test_tasks` (`tests/conftest.py`) сносит
задачи **и проекты** сюиты по маске заголовка `__pytest%` до прогона и после; маска
закрывает собой все префиксы файлов сюиты, включая `__pytest_qa_mode__`. Проверить, что
стенд свободен: `pgrep -af "pytest tests/"`.

⚠⚠ **Проект сносится последним, после своих задач и фаз планирования.** Внешнего ключа
к `project` у них нет (единственный — `project_team`, и тот с каскадом), поэтому
удалённый первым проект не уносит их за собой, а обращает в сирот: `project_id`
указывает в пустоту, а своего признака в строке нет — тестовые задачи зовутся «родитель»
и «первая». Так на рабочей базе скопились 21 задача и 30 фаз при том, что фикстуры
тестов за собой убирали. Сироты и сейчас находятся только по разрыву связи — правило в
`test_cleanup.py`, единственное там без опоры на приставку.

Пробел: зависимость от свободного стенда из сюиты не выведена — чинится со стороны
уборки (маска заголовка на файл, повтор попытки на `404`), а не правкой отдельного
теста. Зелёный прогон без `pgrep` ничего не значит.

## Как выбрать группу под свою правку

**По тому, что тронул, а не по тому, что назвал.** Правил `src/project/task/` —
`pipeline`. Трогал `src/project/team/` или `/admin/team` — `team`. Менял промпты
шагов workflow миграцией — `ai` плюс `pipeline`, если правил роли конвейера.

Три случая, когда группы мало:

- **правка в общем месте** — `py_modules/`, `src/uvicorn/routers/`, `conftest.py`,
  схема БД: задето может быть что угодно, гони всё;
- **не уверен, какую задел** — гони всё. Три минуты дешевле сорванной приёмки;
- **перед merge request** — полная сюита обязательна, как бы мала ни была правка.
  Группа экономит время внутри круга, а не заменяет проверку на выходе.

## Как делить новые тесты

Группа ставится **файлу целиком**, строкой под докстрингом:

```python
"""
Что проверяется и зачем.
"""
import pytest

pytestmark = pytest.mark.pipeline
```

Уже есть `pytestmark` — дополняй списком: `pytestmark = [pytest.mark.pipeline,
pytest.mark.integration]`.

**Файл принадлежит ровно одной группе.** Тест, покрывающий стык двух подсистем, идёт
в ту, чей контракт он стережёт: `test_team_llm_ping.py` проверяет, что мёртвая модель
не получает кругов, — это про команду и её пул, а не про конвейер, хотя круги раздаёт
он.

Тесты фронтенда (`test_workflow_undefined_index.py`, `test_workflow_undefined_vars.py`,
`test_workflow_graph_vars_list.py`, `test_workflow_trace_var_chips.py`,
`test_workflow_text_translate.py`) стоят в группе
`core` и проверяют **настоящие** `.js`-модули `data/uvicorn/public/js/workflow/`: харнесс
вписывает пути модулей токенами в скрипт и гоняет его на `node`, заглушки у харнесса —
только DOM и сеть. Правку модуля такой тест ловит сразу; свою копию модуля в тесте не
писать — тест без настоящего файла проверяет пустоту.

Новый файл без маркера попадёт в «ничьи» и не запустится ни в одной группе — молча,
без единой жалобы. Проверить, что таких нет:

```bash
.venv/bin/python3 -m pytest -q --collect-only \
  -m "not pipeline and not team and not browser and not ai and not auth and not core and not telegram"
```

Ответ `no tests collected` — все размечены. ⚠ Проверка смотрит только `tests/`:
`tests_browser/` вне `testpaths`, а `tests_llm/` делится не группами, а метками
`llm` / `llm_live` и папками по workflow ноды Testing.

## Тест убирает за собой то, что завёл снаружи

Строки в базе сносит фикстура-уборщик, и про них помнят. Забывают про **чужие
хранилища** — те, что переживают конец теста сами по себе.

### ⚠⚠ Но больше половины мусора заводит не тест, а код под тестом

Уборщики по имени (`test_` у пользователя, `test_agent_` у агента, список ролей)
снимают то, что завёл сам тест и знает, как назвал. А один вызов `/chat/ask`
оставляет после себя сессию агента, след прогона workflow с деревом шагов, строки
запросов к модели и факты, которые агент сочинил сам. Имён у них нет, и номеров их
тест не видел: он их не заводил.

Замер после трёх дней прогонов — **172 тысячи строк**:

| таблица | строк |
|---|---|
| `agent_session` | 82 948 |
| `agent_workflow_trace_step` | 76 744 (каскадом за следом) |
| `agent_workflow_trace` | 9 943 |
| `llm_request` | 2 243 |
| `fact` | 92 |

Общее у них одно — **хозяин**: всё заведено под тестовой учёткой. Она отдельная и
неадминская ровно затем, чтобы по строке было видно, кто действовал
(`testing_rules.md`, §3), и этого признака хватает. Снимает их
`cleanup_test_rows` в `tests/conftest.py` — до прогона и после.

⚠ Список таблиц **белый, а не чёрный**. У тестовой учётки есть строки, которые
мусором не являются: токен доступа, узлы, настройки, проекты. Снеси их за
компанию — следующий прогон не войдёт.

⚠ Номер учётки ищется **по имени входа**: автономер у каждой инсталляции свой, и
зашитое число молча не нашло бы ничего.

⚠⚠ **У факта две половины, и вторая — вектор в Qdrant.** `DELETE` из MySQL его не
трогает (это известные грабли, `fact.md`), поэтому точки снимаются **до** удаления
строк: точка адресуется номером строки — `uuid5(NAMESPACE_DNS, 'fact_id_<id>')`, —
и после `DELETE` этих номеров уже не узнать.

⚠⚠⚠ Клиент Qdrant для уборки заводится **свой**, а не через
`_qdrant_db_get_client()`: тот зашивает `host="qdrant", port=6333` — имя сервиса
внутри compose-сети, — и с хоста, где идёт сюита, не разрешается вовсе. Первая
версия уборки звала его и молча падала в `except`: строки исчезали, а 92 точки
оставались при 55 живых фактах. Ровно тот же разрыв «хост против сети compose»,
что и у `MYSQL_TEST_HOST`, и лечится так же — наружу Qdrant опубликован портом
6335. Поэтому же в отчёте уборки счёт точек печатается **всегда, когда были
факты**, даже нулевой: «qdrant: 0» при непустом `fact` — это и есть примета
молчаливого отказа.

Посмотреть, что оставил упавший прогон: `KEEP_TEST_DATA=1` снимает уборку целиком —
и ту, что до прогона, тоже.

Живьём: `test_browser_site_open.py` жмёт «Открыть» на карточке сайта, и страница
заводит настоящую сессию в контейнере-браузере. `browser.close()` в фикстуре гасит
playwright-браузер самого теста, а сессия в контейнере остаётся. Три теста за прогон —
три забытых страницы; за утро набежало девять из двадцати пяти мест пула, и все
мёртвые (`chrome-error://chromewebdata/`). Пул общий: переполни его — и работать
перестанет уже не тест, а человек в админке.

Правило: **завёл снаружи — погаси в `finally`**. Своё от чужого отличают разницей «до
и после», а не именем: идентификатор придумывает контейнер, а рядом живут сессии,
открытые человеком, — их трогать нельзя.

```python
before = _session_ids()
try:
    yield page
finally:
    browser.close()
_sessions_drop(_session_ids() - before)
```

Проверять уборку надо снятием: сними её — счётчик обязан вырасти (9 → 12), верни —
остаться на месте (9 → 9). Тест, который «убирает» несуществующее, зелёный всегда.

**Фикстура не покрывает прерванный прогон.** Убитый pytest (Ctrl-C, SIGKILL) хвост не
выполняет — проверено, сессия пережила SIGINT. У контейнера-браузера TTL нет вовсе:
страница живёт до явного DELETE или до его перезапуска. Поэтому вторая линия —
`cleanup_browser_sessions` в **`tests_browser/conftest.py`**: подметает до и после
прогона своей папки.

⚠ Фикстура уехала туда вместе с браузерными тестами. В общем `tests/conftest.py`
она ходила к контейнеру на каждом прогоне сюиты впустую — а после появления
сторожа сети ещё и мимо него.

Подметает она **только мёртвые страницы своего сайта** (`chrome-error://` и имя из
`BROWSER_TEST_SITE_NAME`). Живую не трогает никогда: рядом работает человек, у него
может быть открыта авторизованная страница под сценарий.

## Живой браузер — отдельной папкой, вне автоматического прогона

Тесты, поднимающие Chromium, живут в `tests_browser/`, и **в `testpaths` их
нет**: сами они не запускаются.

⚠⚠ Три причины, и все про плавучесть, а не про скорость: контейнер-браузер ходит
наружу **сам** (сторож сети его не видит — запрос делает чужой процесс), пул
вкладок общий с человеком и мал, а «обновилось без перезагрузки» — утверждение
про время. Плавающий тест в общем прогоне приучает не смотреть на красное.

⚠ **Правишь разметку, скрипты страниц или мини-приложение — предложи прогон и
дождись ответа.** Правила целиком — `testing_browser.md`.

```bash
.venv/bin/python3 -m pytest tests_browser -q      # руками, по решению человека
```

## Живые вызовы модели — отдельной папкой, но не отдельной жизнью

Сюита выше модель **не зовёт**: LLM для проверки кода не нужна, а лишний прогон
workflow стоил бы минуту и токены. Но ход разговора без неё не проверить — развилка
«о чём сейчас речь» это шаг `llm_to_json`, и решает его только сама модель.

Такие тесты живут в `tests_llm/` и гоняют **свои** маленькие workflow ноды
`Testing` — по одному на фичу движка. **52 теста, 38 секунд.**

⚠⚠⚠ **Боевые сценарии (`dating_talk` и прочие) не проверяются ни одним
тестом**, и это решение. Прежде проверяли: 161 тест на пяти боевых workflow
ноды Dating. Но правки в workflow вносит человек **на проде** — оттуда их
экспортируют и импортируют локально, а не наоборот; значит каждое
переименование шага или правка промпта роняли сюиту, сообщая о правке, к
предмету теста отношения не имеющей.

Нужна проверка — **заведи для неё свой workflow в ноде Testing**, два-четыре
шага. Девять таких уже есть: развилка, раскладка ответа, метки промпта, вызов
инструмента, карты подпотока, цикл, переписывание с потолком, тема по меткам,
факты. Состав и доводы — `testing_llm.md`.

⚠⚠ Что живой модели в прогоне нет — держится **нодой**, а не обещанием: у
`Testing` единственная модель `fake/echo`, и реестр провайдеров находит её по
префиксу имени. Забыть «включить подмену» нельзя — включать нечего.

⚠ Короткое время это делал глобальный `LLM_FAKE`; он снят вместе с переездом
тестов. Пока он лежал неподключённым, все `tests_llm` молча ходили к живой
`gx10/qwen-small`, и прогон шёл 79 минут вместо шести.

⚠⚠ **`llm_live` — носителей нет.** Метка и её исключение в `addopts` оставлены:
заведёт человек живой тест — он опять не пойдёт сам.

⚠⚠⚠ Главное правило: **ответ модели не угадывают, а задают**. Тест «спросили
про фото — жди `topic == photo_mail`» держится на том, что модель решит как
вчера. Задай ответ умолчанием подмены — и та же строка проверяет раскладку
по-настоящему.

⚠ **Текст ответа не проверяется ничем и никогда** — только трасса:
`prompt_of(шаг)`, `output_of(шаг)`, `ran(шаг)`. Это под сторожем
(`tests/test_llm_tests_guarded.py`).

⚠ **Раскладка: папка на workflow, названная его системным именем** —
`tests_llm/testing_branch/`. Приметы шагов живут в `conftest.py` этой папки,
общая оснастка — в корневом.

```bash
.venv/bin/python3 -m pytest -q                  # сюита + тесты фич движка
.venv/bin/python3 -m pytest tests_llm -q        # только фичи движка, 38 секунд
.venv/bin/python3 -m pytest tests_llm/testing_branch -q   # одна фича
```

⚠⚠ **Утверждения там берутся только из трассы прогона** — маршрут, шаги, промпт
после подстановки. Текст ответа модели не проверяется никогда: она каждый раз
отвечает иначе, и такой тест приучает не смотреть на красное.

Подробности и само правило — `.claude/docs/testing_llm.md`.

## Чего группы не делают

**Не заменяют полную сюиту перед сдачей работы.** Деление помогает внутри круга, где
правка узкая и проверять её надо часто. Связи между подсистемами оно не видит: правка
в `task_state.py` может сломать `team`, и узнать об этом на приёмке дороже, чем
прогнать всё самому.

**Не ускоряют то, что медленно по природе.** Браузерные тесты (`slow`) поднимают живой
Chromium: 21 тест на всю сюиту, 48 секунд вместе. Их стоит гонять, когда трогал
страницу, и пропускать, когда правил модуль.

В группе `browser` их всего три (`test_browser_site_open`), но берут они 20 секунд из
28 — остальные 54 теста идут по API и укладываются в 9:

```bash
.venv/bin/python3 -m pytest -m "browser and not slow" -q   # 54 теста, ~9 с
.venv/bin/python3 -m pytest -m browser -q                  # 57 тестов, ~28 с
```

Самый долгий во всей сюите — не браузерный из `browser`, а
`test_progress_column_refreshes_without_reload` (15 с): он ждёт живого автообновления
колонки, и быстрее не станет.
