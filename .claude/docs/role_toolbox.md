# Инструменты роли — чем работать в этом проекте

> **Читают все роли конвейера.** Здесь только то, что нужно, чтобы не искать:
> команды, которые работают, и запреты, о которые не надо биться.
>
> Что делает именно твоя роль и чего не делает — в своём файле:
> `role_developer.md`, `role_qa.md`, `role_bugfixer.md`, `role_manager.md`.
>
> Устройство конвейера — `project_task.md`, шаги ролей — `project_task_roles.md`.

## Главное за десять секунд

| Что делаешь | Чем |
|---|---|
| Прогнать тесты | `.venv/bin/python3 -m pytest tests/ -q` |
| Один файл тестов | `.venv/bin/python3 -m pytest tests/test_task_log.py -q` |
| Проверить синтаксис | `.venv/bin/python3 -c "import ast; ast.parse(open('файл').read())"` |
| Поднять сервер задачи | `./task_server.sh up` (порт 8013) |
| Тесты против него | `BASE_URL=http://localhost:8013 .venv/bin/python3 -m pytest tests/ -q` |
| Запрос к приложению | `curl -s http://localhost:8011/...` |
| Посмотреть базу | `docker exec rhapsodyai-mysql-1 mysql -uroot -ppassword --default-character-set=utf8mb4 -e "SQL"` |

**Голый `python3` запрещён.** `python3 …`, `python …` и `sudo …` отклоняются
всегда — не пробуй их и не ищи обходов. Работает `.venv/bin/python3`: это то же
самое окружение, только полным путём, и в нём уже стоят `pytest`, `httpx`,
`playwright`. В твоей выкладке `.venv` — ссылка на общий, отдельно ставить нечего.

## Тесты

Сьюта интеграционная: тесты ходят по HTTP в **запущенный** сервер, а не поднимают
своё приложение. Поэтому сервер должен работать, иначе всё падает на подключении.

```bash
.venv/bin/python3 -m pytest tests/ -q                    # весь набор
.venv/bin/python3 -m pytest tests/test_task_log.py -q    # один файл
.venv/bin/python3 -m pytest tests/ -q -k "metric"        # по имени
```

Адрес сервера — в `BASE_URL`, по умолчанию `http://localhost:8011` (общий стенд).
Свой сервер задачи поднимается на `:8013`:

```bash
./task_server.sh up
BASE_URL=http://localhost:8013 .venv/bin/python3 -m pytest tests/ -q
./task_server.sh down
```

**Чего не делать.** Не гоняй весь набор ради двух своих тестов: там есть тики
конвейера, и они мешают живым кругам соседних подзадач. Гоняй свои файлы, полный
набор — забота QA после тебя.

## Где можно писать, а где нет

Пиши **только в своей выкладке** — каталоге, в котором тебя запустили
(`.claude/worktrees/feature_task_<номер>/`). Там у тебя своя ветка и полные права.

Запись в чекаут человека закрыта: `src/`, `tests/`, `data/`, `py_modules/`,
`migrations/`, `docker/`, `docker-compose*.yml`, `main_*.py`, `.env*` в корне
проекта. Получил отказ на запись — посмотри путь: скорее всего ты вышел за
пределы своей выкладки. Это не препятствие для работы, а страховка от того, чтобы
править чужой рабочий каталог.

## После правок

```bash
docker restart uvicorn      # .py-файлы приложение подхватывает только при рестарте
```

Шаблоны (`data/uvicorn/template/**`) перечитываются сами, рестарт им не нужен.

## Изменения в базе

**SQL кладёшь файлом, но не применяешь.** База одна на весь стенд: твой `UPDATE`
немедленно видят соседние подзадачи и живой конвейер, а откатить его, в отличие от
ветки, нельзя.

Файл — `migrations/<метка времени>_<что делаешь>.sql`, где метка — текущее время
целиком, `YYYYMMDDHHMMSS`. Бери её командой, а не сочиняй:

```
date +%Y%m%d%H%M%S      # 20260831150137
```

Секунды нужны. В проекте почти все метки «круглые» (`...150000`), потому что их
писали руками, — и две работы, начатые в один час, берут один номер. Живьём так и
вышло: подзадача #5219 собиралась завести `20260831150000_wf57_qa_mode.sql`, а такой
номер уже был занят соседней правкой. Два файла на одну метку yoyo применит в
неопределённом порядке, а при слиянии веток это конфликт.

Применит файл yoyo при старте приложения,
уже после слияния ветки. Ни `POST /tool/sync`, ни правку шагов workflow руками не
делай — спроси, если кажется, что без этого никак.

Подробности — `.claude/docs-common/database_rules.md`.

## Развилки

Уперся в решение, которое не твоё (менять ли контракт API, трогать ли чужую
подсистему, ломать ли обратную совместимость) — **задай вопрос полем `question` в
своём отчёте**, с двумя-тремя готовыми вариантами. Круг за это не тратится, работа
встаёт и ждёт человека.

Не додумывай за заказчика и не делай «на всякий случай» больше, чем в подзадаче.

## Журнал

В каталоге подзадачи лежат `.task-log.md` (что делали по кругам) и
`.task-state.md` (итог последнего круга). **Прочитай их прежде, чем лезть в
проект**: прошлый круг мог оборваться по таймауту, и работа уже сделана — в
журнале это видно, а в коде не всегда.

Писать в них не нужно, их ведёт конвейер сам.

## Общее правило

Делаешь свою подзадачу и только её. Заметил чужую проблему — назови её в отчёте,
но не чини: это чужая работа, и правка в твоей ветке сорвёт чужую приёмку.
