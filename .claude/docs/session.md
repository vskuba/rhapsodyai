# Session — чтение журнала диалогов `agent_session`

> Список сессий с фильтрами по агенту/пользователю/companion, последние
> сессии, диалог по `session_uuid` с лимитом по диалоговым сообщениям и
> удаление переписки. Не-админы видят только сессии своих агентов — фильтр
> строится по `agent_role` и имени роли.

`session` — только-чтение (и удаление) журнала диалогов. Все сообщения
агентов лежат в таблице `agent_session`: `session_uuid` связывает сообщения
одной переписки, `kind_type` помечает тип записи (`user-prompt`,
`response-final` — диалоговые; `llm-request` и прочие — служебные),
`agent_id`/`user_id`/`companion_id` — кто с кем (companion.md), `llm_id` —
какой LLM отвечал. Запись в журнал делает `/chat/ask` (chat.md); этот роутер
журнал только читает и удаляет.

## 1. Роуты

Роутер подключён в `main_uvicorn.py` без префикса. Контракт `{result}` —
`docs-common/api_rules.md`.

| Метод | Путь | Право | Что делает |
|-------|------|-------|-----------|
| POST | `/session/list` | `SESSION_VIEW` | Сессии по фильтрам `agent_id`/`user_id`/`companion_id`, по `last_message_at DESC` |
| GET | `/session/kind_type/list` | `SESSION_VIEW` | Отдельные `kind_type` в журнале |
| POST | `/session/last` | `SESSION_VIEW` | Та же выборка, что `list`, но одна — последняя |
| POST | `/session/last/uuid` | `SESSION_VIEW` | Только `session_uuid` последней сессии (или `null`) |
| POST | `/session/messages` | `SESSION_VIEW` | Сообщения сессии; лимит — по диалоговым, в ответе по хронологии |
| DELETE | `/session/{session_uuid}` | `SESSION_DELETE` | Удаляет все сообщения сессии; нет строк — `404` |

Тело `list`/`last`/`last/uuid`: `{"agent_id":…, "user_id":…, "companion_id":…}`
— все фильтры необязательны. Тело `messages`: `{"session_uuid": "…",
"limit": 25}`.

## 2. Видимость не-админов

Для неполноправной роли (проверка `auth_role_is_full`, см. auth.md) ко всем
выборкам добавляется условие `_agent_role_condition()`:
`agent_id IN (SELECT agent_id FROM agent_role JOIN role ON role.id = agent_role.role_id WHERE role.name = <роль пользователя>)`.
То есть не-админ видит сессии только тех агентов, которым назначена его роль
(привязка `agent_role` — agent.md). У агента без строки в `agent_role`
сессии для не-админа невидимы. Условие подставляется и в `DELETE` — чужую
переписку удалить нельзя.

## 3. Лимит `messages` считает диалоговые, а не все

`limit` (по умолчанию 25, диапазон 1–200) отсчитывается по сообщениям
`kind_type ∈ {user-prompt, response-final}`. Выборка идёт по `id DESC`:
служебные записи (`llm-request` и пр.) включаются, пока принадлежат уже
выбранным диалоговым; до N-го диалогового сообщения дошли — дальше обрыв.
Ответ разворачивается в хронологический порядок. Служебные записи дают
картинку «что шло в LLM» вокруг диалога, но не раздувают выдачу.

## 4. Что здесь не делать

- Не писать в `agent_session` отсюда — запись одна дорога: `/chat/ask`
  (chat.md). Две дороги к журналу разошлись бы на первой правке.
- Не полагаться на `role`/`kind_type` из `list` как на «последнее значение» —
  это агрегаты `MAX()` по группе (см. грабли).

## Грабли

1. **`role` и `kind_type` в `list`/`last` — не последние, а `MAX()`.**
   Группировка по `session_uuid` берёт `MAX(role)`, `MAX(kind_type)` —
   лексикографически максимум по строкам группы, не значение последнего
   сообщения. **Симптом** — «последнее сообщение — ответ, а в списке
   сессии `role` показывает что-то другое»; нельзя по этим полям
   реконструировать ход диалога.
2. **Сессия без диалоговых сообщений отдаётся целиком.** Лимит в `messages`
   срабатывает только когда счётчик диалоговых дошёл до `limit`; если в
   сессии только служебные записи, обрыва не происходит и возвращаются все
   строки. **Симптом** — «лимит 25, а пришло 400»: это сессия, где нет ни
   одного `user-prompt`/`response-final`.
3. **Переименование роли выключает видимость.** Фильтр сравнивает
   `role.name` с ролью пользователя строкой (см. role.md). Сменили имя
   роли — не-админы молча теряют доступ к сессиям, хотя `agent_role` не
   тронут. **Симптом** — пустой `/session/list` у пользователей с выданной
   ролью.
4. **`DELETE` отдаёт количество, не факт.** В ответе `rowcount`; ноль строк
   превращён в `404`, но при нахождении нескольких сообщений ответ — число
   удалённых, не `{deleted: true}`. Фронт не должен строить интерфейс на
   форме ответа «удалил/не удалил». **Симптом** — «кнопка удаления ломается
   на сессии с несколькими сообщениями», если клиент ждал булево.
