# User — пользователи, ноды и токены доступа

> Админский CRUD пользователей: список с ролями и нодами, создание с
> bcrypt-хешем, обновление, удаление; плюс выдача/отзыв токенов и
> self-профиль по API-ключу. Каждое действие — своё право `USER_*`.

`user` — учётные записи приложения: `username`, `email`, bcrypt-хеш пароля,
роль (`role_id` → `role`, см. role.md) и язык (из `setting` по `user_id`,
`node_id IS NULL`, `key = 'language'`). Привязка «пользователь ↔ нода» —
таблица `user_node` (через неё не-админ видит подмножество нод и агентов,
см. agent.md). Токены доступа — таблица `user_access_token`
(`user_id`, `token`): их принимает `AuthChecker` как альтернативу сессии
(X-API-KEY / Bearer, устройство в auth.md).

## 1. Роуты

Роутер подключён в `main_uvicorn.py` без префикса. Контракт `{result}` —
`docs-common/api_rules.md`.

| Метод | Путь | Право | Что делает |
|-------|------|-------|-----------|
| GET | `/user/list` | `USER_VIEW` | Пользователи с `role`, `language`, `node_ids`; только `dynamic = 0` |
| GET | `/user/{user_id}` | `USER_VIEW` | Один пользователь + его `node_ids` |
| POST | `/user` | `USER_CREATE` | Создаёт; `password` → bcrypt-хеш; `node_ids` → `user_node` |
| PUT | `/user/{user_id}` | `USER_UPDATE` | Частичное обновление; `password` минимум 8 символов; `node_ids` — полная замена |
| DELETE | `/user/{user_id}` | `USER_DELETE` | Удаляет пользователя |
| GET | `/role/list` | `USER_VIEW` | Дубликат точки role.md (см. там «дублирующийся `/role/list»`) |
| GET | `/user/{user_id}/token` | `USER_VIEW` | Токены пользователя |
| POST | `/user/{user_id}/token` | `USER_UPDATE` | Создаёт uuid-токен, возвращает `token` в ответе |
| DELETE | `/user/token/{token_id}` | `USER_DELETE` | Удаляет токен |
| GET | `/user` | любой залогиненный | Self-профиль: `id`, `username` текущего пользователя |

## 2. Пароль — только хеш, только через эти точки

`password` из тела никуда в открытом виде не пишется: на создании и на
обновлении сразу `bcrypt.hashpw` в `password_hash`. При обновлении пустой
пароль — «не меняем» (поле не попадает в `update_data`); на создании пароль
не обязателен. Минимум длины 8 проверяется только при обновлении.

## 3. `node_ids` — полная замена при PUT

`PUT /user/{id}` с полем `node_ids` сначала удаляет все строки `user_node`
пользователя, затем вставляет переданные. Пустой массив — «нод нет».
Поле не передано — привязки не трогает (в отличие от полной замены).
Сходно с заменой `role_ids` в agent.md и `node_ids` в role.md.

## 4. Self-профиль и токены

`GET /user` без прав отдаёт данные самого запросившего (`user.user_id`,
`username`) — это не дыра, а точка «кто я» для клиента по API-ключу.
`POST /user/{id}/token` возвращает токен в ответе один раз; в `user_access_token`
он хранится открыто (таблица служебная, выдача только под `USER_UPDATE`).

## 5. Что здесь не делать

- Не хранить пароль в открытом виде и не читать `password_hash` наружу —
  точки только пишут хеш, наружу его не выводят.
- Не давать не-админу чужие `user_node` — видимость нод строится на этой
  таблице (agent.md, session.md), лишние ноды = лишние агенты в списках.

## Грабли

1. **`dynamic = 1` не виден в `/user/list`.** Список фильтрует
   `WHERE u.dynamic = 0` — динамические (служебные, созданные не вручную)
   пользователи в админке не показываются, хотя `GET /user/{id}` их
   отдаст. **Симптом** — «пользователь в БД есть, в списке нет».
2. **Токен в `GET /user/{id}/token` открыт.** Точки выдачи и списка токенов
   показывают `token` в ответе; это служебные точки под `USER_*`, но лог
   запросов и ответы не должны уходить в публичные места. **Симптом** —
   токен в логах/отладочных дампах.
3. **Обновление без `node_ids` оставляет старые ноды.** Замена срабатывает
   только когда поле передано. Чтобы «снять» ноды — передать
   `"node_ids": []`, а не опустить поле. **Симптом** — «сбросил ноды, а они
   остались».
