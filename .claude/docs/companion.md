# Companion — справочник собеседников

> Справочник на два эндпоинта: список и get-or-create. Права — любой залогиненный
> пользователь. Записей немного, пагинации и правки нет — только создание и
> обновление заголовка.

`companion` — справочник «со стороны разговора»: с кем агент говорит. Таблица `companion`
хранит пары `name` (системное имя) и `title` (отображаемое). Собеседника в диалог
теперь кладёт сам вызывающий — троицей `companion_*` в `variables` (chat.md §3), и
справочник нужен, чтобы за этой троицей стояла честная запись: get-or-create до
вызова. Ключ разговора — `unique_id` записи; по нему `companion_session` и связывает
обмен с персоной.

## 1. Роуты

Роутер подключён в `main_uvicorn.py` без префикса — пути литеральные. Авторизация
— `AuthChecker([])`: любой залогиненный пользователь, отдельного права нет.

| Метод | Путь | Тело | Что делает |
|-------|------|------|-----------|
| GET | `/companion/list` | — | Все `companion` в порядке `id DESC` |
| POST | `/companion` | `{"name": "support", "title": "Поддержка"}` | Get-or-create по `name`; возвращает запись |

Ответы — контракт `{result}` из `docs-common/api_rules.md`; ошибки — `500` с текстом
исключения.

## 2. Get-or-create: `name` — ключ, `title` — обёртка

Повторный `POST /companion` с тем же именем не создаёт запись:

- имя сравнивается после `lower()` — `Support` и `support` это одна запись;
- `title` не передан — остаётся старое значение (при первом создании
  `title = name`);
- `title` передан и отличается от сохранённого — обновляется в БД;
- `title` передан и совпадает — запись не трогается.

Так `companion` заводят из кода (workflow, вызывающие сервисы): имя стабильное,
заголовок подставляют по необходимости, дублей не появляется.

## 3. Кто пишет сюда

Роутер только читает и создаёт записи; саму запись в диалог кладёт тот, кто зовёт
агента: троица `companion_*` в `variables` (chat.md §3), а `companion_session`
вяжет обмен с персоной по `unique_id` (см. session.md). Удаления записей через API
нет.

В промпт собеседник попадает только как переменные: движок их не подставляет —
кому нужны `companion_id` / `companion_name` / `companion_title`, тот объявляет
их входящими и ждёт полным списком от вызывающего (chat.md §3). Потому имя и
заголовок ищутся в реестре заранее: `POST /companion` (get-or-create) → троица
в `variables` → только потом `/chat/ask`.

## 4. Что здесь не делать

- Не держать в `companion` состояние разговора — состояние в `agent_session`,
  `companion` только «кто говорит».
- Не полагаться на порядок `id ASC` при выборе «первого собеседника» — выдача
  идёт `id DESC`, а выбор номера — дело вызывающего кода.

## Грабли

1. **Записи нет — троица в `variables` ссылается в пустоту.** Шаг «История»
   резолвит `unique_id` в номер строки `companion_session`; без записи резолв
   пустой и обмен в неё не ляжет. Сначала `POST /companion` (get-or-create),
   потом троица в `variables`. **Симптом** — список диалогов разваливается по
   «собеседнику»: чужая персона или её отсутствие в строке разговора.
2. **Заглавная буква в `name` дублирует запись в других местах.** API
   нормализует через `lower()`, но запись в `agent_session` или переменную
   workflow с тем же именем вручную может пойти в другом регистре. **Симптом** —
   два «одинаковых» собеседника в разных таблицах.
