# Реестр сессий Claude Code для Telegram Mini App

> Цель: в Mini App, на вкладке Cloud, видеть все активные терминальные сессии Claude Code
> (по одной иконке на сессию), заходить в чат конкретной сессии с полной историей, и управлять
> её жизненным циклом (регистрация при старте терминала, мягкое отключение через Telegram).
> Множественные сессии независимы друг от друга, могут относиться к одному или разным проектам,
> закреплены за ролью (пока только `developer`, дальше — `qa` и др., см. `workflow_dev_qa_agents.md`).

## 1. Что уже есть и переиспользуется

`ai_claude_session` (`migrations/0001.sql`) — это **очередь сообщений**, не реестр: каждая строка —
одно сообщение, ключуется по `session_uuid` (`content`/`response`/`handled`). Уже поддерживает
сколько угодно параллельных `session_uuid` — сейчас используется только один (статичный агент
"Claude", id 34 в `agent_workflow`/`agent`, `migrations/0005.sql`).

- `claude_message_user(prompt_user, session_uuid)` (`src/tool/claude_/claude_.py`) — кладёт
  сообщение пользователя в очередь.
- `claude_message_cloud(session_uuid, response, inbox_id)` — терминал пишет ответ обратно + дублирует
  в `agent_session`/Telegram.

**Вывод:** переписка уже мультисессионна по конструкции. Не хватает только слоя **реестра** —
кто сейчас активен, под какой ролью, под каким проектом — и UI поверх него.

## 2. Новая таблица — реестр (не путать с очередью выше)

Сознательно только **две** таблицы, без третьей "сессионных фактов" — краткое содержание пишется
прямо в реестр в момент закрытия сессии (см. §5), когда LLM и так активна для финальной уборки;
отдельный Workflow/fact-пайплайн для этого избыточен на первую версию.

Добавляется прямо в `migrations/0001.sql` (без сидовых данных, это чистая DDL-миграция):

```sql
CREATE TABLE ai_claude_session_registry (
  id INT AUTO_INCREMENT PRIMARY KEY,
  session_uuid CHAR(36) NOT NULL UNIQUE,   -- тот же uuid, что ключует ai_claude_session
  role VARCHAR(50) NOT NULL DEFAULT 'developer',
  project_label VARCHAR(255) NOT NULL,     -- basename cwd — папка, где запущен терминал
  status ENUM('active','closing','inactive') NOT NULL DEFAULT 'active',
  summary VARCHAR(500) NULL,               -- краткое содержание переписки, пишется при закрытии
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  last_seen_at DATETIME NULL,              -- heartbeat от /loop
  closed_at DATETIME NULL,
  INDEX idx_status (status),
  INDEX idx_project (project_label)
);
```

## 3. Регистрация/возобновление — хук `SessionStart`, не скилл

**Уточнение механики Claude Code (важно для реализации):** скилл — это промпт-инструкция, которую
выполняет агент через свои тулы, но её всегда нужно **вызвать вручную** (`/skill-name`, либо агент
сам решает её использовать). Для "при каждом старте терминала — автоматическая регистрация" это не
подходит — нужен **хук `SessionStart`**: харнесс сам, без чьего-либо решения, исполняет команду при
старте новой сессии Claude Code в директории проекта (получает `session_id`/`cwd` на stdin,
конфигурируется в `.claude/settings.json`, тип `command` или `http`).

**Разделение ответственности:** хук гарантированно (без чьего-либо решения) достаёт данные и
инжектит их в контекст новой сессии; сам интерактивный выбор — это уже работа агента (меня) через
`AskUserQuestion`, когда сессия уже стартовала с этим контекстом на руках.

Итоговая механика:

1. Хук `SessionStart` (shell-скрипт или прямой HTTP-вызов, `type: "http"`) при старте сессии
   запрашивает у API список registry-записей для текущего `project_label` (= basename cwd) —
   **все**, не только активные (нужны и закрытые — их тоже можно выбрать для продолжения).
   Каждая запись: `role`, `id`, `project_label`, `status`, `closed_at`, `summary`.
2. Хук возвращает этот список как дополнительный контекст в начало сессии, вместе с инструкцией:
   "покажи пользователю через AskUserQuestion выбор из этих сессий (роль/id/дата закрытия/summary)
   + опцию "создать новую"; при создании новой — уточни роль (пока только `developer`)".
3. Я (агент) в начале сессии вижу эту инструкцию и данные, показываю выбор пользователю.
   - **Выбрана существующая** — вызываю `POST /api/session/resume` с её `session_uuid`, подтягиваю
     историю из `ai_claude_session` (content/response пары) как контекст, `status='active'`.
   - **Создать новую** — уточняю роль, вызываю `POST /api/session/register` (uuid4, `role`,
     `project_label` = cwd), `status='active'`.
4. Сохраняю `session_uuid` локально в проекте (например `.claude/session_uuid` — не коммитить,
   добавить в `.gitignore`), чтобы `/loop`-промпт на каждой итерации знал, за какой registry-строкой
   ему обновлять heartbeat.

## 4. Heartbeat и обнаружение "пропажи" сессии

Прямого способа узнать, что терминал закрылся (крash, разрядился ноутбук, сеть) — не существует.
Единственный надёжный механизм — **staleness по heartbeat**:

- Каждое пробуждение `/loop` обновляет `ai_claude_session_registry.last_seen_at = NOW()` для своего
  `session_uuid` (одновременно с проверкой очереди сообщений — см. `workflow_dev_qa_agents.md` §7).
- API/Mini App считает сессию реально активной, если `last_seen_at` не старше ~2× интервала `/loop`.
  Если старше — статус в БД может всё ещё быть `active`, но UI показывает "отвалилась"
  (например, серая иконка вместо зелёной), не дожидаясь явного `closed_at`.

## 5. Мягкое отключение через Telegram (подтверждено пользователем)

Кнопка "Отключить разработчика" **не убивает процесс** — она выставляет `status='closing'` в
реестре. Дальше:

1. На ближайшем пробуждении `/loop` видит `status='closing'` для своего `session_uuid`.
2. Делает финальную уборку: краткое summary переписки (по последним ~10 сообщениям из
   `ai_claude_session`) пишется в `ai_claude_session_registry.summary` — для показа в пикере хука
   при следующем запуске (§3); при необходимости — отдельно факт в долгосрочную память
   (см. `workflow_dev_qa_agents.md` §6).
3. Проставляет `status='inactive'`, `closed_at=NOW()`.
4. **Не планирует следующее пробуждение** (`ScheduleWakeup` не вызывается) — `/loop` естественным
   образом останавливается. Сам терминал (окно) остаётся открытым — пользователь закроет его вручную,
   когда захочет.

**Подтверждено:** простаивающий терминал без запланированного `/loop`-пробуждения не делает никаких
запросов к модели и не тратит токены — это и есть весь смысл "мягкого стопа", а не имитация
буквального закрытия терминала.

Задержка между нажатием кнопки и фактической остановкой = один интервал `/loop` (ожидаемо, не баг).

## 6. Telegram Mini App — UI

- Вкладка Cloud: первая (верхняя) иконка — "назад", дальше — по одной иконке на каждую
  registry-запись со `status='active'` **и** свежим `last_seen_at` (см. §4).
- Иконка показывает роль + `project_label` (например "Developer — RhapsodyAi").
- Клик по иконке → чат, отфильтрованный по конкретному `session_uuid` — подтягивает историю из
  `ai_claude_session` (уже готовый механизм, просто параметризованный по uuid, а не хардкод одного).
- В чате — кнопка управления "Отключить [роль]" (см. §5).

## 7. API-эндпоинты (реализовано в `src/uvicorn/routers/telegram_app/telegram_app.py`)

| Эндпоинт | Кто вызывает | Действие |
|---|---|---|
| `GET /telegram-app/claude/sessions?project_label=...` | Хук `SessionStart` | Список всех registry-записей для проекта (любой статус) |
| `POST /telegram-app/claude/session/register` | Хук `SessionStart` | Создать новую запись (`role`, `project_label`) → `session_uuid` |
| `POST /telegram-app/claude/session/resume` | Хук `SessionStart` | `status='active'`, вернуть историю сообщений (`agent_session`) |
| `POST /telegram-app/claude/session/heartbeat` | `/loop` (каждая итерация) | Обновить `last_seen_at`, вернуть текущий `status` |
| `POST /telegram-app/claude/session/finalize` | `/loop` (увидев `status='closing'`) | Записать `summary`, `status='inactive'`, `closed_at` |
| `GET /telegram-app/claude/sessions/active` | Mini App | Активные сессии для иконок (heartbeat ≤ 30 мин) |
| `POST /telegram-app/claude/session/close-request` | Mini App (кнопка) | `status='closing'` |

Авторизация — тем же паттерном, что уже есть в файле: терминальные вызовы через
`_require_claude_secret` (заголовок `X-Claude-Secret`, секрет = `TELEGRAM_TOKEN_RHAPSODY`), вызовы
из Mini App — через `_require_telegram_owner` (сессия владельца).
