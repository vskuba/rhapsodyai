# Реестр сессий Claude Code для Telegram Mini App

> Цель: в Mini App, на вкладке Cloud, видеть все активные терминальные сессии Claude Code
> (по одной иконке на сессию), заходить в чат конкретной сессии с полной историей. Сессия
> видна ровно пока открыт терминал (staleness по heartbeat, см. §4/§5) — управлять паузой из
> Telegram не нужно.
> Множественные сессии независимы друг от друга, могут относиться к одному или разным проектам,
> закреплены за ролью (пока только `developer`, дальше — `qa` и др., см. `workflow_dev_qa_agents.md`).

## 1. Что уже есть и переиспользуется

`ai_claude_session` (`migrations/0001.sql`) — это **очередь сообщений**, не реестр: каждая строка —
одно сообщение, ключуется по `session_uuid` (`content`/`response`/`handled`). Уже поддерживает
сколько угодно параллельных `session_uuid` — сейчас используется только один (статичный агент
"Claude", id 34 в `agent_workflow`/`agent`, `migrations/0005.sql`).

- `claude_message_user(prompt_user, session_uuid)` (`src/tool/claude_/claude_.py`) — кладёт
  сообщение пользователя в очередь.
- `claude_message_cloud(session_uuid, response, inbox_id)` — терминал пишет ответ обратно + дублирует
  в `agent_session`/Telegram.

**Вывод:** переписка уже мультисессионна по конструкции. Не хватает только слоя **реестра** —
кто сейчас активен, под какой ролью, под каким проектом — и UI поверх него.

## 2. Новая таблица — реестр (не путать с очередью выше)

Сознательно только **две** таблицы, без третьей "сессионных фактов" — краткое содержание пишется
прямо в реестр в момент закрытия сессии (см. §5), когда LLM и так активна для финальной уборки;
отдельный Workflow/fact-пайплайн для этого избыточен на первую версию.

Добавляется прямо в `migrations/0001.sql` (без сидовых данных, это чистая DDL-миграция):

```sql
CREATE TABLE ai_claude_session_registry (
  id INT AUTO_INCREMENT PRIMARY KEY,
  session_uuid CHAR(36) NOT NULL UNIQUE,   -- тот же uuid, что ключует ai_claude_session
  role VARCHAR(50) NOT NULL DEFAULT 'developer',
  project_label VARCHAR(255) NOT NULL,     -- basename cwd — папка, где запущен терминал
  status ENUM('active','closing','inactive') NOT NULL DEFAULT 'active',
  summary VARCHAR(500) NULL,               -- краткое содержание переписки, пишется при закрытии
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  last_seen_at DATETIME NULL,              -- heartbeat от /loop
  closed_at DATETIME NULL,
  INDEX idx_status (status),
  INDEX idx_project (project_label)
);
```

## 3. Регистрация/возобновление — хук `SessionStart`, не скилл

**Уточнение механики Claude Code (важно для реализации):** скилл — это промпт-инструкция, которую
выполняет агент через свои тулы, но её всегда нужно **вызвать вручную** (`/skill-name`, либо агент
сам решает её использовать). Для "при каждом старте терминала — автоматическая регистрация" это не
подходит — нужен **хук `SessionStart`**: харнесс сам, без чьего-либо решения, исполняет команду при
старте новой сессии Claude Code в директории проекта (получает `session_id`/`cwd` на stdin,
конфигурируется в `.claude/settings.json`, тип `command` или `http`).

**Разделение ответственности (важное отличие от первой версии дизайна):** вся механика "оживления"
сессии — сохранить `session_uuid` в файл, поднять фоновый `watch` — инкапсулирована в коде
(`session_client.py`, `session_start.py`), а не в тексте инструкций, которые агент читает и
_может забыть выполнить_. Раньше это было устроено как "хук инжектит текст → агент читает CLAUDE.md
→ агент вручную выполняет шаги" — на практике оказалось ненадёжно: в другом проекте забыли
скопировать нужный кусок `CLAUDE.md`, и `watch` там просто никогда не запускался, хотя регистрация
(через хук) прошла нормально. Теперь `CLAUDE.md` эту логику вообще не описывает — не относится к
проекту, это инкапсулированная логика хука/сессии. Агенту нужно принять решение только там, где это
объективно требует диалога с пользователем (какую сессию продолжить/под какой ролью создать новую).

Итоговая механика:

1. Хук `SessionStart` при старте сессии первым делом проверяет, есть ли уже `.claude/session_uuid` с
   прошлого запуска.
   - **Если есть** — хук **сам**, без единого решения агента (даже без `AskUserQuestion`), вызывает
     `resume` и поднимает `watch` (см. §4) - функции `activate_session()`/`start_watch_detached()` в
     `session_client.py`, импортированные хуком напрямую. Агенту в `additionalContext` остаётся
     только заведомо не-автоматизируемая часть: завести `Monitor` на лог `watch` и обрабатывать
     реальные сообщения (это требует понимания естественного языка, хук этого не может).
     **Наблюдаемая на практике дыра надёжности:** `Monitor` — примитив уровня самой сессии Claude
     Code, хук физически не может завести его за агента; если агент проигнорирует инструкцию (было
     замечено на живом тесте в другом проекте - сессия зарегистрировалась и watch работал, но
     сообщения копились в очереди незамеченными, потому что `Monitor` не завели), ничего не
     сработает, пока пользователь не подтолкнёт агента вручную. Смягчение — не гарантия: текст
     инструкции сделан предельно акцентированным ("⚠️ ОБЯЗАТЕЛЬНО ПЕРВЫМ ДЕЙСТВИЕМ..."), и агенту
     дополнительно предписано в конце вызвать `session_client.py status --session-uuid <uuid>` -
     эта команда проверяет всё, что видно снаружи (`watch` жив, сервер отвечает, файл
     `session_uuid` на месте), и агент должен вывести пользователю получившийся чек-лист + свою
     строку "Monitor: ✅ armed" от себя (единственное, что command не видит - это внутреннее
     состояние сессии). Так пользователь хотя бы сразу видит, если что-то не завелось, вместо
     тишины.
   - **Если нет** — хук запрашивает у API список registry-записей для `project_label` (= basename
     cwd), инжектит их в `additionalContext` вместе с инструкцией: "покажи пользователю через
     `AskUserQuestion` выбор из этих сессий, либо создать новую". Здесь агент неизбежно нужен —
     выбор между несколькими прошлыми сессиями или ролью для новой требует диалога с человеком,
     хук вопросы не задаёт.
2. Агент (только в ветке "нет сохранённого uuid") вызывает `session_client.py resume --session-uuid
   <uuid>` (для выбранной) или `register --role <роль> --project-label <label>` (для новой). Обе
   команды сами, как часть своей работы (`activate_session()`), сохраняют `session_uuid` в
   `.claude/session_uuid` и поднимают `watch` — это не отдельный шаг, который агент должен не
   забыть, а гарантированный побочный эффект самой команды.
3. При следующем запуске терминала в этом же проекте — уже ветка 1, полностью автоматическая.

## 4. Heartbeat, разбор входящих и пересылка ответов в чат Mini App

Прямого способа узнать, что терминал закрылся (крash, разрядился ноутбук, сеть) — не существует.
Единственный надёжный механизм — **staleness по heartbeat**. Ключевое архитектурное решение:
heartbeat **не завязан** на то, думает ли сейчас LLM (`/loop` с backoff может не просыпаться по
15 минут, см. ниже) — его гонит отдельный бесресурсный (без LLM, без токенов) фоновый процесс:

- `activate_session()` в `session_client.py` (вызывается из `register`/`resume` и напрямую из
  `session_start.py` при автовозобновлении, §3) поднимает `python3 .claude/hooks/session_client.py
  watch --session-uuid <uuid> --terminal-pid <pid>` через `subprocess.Popen(...,
  start_new_session=True)` (эквивалент `setsid`) - **не** через `run_in_background: true` тула
  Bash. Это важно: `run_in_background` привязывает процесс к жизни самого процесса Claude Code, а
  не терминала - если Claude Code перезапустится или упадёт (не просто закрытие терминала), `watch`
  молча умирает вместе с ним, хотя окно терминала остаётся открытым (обнаружено на живом тесте:
  сессия в другом проекте запинговалась один раз и замолчала). `is_watch_running()` (pgrep) перед
  запуском не даёт задублировать процесс, если он уже жив.
- **Двухчастная защита от двух разных отказов, которые легко перепутать:**
  1. `start_new_session=True` полностью отвязывает `watch` от процесса Claude Code - переживает его
     перезапуск/краш, пока терминал (окно/шелл) физически открыт.
  2. Но полная отвязка - перебор в другую сторону: без второй части `watch` вообще ничем не убить
     кроме явного `kill`, даже реальным закрытием окна терминала (второй живой тест: `last_seen_at`
     продолжал обновляться часами после закрытия окна). Поэтому `find_terminal_pid()` до отвязки
     (пока процесс ещё в обычном дереве) находит настоящий шелл-владелец терминала - идёт вверх по
     родителям, ищет первый, который одновременно лидер своей сессии (`SID == PID`) и имеет
     настоящий TTY (наивный `os.getsid(0)` не подходит: харнесс заводит каждый вызов Bash-тула в
     свою изолированную сессию без TTY). Этот PID передаётся `watch`, который на каждом тике
     проверяет `/proc/<pid>` - если шелл терминала пропал (реальное закрытие окна), `watch`
     завершается сам; если жив (Claude Code просто перезапустился в том же терминале) - продолжает
     работать.
- На каждом тике (по умолчанию 5с): пингует `POST /telegram-app/claude/session/heartbeat` (просто
  curl, без LLM) и проверяет `GET /telegram-app/claude/session/inbox`, печатая маркер `NEW_MESSAGES`
  в stdout, только если там сообщение с `id` больше последнего уже увиденного (дедуп по `id` -
  глобальный auto-increment, монотонный; без этого маркер печатался бы на каждом тике, пока
  сообщение остаётся необработанным, а не один раз при появлении - реальная проблема, найденная на
  живом тесте).
- `GET /telegram-app/claude/sessions/active` (дёргает Mini App) считает сессию видимой, если
  `last_seen_at` не старше **15 секунд** (3× интервал поллера) — единственный критерий видимости.
  Так закрытие терминала пропадает из
  Mini App в течение ~15 секунд без какого-либо ручного действия.
- На этот же фоновый процесс вешается `Monitor` (`persistent: true`) — будит агента настоящим
  вызовом модели (с токенами) **только** когда поллер напечатал `NEW_MESSAGES`, т.е. только по
  реальному сообщению от пользователя, а не на каждом 5-секундном тике.

**Когда `Monitor` будит агента новым сообщением:**

1. `GET /telegram-app/claude/session/inbox?session_uuid=...` — забрать непрочитанные (`handled=0`)
   сообщения из `ai_claude_session`, отправленные через чат "Claude" в Mini App
   (`claude_message_user`, `src/tool/claude_/claude_.py`).
2. Обработать как обычный промпт пользователя и переслать результат через
   `POST /telegram-app/claude/respond` с `{session_uuid, response, inbox_id}` — `inbox_id` помечает
   исходное сообщение обработанным (`handled=1`).

Отдельный `/loop` с backoff здесь не нужен вообще — `watch` уже сам поддерживает heartbeat
непрерывно, независимо от того, работает ли сейчас LLM. Раньше рассматривался вариант держать поверх
него ещё и backoff-`/loop`, но это было избыточно: единственная причина заводить `/loop`/`ScheduleWakeup`
в этой схеме — разовая, не связанная с рутинной обработкой inbox задача (например дождаться, пока
пользователь нажмёт что-то в Mini App при ручном тестировании).

**Правило пересылки ответов (не только для входящих через inbox):** пока сессия
зарегистрирована в реестре (`.claude/session_uuid` существует), **любой** ответ, который эта
терминальная сессия производит — промежуточные шаги/размышления и финальный ответ, а не только
ответы на сообщения из inbox — дублируется в чат Mini App через `POST /telegram-app/claude/respond`,
чтобы пользователь видел прогресс в реальном времени, не только по завершении. Для промежуточных
шагов — `notify: false` (пишет в историю чата, без пуша в Telegram); для финального ответа —
`notify: true` (по умолчанию) — реальный пуш пользователю. Это симметрично уже принятому паттерну
для прямых Telegram-сообщений (см. `telegram-progress-visibility` в памяти: react + reply + edit для
промежуточных статусов, новый reply в конце для пуша) — тот же принцип, другой канал.

Эта пересылка — **не** задача хука `SessionStart` (тот исполняется один раз при старте и не может
перехватывать текст ответов в течение сессии) и **не** описана в `CLAUDE.md` (сознательно — это
инкапсулированная логика хука/сессии, не относится к проекту). Инструкция передаётся агенту через
`additionalContext` хука в момент, когда она реально релевантна (сессия зарегистрирована/резюмирована
именно в этом запуске) — см. §3.

**Третий сценарий остановки `watch` — хук `SessionEnd`.** `find_terminal_pid` (см. выше) специально
различает только два случая: краш/перезапуск Claude Code (шелл терминала жив - `watch` переживает) и
реальное закрытие терминала (шелл мёртв - `watch` завершается сам). Но есть третий, отдельный случай:
пользователь осознанно вышел из Claude Code (`exit`/`/exit`), а сам терминал остался открыт - с точки
зрения `find_terminal_pid` это неотличимо от "просто перезапустился", хотя пользователь явно
сигнализировал "я закончил". Для этого случая - `.claude/hooks/session_end.py`, зарегистрированный
на событие `SessionEnd` в `settings.json` (срабатывает на осознанное завершение, у самого краша
сработать физически нечему - процесс просто умирает). Хук останавливает `watch` для сессии этого
проекта (`pkill -f "session_client.py watch --session-uuid <uuid>"`), но **не** удаляет
`.claude/session_uuid` - следующий `claude` в этом же терминале подхватит её заново через
auto-resume (§3) и поднимет `watch` с нуля.

## 5. Пауза не нужна — сессия всегда активна, пока открыт терминал

Раньше здесь была кнопка-тумблер "Пауза"/"Возобновить" (`close-request`/`wake-request`,
`status='closing'/'inactive'`), задуманная как способ не тратить токены, пока сессия простаивает.
От неё отказались (обсуждение с пользователем, см. историю): к моменту, когда кнопку сделали, эта
проблема уже была решена на уровне §4 — `watch` и так не даёт LLM просыпаться, пока не придёт
реальное сообщение, значит "поставить на паузу" не экономит вообще ничего. Хуже того, реализация
паузы ничего и не блокировала технически: `watch`/`Monitor` продолжали будить агента на любое
сообщение независимо от `status`, то есть кнопка была чистым UI-лейблом без поведенческого эффекта.

Итог: `status` в реестре больше не переключается кнопкой из Mini App. Единственный сценарий, где
сессия перестаёт быть видна в Mini App — реальное закрытие терминала (staleness по heartbeat, §4).
Пока терминал открыт, `watch` слушает inbox и Mini App-чат работает всегда, без ручного
включения/выключения.

`POST /claude/session/finalize` как эндпоинт (записать summary, `status='inactive'`, `closed_at`)
остался — это не часть механизма паузы, а отдельная ручная операция (см. `session_client.py finalize`)
для случая, когда сессию осознанно "закрывают" насовсем (например для аккуратного summary в пикере
хука `SessionStart`, §3), но ничего не вызывает её автоматически по кнопке из Telegram.

**Кнопка "Удалить" (безвозвратно, не путать с отменённой паузой)** — другой сценарий: пользователь
явно хочет стереть сессию и начать с чистого листа. `POST /claude/session/delete-request` (owner):

1. Кладёт маркер `SESSION_CLEANUP_MARKER` (`__SESSION_CLEANUP__`) в очередь `ai_claude_session` -
   это должно случиться **до** удаления registry-строки, иначе терминалу нечего будет найти.
2. Удаляет саму registry-строку (`ai_claude_session_registry.delete`).
3. Терминал получает маркер через `watch` (как обычный тик опроса inbox) - и обрабатывает его **сам,
   без LLM**: `cleanup_session()` в `session_client.py` вызывает `POST
   /claude/session/cleanup-confirm` (чистит все строки `ai_claude_session` для этого `session_uuid`,
   включая сам маркер), удаляет локальный `.claude/session_uuid`, и `watch` завершает свой процесс
   (сессии больше нет - heartbeat гнать некому). Никакого `Monitor`-пробуждения агента не происходит
   - это чисто механическое действие, LLM тут нечего решать.
4. Если терминал не отвечает (закрыт) - registry-строка всё равно удалена шагом 2, что уже
   достаточно для "новый терминал зарегистрируется с нуля"; осиротевшие `ai_claude_session`-строки
   просто останутся, не мешают.

## 6. Telegram Mini App — UI

- Вкладка Cloud: первая (верхняя) иконка — "назад", дальше — по одной иконке на каждую
  registry-запись с `last_seen_at` не старше 15с (см. §4) — единственный критерий видимости.
- Иконка показывает роль + `project_label` (например "Developer — RhapsodyAi").
- Клик по иконке → чат, отфильтрованный по конкретному `session_uuid` — подтягивает историю из
  `ai_claude_session` (уже готовый механизм, просто параметризованный по uuid, а не хардкод одного).
  Единственная кнопка управления в чате — "Удалить" (безвозвратно, см. выше); паузы нет (§5 — убрана
  как бесполезная).
- И список сессий, и открытый чат периодически (раз в 5с, `refreshClaudeSessionStatus` в
  `telegram_app.html`) переспрашивают `GET /claude/sessions/active`, пока открыта вкладка Cloud —
  иначе, если окно Mini App простаивает без взаимодействия, картина визуально "залипает" на
  устаревшей (не подтягивается заново только по факту открытия вкладки). Если открытая сессия
  пропала из ответа (терминал реально закрылся) — в чат один раз добавляется предупреждение
  "⚠️ Терминал недоступен (сессия закрыта)".

## 7. API-эндпоинты (реализовано в `src/uvicorn/routers/telegram_app/telegram_app.py`)

| Эндпоинт | Кто вызывает | Действие |
|---|---|---|
| `GET /telegram-app/claude/sessions?project_label=...` | Хук `SessionStart` | Список всех registry-записей для проекта (любой статус) |
| `POST /telegram-app/claude/session/register` | Агент через `session_client.py register` | Создать новую запись (`role`, `project_label`) → `session_uuid`; побочный эффект - сохраняет файл и поднимает `watch` |
| `POST /telegram-app/claude/session/resume` | Хук `session_start.py` (автоматически) или агент через `session_client.py resume` | `status='active'`, вернуть историю сообщений (`agent_session`); тот же побочный эффект - файл + `watch` |
| `POST /telegram-app/claude/session/heartbeat` | Фоновый `session_client.py watch` (каждые ~5с) | Обновить `last_seen_at`, вернуть текущий `status` |
| `GET /telegram-app/claude/session/inbox?session_uuid=...` | Фоновый `session_client.py watch` (каждые ~5с) | Непрочитанные (`handled=0`) сообщения из `ai_claude_session` для этого `session_uuid` |
| `POST /telegram-app/claude/respond` | Терминал Claude Code (после обработки inbox или для промежуточных апдейтов) | Пишет ответ в `agent_session` (видно в чате Mini App), опционально `inbox_id` помечает сообщение обработанным, опционально пушит в Telegram (`notify`) |
| `POST /telegram-app/claude/session/finalize` | Агент вручную (не автоматически, см. §5) | Записать `summary`, `status='inactive'`, `closed_at` |
| `GET /telegram-app/claude/sessions/active` | Mini App (каждые 5с, пока открыта вкладка Cloud) | Сессии для иконок — видимость только по heartbeat ≤ 15с; добавляет `last_message` (превью последнего сообщения из `agent_session`, живой, не `summary`) |
| `POST /telegram-app/claude/session/delete-request` | Mini App (кнопка "Удалить") | Кладёт `SESSION_CLEANUP_MARKER` в `ai_claude_session`, затем удаляет registry-строку |
| `POST /telegram-app/claude/session/cleanup-confirm` | `session_client.py watch`, автоматически по маркеру (без LLM) | Удаляет все строки `ai_claude_session` для этого `session_uuid` |

Авторизация — тем же паттерном, что уже есть в файле: терминальные вызовы через
`_require_claude_secret` (заголовок `X-Claude-Secret`, секрет = `TELEGRAM_TOKEN_RHAPSODY`), вызовы
из Mini App — через `_require_telegram_owner` (сессия владельца).
