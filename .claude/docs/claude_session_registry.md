# Реестр сессий Claude Code для Telegram Mini App

> Цель: в Mini App, на вкладке Cloud, видеть все активные терминальные сессии Claude Code
> (по одной иконке на сессию), заходить в чат конкретной сессии с полной историей, и управлять
> её жизненным циклом (регистрация при старте терминала, мягкое отключение через Telegram).
> Множественные сессии независимы друг от друга, могут относиться к одному или разным проектам,
> закреплены за ролью (пока только `developer`, дальше — `qa` и др., см. `workflow_dev_qa_agents.md`).

## 1. Что уже есть и переиспользуется

`ai_claude_session` (`migrations/0001.sql`) — это **очередь сообщений**, не реестр: каждая строка —
одно сообщение, ключуется по `session_uuid` (`content`/`response`/`handled`). Уже поддерживает
сколько угодно параллельных `session_uuid` — сейчас используется только один (статичный агент
"Claude", id 34 в `agent_workflow`/`agent`, `migrations/0005.sql`).

- `claude_message_user(prompt_user, session_uuid)` (`src/tool/claude_/claude_.py`) — кладёт
  сообщение пользователя в очередь.
- `claude_message_cloud(session_uuid, response, inbox_id)` — терминал пишет ответ обратно + дублирует
  в `agent_session`/Telegram.

**Вывод:** переписка уже мультисессионна по конструкции. Не хватает только слоя **реестра** —
кто сейчас активен, под какой ролью, под каким проектом — и UI поверх него.

## 2. Новая таблица — реестр (не путать с очередью выше)

Сознательно только **две** таблицы, без третьей "сессионных фактов" — краткое содержание пишется
прямо в реестр в момент закрытия сессии (см. §5), когда LLM и так активна для финальной уборки;
отдельный Workflow/fact-пайплайн для этого избыточен на первую версию.

Добавляется прямо в `migrations/0001.sql` (без сидовых данных, это чистая DDL-миграция):

```sql
CREATE TABLE ai_claude_session_registry (
  id INT AUTO_INCREMENT PRIMARY KEY,
  session_uuid CHAR(36) NOT NULL UNIQUE,   -- тот же uuid, что ключует ai_claude_session
  role VARCHAR(50) NOT NULL DEFAULT 'developer',
  project_label VARCHAR(255) NOT NULL,     -- basename cwd — папка, где запущен терминал
  status ENUM('active','closing','inactive') NOT NULL DEFAULT 'active',
  summary VARCHAR(500) NULL,               -- краткое содержание переписки, пишется при закрытии
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  last_seen_at DATETIME NULL,              -- heartbeat от /loop
  closed_at DATETIME NULL,
  INDEX idx_status (status),
  INDEX idx_project (project_label)
);
```

## 3. Регистрация/возобновление — хук `SessionStart`, не скилл

**Уточнение механики Claude Code (важно для реализации):** скилл — это промпт-инструкция, которую
выполняет агент через свои тулы, но её всегда нужно **вызвать вручную** (`/skill-name`, либо агент
сам решает её использовать). Для "при каждом старте терминала — автоматическая регистрация" это не
подходит — нужен **хук `SessionStart`**: харнесс сам, без чьего-либо решения, исполняет команду при
старте новой сессии Claude Code в директории проекта (получает `session_id`/`cwd` на stdin,
конфигурируется в `.claude/settings.json`, тип `command` или `http`).

**Разделение ответственности:** хук гарантированно (без чьего-либо решения) достаёт данные и
инжектит их в контекст новой сессии; сам интерактивный выбор — это уже работа агента (меня) через
`AskUserQuestion`, когда сессия уже стартовала с этим контекстом на руках.

Итоговая механика:

1. Хук `SessionStart` (shell-скрипт или прямой HTTP-вызов, `type: "http"`) при старте сессии
   запрашивает у API список registry-записей для текущего `project_label` (= basename cwd) —
   **все**, не только активные (нужны и закрытые — их тоже можно выбрать для продолжения).
   Каждая запись: `role`, `id`, `project_label`, `status`, `closed_at`, `summary`.
2. Хук возвращает этот список как дополнительный контекст в начало сессии, вместе с инструкцией:
   "покажи пользователю через AskUserQuestion выбор из этих сессий (роль/id/дата закрытия/summary)
   + опцию "создать новую"; при создании новой — уточни роль (пока только `developer`)".
3. Я (агент) в начале сессии вижу эту инструкцию и данные, показываю выбор пользователю.
   - **Выбрана существующая** — вызываю `POST /api/session/resume` с её `session_uuid`, подтягиваю
     историю из `ai_claude_session` (content/response пары) как контекст, `status='active'`.
   - **Создать новую** — уточняю роль, вызываю `POST /api/session/register` (uuid4, `role`,
     `project_label` = cwd), `status='active'`.
4. Сохраняю `session_uuid` локально в проекте (например `.claude/session_uuid` — не коммитить,
   добавить в `.gitignore`), чтобы `/loop`-промпт на каждой итерации знал, за какой registry-строкой
   ему обновлять heartbeat.

## 4. Heartbeat, разбор входящих и пересылка ответов в чат Mini App

Прямого способа узнать, что терминал закрылся (крash, разрядился ноутбук, сеть) — не существует.
Единственный надёжный механизм — **staleness по heartbeat**. Ключевое архитектурное решение:
heartbeat **не завязан** на то, думает ли сейчас LLM (`/loop` с backoff может не просыпаться по
15 минут, см. ниже) — его гонит отдельный бесресурсный (без LLM, без токенов) фоновый процесс:

- Сразу при регистрации/резюме сессии (§3, шаг 3) запускается в фоне (`run_in_background: true`)
  `python3 .claude/hooks/session_client.py watch --session-uuid <uuid>` — на каждом тике (по
  умолчанию 30с): пингует `POST /telegram-app/claude/session/heartbeat` (просто curl, без LLM) и
  проверяет `GET /telegram-app/claude/session/inbox`, печатая маркер `NEW_MESSAGES` в stdout, только
  если там есть непрочитанное. Живёт ровно пока жив терминал — если окно/процесс Claude Code закрыт
  (крash, вручную), фоновый процесс умирает вместе с ним, и пинги останавливаются сами собой.
- `GET /telegram-app/claude/sessions/active` (дёргает Mini App) считает сессию видимой, если
  `last_seen_at` не старше **60 секунд** (2× интервал поллера) — единственный критерий видимости,
  не завязан на поле `status`. Так закрытие терминала (в обход кнопки "Пауза") пропадает из
  Mini App в течение ~60 секунд без какого-либо ручного действия.
- На этот же фоновый процесс вешается `Monitor` (`persistent: true`) — будит агента настоящим
  вызовом модели (с токенами) **только** когда поллер напечатал `NEW_MESSAGES`, т.е. только по
  реальному сообщению от пользователя, а не на каждом 30-секундном тике.

**Когда `Monitor` будит агента новым сообщением:**

1. `GET /telegram-app/claude/session/inbox?session_uuid=...` — забрать непрочитанные (`handled=0`)
   сообщения из `ai_claude_session`, отправленные через чат "Claude" в Mini App
   (`claude_message_user`, `src/tool/claude_/claude_.py`).
2. Если сообщение — маркер `__SESSION_WAKE__` (см. §5, кнопка "Возобновить") — просто вызвать
   `session/resume`, никакого содержательного ответа не требуется (можно тихо, `notify: false`,
   подтвердить в чат "Сессия возобновлена").
3. Иначе — обработать как обычный промпт пользователя и переслать результат через
   `POST /telegram-app/claude/respond` с `{session_uuid, response, inbox_id}` — `inbox_id` помечает
   исходное сообщение обработанным (`handled=1`).
4. После обработки — если ожидается продолжение диалога (не просто разовая пауза), можно
   дополнительно завести собственный `/loop` с backoff (60s → удвоение → потолок 900s) поверх уже
   работающего фонового `watch` — но это уже не обязательно для одного только поддержания heartbeat,
   он и так продолжает идти через `watch`.

**Правило пересылки ответов (не только для входящих через inbox):** пока сессия
зарегистрирована в реестре (`.claude/session_uuid` существует), **любой** ответ, который эта
терминальная сессия производит — промежуточные шаги/размышления и финальный ответ, а не только
ответы на сообщения из inbox — дублируется в чат Mini App через `POST /telegram-app/claude/respond`,
чтобы пользователь видел прогресс в реальном времени, не только по завершении. Для промежуточных
шагов — `notify: false` (пишет в историю чата, без пуша в Telegram); для финального ответа —
`notify: true` (по умолчанию) — реальный пуш пользователю. Это симметрично уже принятому паттерну
для прямых Telegram-сообщений (см. `telegram-progress-visibility` в памяти: react + reply + edit для
промежуточных статусов, новый reply в конце для пуша) — тот же принцип, другой канал.

Эта пересылка — **не** задача хука `SessionStart` (тот исполняется один раз при старте и не может
перехватывать текст ответов в течение сессии). Правило закреплено в `CLAUDE.md` (durable,
перечитывается каждый запуск сессии), т.к. хук физически не может обернуть каждый последующий ответ.

## 5. Пауза/Возобновить через Telegram (кнопка-тумблер, не "Отключить")

Кнопка в чате Mini App — тумблер "Пауза"/"Возобновить" (`⏸`/`▶`, см. §6), не безвозвратное
удаление. **Не убивает процесс терминала** ни в одну из сторон:

**Пауза** (`POST /claude/session/close-request`) — выставляет `status='closing'` в реестре:

1. На ближайшем тике фонового `watch`-процесса (или ближайшем пробуждении активного `/loop`, если
   он в этот момент работает) видит `status='closing'` для своего `session_uuid`.
2. Делает финальную уборку: краткое summary переписки (по последним ~10 сообщениям из
   `ai_claude_session`) пишется в `ai_claude_session_registry.summary` — для показа в пикере хука
   при следующем запуске (§3); при необходимости — отдельно факт в долгосрочную память
   (см. `workflow_dev_qa_agents.md` §6).
3. Проставляет `status='inactive'`, `closed_at=NOW()`.
4. **Не тратит токены дальше, но остаётся "будимой" через Telegram** — фоновый `watch` (§4)
   **не останавливается**: heartbeat продолжает идти каждые 30с (сессия остаётся видимой в Mini App,
   просто с серой точкой/иконкой на паузе, см. §6), `Monitor` продолжает слушать его stdout. Никакого
   отдельного `ScheduleWakeup` держать не нужно — весь смысл в том, что между паузой и возобновлением
   агент вообще не просыпается и не тратит токены, а heartbeat всё равно идёт (он гонится процессом
   без LLM).

**Возобновить** (`POST /claude/session/wake-request`) — не может напрямую "разбудить" спящий
процесс, поэтому кладёт спец-сообщение `__SESSION_WAKE__` в ту же очередь `ai_claude_session`,
которую слушает фоновый `watch`. Тот видит непрочитанное, печатает `NEW_MESSAGES`, `Monitor` будит
агента реальным вызовом модели → см. §4, шаг 2 (агент вызывает `session/resume`, статус снова
`active`).

**Ограничение:** всё это работает, только пока сам терминал (процесс Claude Code) физически
открыт — фоновый `watch` и `Monitor` живут внутри него. Если пользователь закроет окно терминала —
heartbeat перестаёт идти, сессия пропадает из Mini App через ~60с (§4) и разбудить её через Telegram
уже нечем ни паузой, ни "Возобновить" (кнопка в UI сама скроется вместе с иконкой сессии). Единственный
путь для этого случая — периодическая headless-джоба Cronicle (`claude -p ...`, см.
`workflow_dev_qa_agents.md` §7), которая поднимает новый процесс с нуля на расписании (например раз в
15-30 минут) и реально тратит токены на каждый запуск, но не зависит от того, жив ли терминал.

Задержка между нажатием кнопки и фактической остановкой = один тик `watch` (до ~30с, ожидаемо, не баг).

## 6. Telegram Mini App — UI

- Вкладка Cloud: первая (верхняя) иконка — "назад", дальше — по одной иконке на каждую
  registry-запись с `last_seen_at` не старше 60с (см. §4) — независимо от `status`, активна она или
  на паузе.
- Иконка показывает роль + `project_label` (например "Developer — RhapsodyAi"); точка статуса в
  списке сессий — зелёная (`active`) либо серая (`closing`/`inactive`, т.е. на паузе).
- Клик по иконке → чат, отфильтрованный по конкретному `session_uuid` — подтягивает историю из
  `ai_claude_session` (уже готовый механизм, просто параметризованный по uuid, а не хардкод одного).
- В чате — кнопка-тумблер "Пауза"/"Возобновить" (`⏸`/`▶`, см. §5), не безвозвратное удаление.
- И список сессий, и открытый чат периодически (раз в 15с, `refreshClaudeSessionStatus` в
  `telegram_app.html`) переспрашивают `GET /claude/sessions/active`, пока открыта вкладка Cloud —
  иначе, если окно Mini App простаивает без взаимодействия, статус/кнопка визуально "залипают" на
  устаревшей картинке (не подтягиваются заново только по факту открытия вкладки). Если открытая
  сессия пропала из ответа (терминал реально закрылся) — кнопка блокируется и подписывается
  "Сессия недоступна".

## 7. API-эндпоинты (реализовано в `src/uvicorn/routers/telegram_app/telegram_app.py`)

| Эндпоинт | Кто вызывает | Действие |
|---|---|---|
| `GET /telegram-app/claude/sessions?project_label=...` | Хук `SessionStart` | Список всех registry-записей для проекта (любой статус) |
| `POST /telegram-app/claude/session/register` | Хук `SessionStart` | Создать новую запись (`role`, `project_label`) → `session_uuid` |
| `POST /telegram-app/claude/session/resume` | Хук `SessionStart`, агент (после `__SESSION_WAKE__`) | `status='active'`, вернуть историю сообщений (`agent_session`) |
| `POST /telegram-app/claude/session/heartbeat` | Фоновый `session_client.py watch` (каждые ~30с) | Обновить `last_seen_at`, вернуть текущий `status` |
| `GET /telegram-app/claude/session/inbox?session_uuid=...` | Фоновый `session_client.py watch` (каждые ~30с) | Непрочитанные (`handled=0`) сообщения из `ai_claude_session` для этого `session_uuid` |
| `POST /telegram-app/claude/respond` | Терминал Claude Code (после обработки inbox или для промежуточных апдейтов) | Пишет ответ в `agent_session` (видно в чате Mini App), опционально `inbox_id` помечает сообщение обработанным, опционально пушит в Telegram (`notify`) |
| `POST /telegram-app/claude/session/finalize` | Агент (увидев `status='closing'`) | Записать `summary`, `status='inactive'`, `closed_at` |
| `GET /telegram-app/claude/sessions/active` | Mini App (каждые 15с, пока открыта вкладка Cloud) | Сессии для иконок — видимость только по heartbeat ≤ 60с, `status` только для вида иконки |
| `POST /telegram-app/claude/session/close-request` | Mini App (кнопка "Пауза") | `status='closing'` |
| `POST /telegram-app/claude/session/wake-request` | Mini App (кнопка "Возобновить") | Кладёт `__SESSION_WAKE__` в `ai_claude_session` — будит `watch`/`Monitor` терминала |

Авторизация — тем же паттерном, что уже есть в файле: терминальные вызовы через
`_require_claude_secret` (заголовок `X-Claude-Secret`, секрет = `TELEGRAM_TOKEN_RHAPSODY`), вызовы
из Mini App — через `_require_telegram_owner` (сессия владельца).
