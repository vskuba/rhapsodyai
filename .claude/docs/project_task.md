# Task — страница задач и конвейер агентов

> Модуль задач: админ-страница `/admin/task`, REST API и конвейер, в котором задачу
> последовательно ведут Manager → человек → Developer → QA. У задачи два независимых
> состояния (`status` и `pipeline_state`), конвейер крутит транзакционный воркер.

**Все три роли настоящие.** Каждая отправляет задание живому Claude Code в свою
shell-оболочку и ждёт ответа: Manager (роль `manager`) возвращает план, разбиение и цели;
Developer (роль `developer`, каталог проекта задачи) выполняет одну подзадачу и
отчитывается о сделанном; QA (роль `qa`, тот же каталог) принимает её работу по целям
подзадачи. Контракт ролей — §7.

## 1. Две независимые оси состояния

Главное, что нужно понять про этот модуль: у задачи **два состояния, а не одно**.

| Поле | Что означает | Кто меняет |
|------|--------------|------------|
| `project_task.status` | человеческий kanban-статус | человек через `/admin/task` |
| `project_task.pipeline_state` | стадия автоматики; `NULL` = вне конвейера | оркестратор + кнопки утверждения |

Смешивать их нельзя: на `status` завязаны фильтры, сортировка и цвета админки.

Вход в конвейер — **отсутствие плана**, а не явное действие человека: задачу, у которой
в `pipeline_plan` нет подзадач, Manager подхватывает на ближайшем тике, независимо от
`status` и от того, был ли нажат «В конвейер». Кнопка `start` осталась только как
способ вернуть в работу отклонённую задачу.

Исключения два:

- `pipeline_state = 'failed'` — у сорвавшегося менеджера план так и остался пустым,
  и без этого фильтра тик подбирал бы такую задачу вечно;
- **задача с подзадачами** — планируются только листья, см. §2.1.

**Второй вход — пересмотр.** Кнопка «Обновить план» ставит `pipeline_state = 'reviewing'`,
и задачу забирает отдельный шаг. Отдельное состояние нужно именно потому, что обычный
отбор идёт по **отсутствию** плана (`JSON_LENGTH($.subtasks) = 0`): у задачи с уже
написанным планом это условие не выполнится никогда, и без `reviewing` она осталась бы
для конвейера невидимой.

`project_task.status`: `pending` · `queued` · `active` · `done` · `blocked` · `cancelled`

## 2. Страница `/admin/task`

Шаблон: `data/uvicorn/template/admin/project/task.html` (extends `base.html`).
Маршрут: `src/uvicorn/routers/dashboard.py` → `task_page()`.

### Панель инструментов

Заголовок, счётчик отфильтрованных задач, выбор проекта («Без проекта» = `project_id 0`),
поиск, чипы-фильтры по статусам с количеством, кнопка «+ Добавить».

Селект проекта не «показать всё», а полноценный фильтр: страница всегда грузит
`GET /tasks/{project_id}`, и пункт «Без проекта» отдаёт задачи, у которых
`project_id = 0 ИЛИ NULL` (форма пишет 0, задачи мимо неё остаются с NULL).

Выбранный проект запоминается в `localStorage.task_project_id` и восстанавливается
в `loadProjects()`: страница задач — рабочее место внутри одного проекта, сбрасывать
его на каждый F5 бессмысленно. Значение сверяется со списком опций — если проект
удалили, молча откатываемся на «Без проекта», а не оставляем пустой селект.

Поиск и чипы применяются на клиенте в `taskMatches()` — по названию, описанию
и отчёту. Строки собирает `treeRows()` (§2.1).

### Таблица

Семь колонок (`data-col`): `id` · `status` · `title` · `desc` · `goals` · `date` · `act`.

- **Порядок колонок** — drag-and-drop за заголовок, `localStorage.task_col_order_v1`
- **Ширины** — перетаскиванием разделителя, в процентах, `localStorage.task_col_pct_v3`

> При изменении набора колонок **обязательно поднять версию ключа** `task_col_pct_v3`,
> иначе применятся сохранённые ширины от старой раскладки и вёрстка поедет.
> (Колонки `project` не стало именно поэтому ключ уже `v3`, а не `v2`.)

Слева у каждой строки — цветная полоса статуса (`--row-accent`, см. `STATUS_ACCENT`).
Строка кликабельна: раскрывается инлайн-редактор.

**Порядок строк — по статусу, затем ручной** (`taskCompare`). Наверху то, что идёт прямо
сейчас («В работе»), под ним ближайшее к запуску («В очереди»), затем всё незакрытое
(«Ожидает», «Заблокировано», «Отменено») и в самом низу «Готово» — законченное места наверху
не занимает, а список растёт именно им. Группы берутся из `STATUS_ORDER`, того же, по
которому стоят чипы фильтра. Внутри группы — `position` (стрелки ⬆⬇) и дата создания.
Отсюда следствие: **стрелки двигают задачу только внутри её группы**, соседа из другой
группы перепрыгнуть нельзя, пока не сменится статус. В дереве правило работает на каждом
уровне отдельно — дети сортируются между собой и остаются под своим родителем.

### 2.1 Дерево задач (`project_task.parent_id`)

Большую задачу можно разбить на подзадачи: `project_task.parent_id` ссылается на `project_task.id`,
глубина ограничена только `MAX_DEPTH = 5`.

> **Дерево одно на всех.** Подзадачи, которые конвейер раскладывает из утверждённого плана
> менеджера, — такие же дети `project_task`, только с меткой `pipeline_from_plan = 1`.
> Отдельной таблицы у конвейера нет: по метке он находит свои строки, а человеческую
> декомпозицию «эпик → подзадачи» не трогает (сброс и пересмотр плана удаляют только
> помеченные).

**Вложенность живёт внутри колонки «Название», отдельной колонки нет.** Ширины
колонок сохранены в `localStorage` по их количеству, и лишняя колонка обнулила бы
всем сохранённую раскладку (см. предупреждение про `task_col_pct_v3` выше).

Отрисовка — `treeRows()` в шаблоне, обход в глубину; возвращает
`{t, depth, rails, isLast, hasKids, expandable, kidsTotal, kidsDone, ghost}`:

| Элемент | Что делает |
|---------|-----------|
| `treeIndent(row)` | рельсы предков + уголок; в слоте `j` идёт линия предка глубины `j+1`, поэтому срез `rails.slice(1, depth)` |
| `treeCaret(row)` | сворачивание ветки; состояние в `localStorage.taskTreeCollapsed` |
| `.tree-kids` | пилюля `сделано/всего` по прямым детям, зелёная когда всё закрыто |
| `＋` (`.btn-row-sub`) | открывает форму добавления с баннером «подзадача к …» |
| селект «Родительская задача» | перенос по дереву; своя ветка из списка исключена |

Поведение при фильтре и поиске:

- задача, подошедшая под поиск, **тянет за собой предков** — иначе ветка повисла бы
  без родителя; предки помечены `ghost` и приглушены;
- в счётчике найденного только не-`ghost` строки, иначе контейнеры раздували бы число;
- свёрнутость при активном фильтре **игнорируется**, каретка прячется (`expandable`) —
  иначе найденное пряталось бы внутри свёрнутого родителя и поиск бы врал.

Правила целостности — `src/project/task/task_tree.py`, вызываются из роутера на
создании и на обновлении:

- родителя нет → `400` (не `500` от внешнего ключа);
- сама себе родитель → `400`;
- перенос внутрь собственной ветки (цикл) → `400`, проверка идёт вверх от родителя;
- превышение `MAX_DEPTH` → `400`;
- `position` считается **внутри родителя**, а не сквозь проект — иначе подзадача
  уезжала бы в конец таблицы вместо своей ветки.

**Удаление каскадное:** `fk_pt_parent ... ON DELETE CASCADE` — родитель уносит всю
ветку. Перед удалением фронт считает потомков и предупреждает точным числом.

**Планируются только листья.** Задача, у которой есть подзадачи, конвейером не
подхватывается: родитель — контейнер, его планом уже является список детей. Иначе
эпик с пятью подзадачами дал бы шесть прогонов планирования (см. `task_claim_task_unplanned`).

### Цели

JSON-массив `[{text, done}]` в колонке `project_task.goals` — у проверенной QA цели
добавляется третий ключ `evidence` (чем проверена; показывается подсказкой при
наведении на формулировку). Редактируются в двух местах:

- **прямо в таблице** — чекбокс, ✏ и ✕ (`inlineToggleGoal` / `inlineEditGoal` /
  `inlineDeleteGoal`), сохраняются сразу, без кнопки «Сохранить»; над списком —
  прогресс `2/3` с полоской
- **в раскрытой строке** — секция «Цели» с `_goalsCache`

Заполняются и вручную, и Manager'ом: при планировании его цели дописываются к целям
человека, не затирая их (§7.2). В блоке «Конвейер» тот же список показан на чтение —
это версия из плана, чтобы было видно расхождение с отредактированной.

Галочки ставят трое, и каждый по своему поводу: человек — руками; QA — по одной,
отдельным ответом на каждую цель подзадачи (§7.3); родительская задача — только
наследованием (`task_state_goals_inherit`) тех своих целей, которые дословно совпали
с целями, закрытыми в её подзадачах. Скопом список не закрывается нигде: готовая
задача с пустым чекбоксом честнее, чем галочка без проверки.

### Раскрытая строка

Название, статус, описание (с голосовым вводом), **план**, цели, блок «Конвейер» (§6), отчёт.

Поле «План» (`tplan-{id}`) стоит между описанием и целями. Пишет его Manager по
описанию задачи, человек может править руками. В колонке лежит JSON
`{plan_text, subtasks, goals}`, в форме — только `plan_text`: клиент достаёт его
`parsePlanText()`, а `PUT /task/{id}` принимает ключ `plan_text` и вклеивает его в
JSON, **сохраняя `subtasks` и `goals`** — иначе ручная правка сносила бы разбивку
менеджера и цели из плана. Текст плана в блоке «Конвейер» намеренно не дублируется.

### 2.2 Ревизии плана

В одну строку с заголовком «План» справа висят чипсы ревизий по убыванию
(`#revs-{id}`, контейнер `.task-rev-chips`). Первый — **«Текущая»**, дальше
«Ревизия N · HH:MM» по остальным (`revs.slice(1)`), в конце — «…ещё N», если история
длиннее отданного окна.

> Отдельного чипса под текущий план нет: снимок пишется в момент **создания** версии,
> поэтому самая свежая ревизия и **есть** текущий план — рисуя её дважды, мы бы
> показали одну версию под двумя именами.

Чипсы **переносятся по строкам**, а не скроллятся: у `.task-scroll` стоит
`overflow-x: hidden`, и собственная горизонтальная полоса внутри строки заголовка
осталась бы недосягаемой.

**Клик по чипсу — только просмотр.** `revisionShow()` подставляет в textarea план из
ревизии, ставит `readonly`, рисует цели той версии, отключает «+ Добавить цель» и
«Сохранить», а над полем показывает бейдж «Просмотр ревизии N» с кнопкой
«Восстановить». Возврат — чипс «Текущая» (`revisionCurrent()`).

Живой, несохранённый текст плана при входе в просмотр уезжает в `_revPlanStash[taskId]`
и возвращается на выходе, а цели ревизии рисуются мимо `_goalsCache` — иначе заглянуть
в историю значило бы потерять свои правки.

**Кнопка «Обновить план»** живёт в `#pipe-actions-{id}` рядом с «Утвердить»/«Отклонить»
(там уже известен `pipeline_state`). Её нет вовсе, пока плана нет — за первый план
отвечает «В конвейер». Активна только при
`pipeline_state ∈ {NULL, plan_approval, done, failed}`; в остальных состояниях
`disabled` с объяснением в `title` (`PLAN_REVIEW_BLOCKED`).

> Подсказка висит на обёртке `<span class="pipe-btn-wrap" title="…">`, а не на самой
> кнопке: у `disabled`-кнопки браузер `title` не показывает, и причина блокировки была
> бы недоступна ровно там, где нужна.

Данные ревизий грузятся **лениво**, при раскрытии строки (`revisionsLoad` рядом с
`pipelineLoad` в `toggleEdit`) — тянуть их в `loadTasks` значило бы +N запросов на
страницу, где раскрыта одна строка.

> `renderTable()` пересобирает `wrap.innerHTML` и закрывает раскрытую строку. Всё, что
> перезагружает таблицу (`saveTask`, `pipelineAction`, `revisionRestore`), обязано
> запомнить `wasOpen` и открыть строку заново через `toggleEdit(id)`, иначе панель
> исчезает прямо из-под курсора.

Времена ревизий форматирует глобальный `window.fmtTz` из `tz.js`; инициализация
страницы ждёт `window.loadTz()` перед первой отрисовкой — без него `fmtTz` молча
показывает UTC.

> Поле отчёта имеет id `trep-{id}`, **не** `tr-{id}` — последний занят самим `<tr>`
> строки, и `getElementById` возвращал бы элемент таблицы вместо textarea.

### Голосовой ввод и ИИ

- 🎤 → `POST /chat/voice`, распознанный текст дописывается в описание
- «ИИ помощник» → `POST /task/ai-generate`: из описания получаются название,
  развёрнутое описание и список целей (цели применяются после создания задачи)

## 3. Машина состояний конвейера

```
задача (project_task, parent_id = NULL) — pipeline_state:

  NULL | new  --(нет плана)--> planning --> plan_approval
                                                    |
                              («Отклонить») <-------+-------> («Утвердить»)
                                     |                              |
                                   NULL                         approved
                                                                    |
                                                               processing --> done | failed
                                                                    |             ^
                                                                 testing ---------'

  NULL | plan_approval | done | failed  --(«Обновить план»)--> reviewing --> plan_approval

  plan_approval + флажок «в разработку» --> approved (тип задачи: plan --> dev)

  processing + все подзадачи в qa_pending + флажок «в тестирование» --> testing
                                                            (тип задачи: dev --> test)

подзадача (тот же project_task, parent_id != NULL) — pipeline_state:

  planned --> developing --> qa_pending --> done
                   ^                 |
                   |                 +--> failed_qa --> повтор, пока pipeline_attempt_count < timeout_attempt_max
                   +-----------------'                        |
                                                              +--> blocked (лимит исчерпан)
```

Задача уходит в `done`, когда все подзадачи терминальны; если хоть одна `blocked` — в `failed`.

**Флажок «в планирование»** (колонка «Прогресс» на вкладке «Планирование», он же
чекбокс в окошке фиксера) — единственный из трёх, который стоит **до** конвейера, а не
на развилке внутри него: он решает, отдавать ли заведённую задачу менеджеру за планом.
Умолчание «включено», поэтому хранится он наизнанку, как «в тестирование»: ключа нет =
задача планируется, снятый флажок пишется явным `false`. Фиксер поэтому в обычном случае
`metadata` не шлёт вовсе, а снятый флажок отправляет прямо в `POST /tasks/{project_id}`
— заводить задачу и помечать её вторым запросом нельзя, в промежуток успевает попасть
тик оркестратора.

Читает пометку захват: `task_claim_task_unplanned` дописывает в отбор
`task_metadata_plan_free_sql()`. Проверка стоит только там, а не в общем `_task_claim`, —
запрещено написание плана, а не работа вообще, и задачу с уже готовым планом пометка не
тормозит. Кнопка «В конвейер» (`POST /task/{id}/pipeline/start`) ключ стирает: нажатие и
есть просьба о плане прямо сейчас, иначе задача ушла бы в `new` и там осталась.

**Флажок «в разработку»** (колонка «Прогресс» на вкладке «Планирование») — согласие,
данное заранее: человек говорит, что план утверждать не потребуется. Как только менеджер
дописал план и задача встала в `plan_approval`, `task_state_plan_to_development()`
одним UPDATE меняет тип с `plan` на `dev`, переводит состояние в `approved` и снимает
пометку — шаг «Утвердить» пропускается, дальше идёт обычный `processing`. Пометка
одноразовая: флажок рисуется только на вкладке «Планирование», а задача с этого шага
уходит на «Разработку», и снять его было бы уже нечем. Тип, отличный от `plan`, и любое
другое состояние функция не трогает.

**Флажок «в тестирование»** (та же колонка на вкладке «Разработка») — то же согласие на
следующей развилке, но с обратным умолчанием: он **включён**, пока его явно не сняли.
Сделанная работа обязана попадать на проверку сама, решением человека является как раз
отказ от неё, поэтому в `metadata` хранится отклонение от умолчания: ключа нет = пометка
стоит, снятый флажок пишется явным `false`. Читатель обязан отличать «нет ключа» от
`false` (`<> FALSE`, а не `= TRUE`).

Срабатывает пометка, когда разработка кончилась **по всем веткам плана**: есть хотя бы
один ребёнок в `qa_pending` и ни одного в `planned`, `failed_qa`, `developing`, `blocked`
или `failed`. Это ровно то, что страница задач показывает чипсом родителя (`_pipeKidsTask`
берёт самую отстающую подзадачу), — отсюда и слова человека «задача в статусе
`qa_pending`»: в БД у родителя всё это время `processing`, `qa_pending` — состояние
детской ветки. `task_state_dev_to_testing()` одним UPDATE меняет тип `dev` → `test` и
состояние `processing` → `testing`.

Зовут её из двух мест: `_task_to_testing()` после каждого удачного круга Developer
(сработает у того, кто закрыл последнюю ветку) и `POST /task/{id}/metadata`, когда
человек возвращает флажок уже дошедшей до рубежа задаче. Отдельного шага конвейера нет
намеренно — это смена вкладки, а не работа агента. Пометка не одноразовая: она остаётся
в мешке, и после `retry` из `failed` задача войдёт в `testing` повторно.

`testing` — рабочее состояние (`status = active`, «в работе»): круг QA по подзадачам идёт
дальше, просто под вкладкой «Тестирование». Закрывает такую задачу та же
`task_state_task_finalize()`, что и `processing`, — она забирает оба состояния.

## 4. Триггер, очередь, воркер

Оркестратор **ничего не выполняет**. Cronicle раз в минуту дёргает тик, тик смотрит
состояния, захватывает работу, кладёт по сообщению на действие в **Redis-очередь** и
сразу выходит. Работу разбирает `rq worker`, и воркеров может быть много — процесс
масштабируется горизонтально без изменений в коде.

**Кронджоб на весь конвейер ровно один** — `src/cronjob/task_orchestrator.py`. Отдельных
джобов на Manager, Developer и QA нет: один тик централизованно смотрит все стадии сразу
и захватывает первое подошедшее действие (порядок проверок — в `task_pipeline._action_claim`).
Логика лежит в `src/project/task/` и кронджобом не является (правило 4.3 в
`architecture_rules.md`).

```
Cronicle (:3012) --POST /cronjob--> uvicorn --subprocess--> src/cronjob/task_orchestrator.py
                                                                     |
                                                    task_pipeline_tick(): reclaim + claim + enqueue
                                                                     |
                                                          Redis queue `default`
                                                                     |
                     контейнер worker (`rq worker default`) --> task_worker_job_run(action)
                                                                     |
                                                    task_pipeline_action_run(): Manager / Dev / QA
```

```bash
curl -s -X POST localhost:8011/cronjob -H 'Content-Type: application/json' \
  -d '{"cronjob_path":"src/cronjob/task_orchestrator.py","metadata":{"max_actions":1},"timeout":60}'
```

`timeout` в теле — потолок жизни подпроцесса тика, и он маленький намеренно: тик не ходит
ни к менеджеру, ни к агентам, зависнуть ему негде. Долгие таймауты живут на другом конце
цепочки и выстроены по возрастанию:

| Настройка | Умолчание | Смысл |
|---|---|---|
| `timeout_manager_run` | 3600s | сколько ждём ответа shell-оболочки менеджера |
| `timeout_developer_run` | 3600s | то же для оболочки разработчика |
| `timeout_qa_run` | 3600s | то же для оболочки QA |
| `timeout_worker_job` | 3900s | потолок job'а в rq (дефолт rq — 180s, его обязательно переопределять) |
| `timeout_task_lock` | 4200s | когда блокировку считают протухшей и работу отдают заново |

Это не константы в модулях, а строки таблицы `setting`: реестр — `src/project/task/task_setting_timeout.py`,
редактор — блок «⏱ Таймауты» на карточках `/admin/team`, значение читается в момент
ожидания, поэтому правка работает без перезапуска контейнеров (см. `setting.md`).

Порядок именно такой: job обязан сорваться позже, чем сдался сам агент, но раньше,
чем строку сочтут брошенной, иначе второй воркер возьмёт ещё живую работу. Нарушение
лестницы страница показывает предупреждением (`task_setting_timeout_ladder_problem`), но не
запрещает: поднять три значения разом одним запросом нельзя. Менеджер и
разработчик держат один и тот же потолок: оба ждут ответа живой оболочки, и делать
разработчику меньший запас незачем — реализация подзадачи идёт дольше, чем написание
плана, а не быстрее.

`metadata.max_actions` — сколько действий **с захватом** поставить в очередь за запуск
(по умолчанию 1). Подметальщики (скан багов, финализация) в этот бюджет не входят и
ставятся до него: захватывать им нечего, их сдерживает только single-flight. Считайся
они за действие — при `max_actions=1` каждый тик уходил бы на скан, а задачи стояли бы.
В stdout уходит JSON `{"queued": N, "reclaimed": N, "jobs": [...]}` — его забирает
исполнитель кронджобов.

### Дубликаты

У действий с захватом дубликатов не бывает по построению: строка уже уведена в переходное
состояние (`planning`, `reviewing`, `developing`, `qa_pending`), и следующий тик её не увидит.
Умер воркер — блокировку вернёт `task_claim_locks_reclaim()` по таймауту.

У двух действий захватывать нечего — они ищут работу уже внутри воркера: скан багов и
финализация. На них стоит redis-ключ single-flight (`SET NX EX`, см.
`task_worker_flight_acquire`): пока прошлый job не закончился, тик не поставит второй такой же.

Очередь — `default`, та же, что поднимает `main_uvicorn` (`redis_queue_init(['default'])`)
и разбирает контейнер `worker_task` из docker-compose; отдельная очередь потребовала бы ещё
одного процесса. Состояние очереди видно в rq-dashboard (:9181, локально :9182).

> Событие в Cronicle заводится вручную через UI и **своё на каждой инсталляции** —
> на проде придётся создать отдельно. Локально это `task_orchestrator` (id
> `etaskorch1`), плагин `urlplug`, `timing: {}` — то есть каждую минуту;
> `max_children: 1`, поэтому наложившийся запуск Cronicle просто пропустит.

### Кто планирует: тип задачи → роль карточки

Планирует владелец вкладки, на которой задача живёт (`src/project/task/task_role.py`):

| Тип задачи (`project_task_type.name`) | Планирует | Оболочка `claude_shell_call` |
|---|---|---|
| `plan`, `research`, тип не задан, неизвестный тип | Менеджер | `manager` |
| `dev` | Разработчик | `developer` |
| `bug`, `test` | QA | `qa` |

Подзадачи утверждённого плана этому распределению **не подчиняются**: их всегда делает
Developer, а проверяет QA. Роль здесь — только про корневую задачу.

Условие отбора строится по **именам** типов (`task_role_type_sql`), а не по id: id
зависят от установки, имена — часть контракта (то же имя уходит в промпт менеджера
переменной `task_type`). Роли по умолчанию (`manager`) достаётся ещё и всё, чего нет в
карте: задача без типа (`ON DELETE SET NULL`) и тип, который добавили в таблицу, но не в
`TASK_ROLE_TYPES` — иначе такая задача выпала бы из конвейера совсем.

**Планирование захватывается только карточкой своего проекта, и только живой.**
`_action_claim` в начале тика зовёт `task_role_shell_live_by_project()` — он читает
`ai_claude_session_registry` (статус `active`/`closing`, `last_seen_at` свежее
настройки `timeout_ping_stale`) и раскладывает живые роли по проектам:
`{project_id: [role]}`. Проект оболочки определяется каталогом запуска (`work_dir`
реестра, нормализованный без хвостового слэша) — тем же правилом, каким `/admin/team`
разносит сессии по блокам проектов. Роль без карточки `(project_id, role)` в
`project_team` живой не считается: захват работы, которую ни одна карточка не
показывает, был бы невидим человеку.

Дальше `task_role_project_type_sql(roles_by_project)` строит условие отбора «свой
проект **и** свой тип»:

```sql
(project_id = 2 AND <типы ролей проекта 2>)
OR ((project_id IS NULL OR project_id = 0) AND <типы всех живых ролей>)
```

Менеджер проекта A физически не может забрать задачу проекта B: её `project_id` не
попадает ни в одну ветку условия. Задача **без** проекта — ничья, её берёт любая живая
роль подходящего типа; иначе задачи, заведённые мимо проекта (через API, тестами, до
появления колонки `project_id`), не выполнил бы никто. Если живых оболочек нет вовсе,
условие вырождается в `1 = 0`: захватить задачу для погашенной карточки нельзя, прогон
сорвался бы на первом же `claude_shell_call` и задача ушла бы в `failed` — вместо этого
она остаётся видимой очередью на своей карточке. Свежесть считается в Python, а не через
`NOW()`: `last_seen_at` пишется временем приложения.

Developer отбирается тем же правилом, но по другому условию —
`task_role_project_sql(roles_by_project, 'developer')` в
`task_claim_subtask_developable`. Разница с корневой задачей в том, что тип здесь ни при
чём: подзадачи утверждённого плана всегда делает Developer и проверяет QA, поэтому
`task_role_project_type_sql` (проект **и** тип) не годится — остаётся только вопрос
«жива ли карточка разработчика в проекте подзадачи». Не жива — подзадачу не берём: захват
сжёг бы попытку из отведённых `timeout_attempt_max` на прогоне, который заведомо сорвётся.
Проект подзадача наследует от родителя при разбиении (`task_state_subtasks_create`).

`plan_split` от оболочек не зависит и идёт всегда: подзадачи создаёт сам воркер, и его
захват проектом **не** ограничен. Захват QA (`task_claim_subtask_qa`) ограничен —
`task_role_project_sql(roles_by_project, 'qa')`, роль `qa` вместо `developer`: проверять
обязана оболочка того же проекта, что и делала работу.

Роль решается при захвате (`task_role_of_task`) и едет в сообщении очереди
(`action['role']`), потому что человек мог поменять тип задачи, пока сообщение лежало в
Redis: планировать должна та роль, которая задачу взяла.

**Адрес оболочки — пара «роль + каталог».** Роль отвечает «кто планирует», каталог — «в
чьём проекте»: карточки заведены на каждый проект отдельно, и менеджеры разных проектов
называются одинаково, поэтому одной роли для адресации мало. Каталог берётся из **задачи**,
а не из сообщения очереди (`task_role_project_work_dir(task['project_id'])` в
`_manager_plan_write`): проект у задачи может смениться, а сообщение помнит только момент
захвата. Обе половины идут в `task_agent_manager_plan(task, revise, role, work_dir)`:

- `team_session_restart_role(role, work_dir)` — перезапуск дочернего Claude Code только в
  своей оболочке; без каталога он снёс бы контекст менеджера соседнего проекта, который
  прямо сейчас работает над своей задачей;
- переменные workflow `task_shell_role` и `task_shell_work_dir` — по ним семь шагов #55
  адресуют `claude_shell_call` (`inputs_map: {"role": …, "work_dir": …}`; раньше в шагах
  стояла константа `_const_manager`). Внутри инструмента каталог сужает выборку сессии:
  `_session_find` добавляет `AND TRIM(TRAILING '/' FROM work_dir) = %s`.

Пустой каталог (у задачи нет проекта либо у проекта не задан `work_dir`) — не ошибка:
адресация деградирует до прежней, только по роли.

Тот же фильтр по типу применяет `team_queue._planner_rows(role)` — очередь на карточках
`/admin/team`. Живой оболочки там, в отличие от захвата, не требуется: карточка для того
и показывает очередь, чтобы было видно, что ждёт погашенную роль.

### Захват работы

Запуски крона могут накладываться, поэтому захват — условный `UPDATE` с проверкой
`rowcount`, а не `SELECT ... FOR UPDATE`:

```sql
UPDATE project_task SET pipeline_state = 'planning', pipeline_locked_at = NOW(), pipeline_locked_by = %s
 WHERE id = %s
   AND COALESCE(JSON_LENGTH(JSON_EXTRACT(IF(JSON_VALID(pipeline_plan), pipeline_plan, '{}'), '$.subtasks')), 0) = 0
   AND (pipeline_state IS NULL OR pipeline_state = 'new')
```

Критерий — **ноль подзадач**, а не `pipeline_plan = ''`: сид и старые записи держат
заглушку `{"plan_text": "", "subtasks": []}`, и по сравнению с пустой строкой такая
задача навсегда выпадала из конвейера, хотя планировать её как раз и надо. Битый JSON
приравнивается к пустому плану (`JSON_VALID`, иначе `JSON_EXTRACT` роняет весь запрос).

`rowcount == 0` → строку увёл параллельный воркер, тихо пропускаем. Условие отбора
повторяется в `UPDATE` — иначе два тика утащили бы одну задачу. Общий код —
`task_claim._task_claim()`, отбор без плана — `task_claim_task_unplanned()`.

**Захват на пересмотр** — `task_claim_task_review()`, `state_to='reviewing'`: состояние не
меняется, задача берётся **только блокировкой**. Прецедент уже есть у
`task_claim_subtask('qa_pending', 'qa_pending', ...)`. Раз перехода нет, единственной
защитой от второго воркера остаётся сама блокировка, поэтому
`pipeline_locked_at IS NULL OR pipeline_locked_by = ''` обязательна прямо в `WHERE`.

В `TASK_CLAIM_STATE_RECLAIM` для `reviewing` стоит `reviewing`, а не `new`: протухшая блокировка
просто снимается и задача снова ждёт пересмотра. Увести её в `new`, как `planning`,
нельзя — план у неё есть, `task_claim_task_unplanned` её не подберёт, и она залипнет
навсегда.

`_claim_manager_review` стоит в `_action_claim` **первым** среди задач, до
`_claim_manager_plan`: на другом конце этого действия живой человек, который нажал кнопку
и ждёт.

Если воркер умрёт посреди перехода, строка залипнет в переходном состоянии
(`planning` / `developing`). `task_claim_locks_reclaim()` в начале каждого тика
возвращает такие строки в работу по `locked_at < NOW() - INTERVAL <timeout_task_lock> SECOND`.

Тик кладёт в сообщение только `kind` и id строки, а не саму строку: пока сообщение лежит
в очереди, состояние могло измениться, поэтому воркер перечитывает её через
`task_state_task_get` / `task_state_subtask_get` и тихо выходит, если строки уже нет.

### Остановка человеком (флажок «в разработку»)

Рядом с человеческим статусом в колонке прогресса на вкладке «Разработка» стоит флажок
«в разработку» — видна у задач в статусах «В работе», «В очереди» и «Ожидает», то есть
пока задача из конвейера не вышла. Галка стоит — задача в работе; снятая галка её
останавливает, возвращённая (или возвращённый флажок фазы) продолжает. Код —
`src/project/task/task_stop.py`.

**Запрет живёт в `metadata.stopped`, а не в человеческом `status`.** Отбор работы на
`status` не смотрит вовсе, он ходит по `pipeline_state`, и «Ожидает», выставленное
руками, следующий тик перебил бы через секунду. Держится запрет в четырёх точках:

1. `metadata.stopped = true` — сама пометка (`task_metadata_stop_sql`);
2. гейт в `_task_claim`: `task_metadata_stop_free_sql()` подмешивается в `where` **один
   раз на все шаги конвейера** — захват один, и это единственное место, где пометку
   нельзя забыть проверить. Проверяется и родитель: у строки в `processing` своей работы
   нет, вся она идёт у подзадач плана;
3. `task_state_kanban_sql` держит статус остановленной строки — тем же приёмом, что и у
   `cancelled`. Иначе прогон, доигрывающий свой конец в воркере, вернул бы задачу в
   «В работе» уже после остановки;
4. строки «в полёте» возвращаются картами реклейма — `TASK_CLAIM_STATE_RECLAIM` у
   корневых, `TASK_CLAIM_SUBTASK_STATE_RECLAIM` у подзадач. Карты разные не для красоты:
   `testing` у корневой задачи — фаза «на проверке», а не захваченная работа, и вернуть
   её в `qa_pending` нельзя.

Порядок шагов в `task_stop_apply` обратному не подлежит: пометка → возврат строк →
перезапуск оболочек → отчёт. Пока пометка не легла, тик вправе забрать строку заново, и
остановка обернулась бы перезапуском.

Перезапускаются **только те роли, что нашлись среди строк этой задачи в полёте**:
карточка одна на роль и проект, и перезапуск «на всякий случай» снёс бы ход соседней
задачи.

Флажок фазы снимается тот, который человек на этой вкладке и видит: «в разработку» у
задачи менеджера, «в тестирование» у задачи разработчика. Иначе снятая остановка тут же
сработала бы повторно — флажок увёл бы задачу дальше по конвейеру сам.

Снятие остановки (`task_stop_clear`) ничего не запускает: убирает запрет, а работу отдаст
ближайший тик оркестратора по тому же `pipeline_state`, куда её вернула остановка.
Зовётся из трёх мест — `/pipeline/resume`, `/pipeline/start`, `/pipeline/retry` — и из
обработчика флажков `POST /task/{id}/metadata`.

> У подзадач флажка фазы нет вовсе, поэтому «продолжить» им доступно только возвратом
> того же флажка «в разработку» — он показывается и у строк плана.

Обе записи попадают в отчёт задачи со штампом времени; подзадачам, у которых сняли
работу, пишется своя строка со ссылкой на остановленную задачу.

### Технические повторы: агент не ответил

Сорвавшийся прогон и несошедшаяся работа — разные вещи. QA вернул замечания, разработчик
отдал `ok: false` — работа состоялась, просто не сошлась: круг закрыт, `pipeline_attempt_count`
вырос, следующий круг идёт с этим замечанием на входе. Агент не ответил вовсе (таймаут
оболочки, мёртвый Claude Code, менеджер с пустым списком подзадач) — работы не было, жечь
за это круг не за что.

Такой прогон повторяется: `src/project/task/task_retry.py`, потолок — настройка `timeout_retry_max` (умолчание 3).

```
прогон сорвался
  -> task_retry_take()   счётчик +1 в metadata.retry (считает MySQL внутри UPDATE)
  -> отчёт задачи        «Менеджер не вернул результат (…). Перезапуск оболочки и повтор 1 из 3»
  -> team_session_restart_role(role, work_dir)   гасим и поднимаем оболочку заново
  -> строка обратно в отбор  задача -> task_state_task_requeue, подзадача -> task_state_subtask_set
```

Порядок именно такой. Умри воркер на перезапуске — строка останется заблокированной в
переходном состоянии, и `task_claim_locks_reclaim()` вернёт её ровно туда же, куда вернули
бы мы. Отпусти мы её первой — задачу успел бы забрать соседний воркер и отправить в
оболочку, которую в этот момент гасим.

Повторяем не внутри job'а, а следующим тиком: второй поход к агенту в ту же job не влезает
(`timeout_worker_job` 3900s против часа на прогон), и rq убил бы его посреди работы.
Состояния возврата — те же, что у брошенной блокировки: планирование → `new`, пересмотр →
`reviewing`, разработка → `planned`, проверка → `qa_pending`.

Счётчиков в `metadata.retry` два. `count` — серия подряд, обнуляется первым же дошедшим
ответом (`task_retry_clear`), по ней решается, повторять ли ещё. `total` — за всё время
строки, не обнуляется никогда: это и есть статистика, по ней видно, каким задачам агенты
даются тяжело. В таблице `/admin/task` `total` показан янтарным значком `↻N` рядом с чипсом
состояния, подсказка раскрывает серию, роль, время и причину последнего срыва.

Исчерпанные повторы: задача уходит в `failed` (в тексте ошибки — сколько прогонов сорвалось
подряд), подзадача — обычным `task_state_subtask_fail`, то есть в `failed_qa` или `blocked`.

Подзадаче `pipeline_error` при срыве **не** пишем: разработчик читает это поле как замечание
QA, а «оболочка не ответила» замечанием не является и сбило бы его со следующего круга. След
остаётся в отчёте задачи, в `metadata.retry` и строкой `project_task_attempt`
(`status='error'`) — по ней видно, сколько прогон продержался.

Потолки — настройки, а не константы: `timeout_attempt_max` (3), `timeout_retry_max` (3),
`timeout_task_lock` (4200s). Реестр и редактор — `src/project/task/task_setting_timeout.py` и
блок «⏱ Таймауты» на карточке `/admin/team`.

## 5. Схема БД

`project_task` — глобальная задача:

| Колонка | Назначение |
|---------|-----------|
| `status` | человеческий kanban-статус |
| `parent_id` | родительская задача, `NULL` = корневая; FK на саму `project_task`, `ON DELETE CASCADE` |
| `goals` | JSON `[{text, done}]` |
| `report` | отчёт о выполненных работах |
| `position` | порядок **внутри родителя** (у корневых — внутри проекта) |
| `pipeline_state` | стадия конвейера, `NULL` = вне его |
| `pipeline_plan` | JSON `{plan_text, subtasks, goals}` от Manager |
| `pipeline_error` | причина `failed` (у подзадачи — ошибка последнего круга) |
| `pipeline_attempt_count` | сколько кругов Developer → QA прошла подзадача; у корневой всегда 0 |
| `pipeline_from_plan` | `1` = строку создало разложение плана родителя, `0` = задачу завёл человек |
| `pipeline_locked_at` / `pipeline_locked_by` | оптимистичная блокировка |
| `trace_meta` | след интеграции: `{domain, error_hash, ...}` у баг-задач, по нему идёт дедуп |
| `metadata` | произвольные данные задачи, JSON `{ключ: значение}`; см. ниже |

### `metadata` — произвольные данные задачи

Мешок «ключ → значение» для того, под что заводить колонку рано: пометки агентов,
ссылки на внешние сущности, счётчики. Схема о составе ничего не знает — контракт
держит код, который пишет конкретный ключ, поэтому читатель всегда готов к отсутствию
ключа. Пустое значение — всегда `{}`, а не `None` (у задач, заведённых до появления
поля, в колонке `NULL`).

С `trace_meta` не пересекается: тот — привязка задачи к источнику ошибки, его трогает
только `task_bug_create`/`task_bug_dedup`.

Работа из кода — `src/project/task/task_metadata.py`:

| Функция | Действие |
|---------|----------|
| `task_metadata_get(task_id)` | прочитать целиком → `dict` |
| `task_metadata_parse(value)` | разобрать колонку уже прочитанной строки (без похода в БД) |
| `task_metadata_row_apply(row)` | строка задачи → `dict` для ответа API с разобранным `metadata` |
| `task_metadata_set(task_id, data)` | записать целиком, затерев прежнее; `None`/`{}` → `NULL` |
| `task_metadata_update(task_id, patch)` | слить патч, чужие ключи сохранив; значение `None` удаляет ключ |

Точечная правка идёт через `task_metadata_update` — MySQL сливает патч
(`JSON_MERGE_PATCH`) одним `UPDATE`. Читать-править-писать на стороне Python нельзя:
над одной задачей одновременно работают оркестратор, воркеры и страница задач, и
второй писатель затёр бы ключ первого.

Известные ключи:

| Ключ | Кто пишет | Значение |
|------|-----------|----------|
| `to_development` | страница `/admin/task`, флажок «в разработку»; снимает `task_state_plan_to_development` | `true` — план утверждать не надо: в `plan_approval` задача сама сменит тип `plan` → `dev` и уйдёт в `approved`. Ключа нет = выключено (отдельное `false` не требуется) |
| `to_testing` | страница `/admin/task`, флажок «в тестирование»; читает `task_state_dev_to_testing` | Хранится наизнанку: ключа нет = пометка стоит (умолчание), снятый флажок пишется явным `false`. Когда все подзадачи упёрлись в `qa_pending`, задача сама сменит тип `dev` → `test` и уйдёт в `testing`. Не одноразовая |
| `to_planning` | страница `/admin/task`, флажок «в планирование», и окошко фиксера; читает захват (`task_metadata_plan_free_sql` в `task_claim_task_unplanned`), стирает кнопка «В конвейер» | Хранится наизнанку, как `to_testing`: ключа нет = задача идёт к менеджеру за планом, снятый флажок пишется явным `false`. Снятая пометка убирает задачу только из отбора на написание плана; уже написанный план и работу дальше по конвейеру не трогает. Не одноразовая |
| `branch` | `task_pipeline._subtask_branch_save` из отчёта разработчика | ветка подзадачи, по умолчанию `feature/task_<id>`. Только у подзадач: у родителя своего кода нет |
| `mr_url` | там же | ссылка на merge request подзадачи; в ячейке рисуется значком `MR #id` (только `http(s)`) |
| `retry` | `task_retry.py` | `{count, total, role, error, at}` — сорвавшиеся прогоны строки: `count` серия подряд, `total` за всё время. См. «Технические повторы» |
| `stopped` | снятый флажок «в разработку» на странице задач (`task_stop.py`) | `true` — работу над строкой запретил человек. Ключа нет = разрешено. См. «Остановка человеком» |

Единица работы Developer/QA — строка этой же таблицы с непустым `parent_id`: отдельной
таблицы подзадач у конвейера нет, `pipeline_state` там принимает детские значения
(`planned` … `blocked`).

`project_task_attempt` — история попыток: `attempt_no`, `role`, `status`, `output`, `error`,
`duration_ms`; `task_id` — та самая подзадача, FK на `project_task` с `ON DELETE CASCADE`.

`project_task_plan_revision` — история версий плана, append-only: `revision_no`,
`plan_text`, `goals`, `subtasks`, `author_kind` (`manager`|`user`), `author_id`,
`author_name`, `created_at`; FK на `project_task` с `ON DELETE CASCADE`.

- **Снимок нового состояния, а не предыдущего.** Так у каждой строки честные автор и
  время («эту версию написал такой-то тогда-то»); при архивации-перед-перезаписью время
  означало бы момент вытеснения. Следствие: самая свежая ревизия **и есть** текущий план.
- Цели и подзадачи снимаются вместе с планом: чипс подменяет и то, и то, а
  восстановление без подзадач дало бы план, который нечем разложить.
- `revision_no` считается на вставке (`INSERT ... SELECT COALESCE(MAX(revision_no),0)+1`
  из той же таблицы — MySQL это разрешает, запрет 1093 касается `UPDATE`/`DELETE`).
  `AUTO_INCREMENT` не годится: он общий на все задачи. Настоящая защита от гонки
  человека и воркера — `UNIQUE (task_id, revision_no)`, при её срабатывании вставка
  повторяется ровно один раз.

Все таблицы конвейера — runtime-данные, **в seed не добавлять**. Схема живёт только в
`migrations/0001.sql`.

## 6. API

| Метод | Путь | Права | Действие |
|-------|------|-------|----------|
| `GET` | `/tasks` | `PLANNING_VIEW` | все задачи |
| `GET` | `/tasks/{project_id}` | `PLANNING_VIEW` | задачи проекта |
| `POST` | `/tasks/{project_id}` | `PLANNING_CREATE` | создать; `parent_id` делает задачу подзадачей; `metadata` — объект |
| `PUT` | `/task/{id}` | `PLANNING_CREATE` | обновить (частично); `plan_text` правит план, не трогая `subtasks`; `parent_id` переносит по дереву, `null` — в корень; `metadata` заменяется целиком (объект или `null`) |
| `POST` | `/task/{id}/metadata` | `PLANNING_CREATE` | `{patch: {…}}` — слить патч в `metadata`, чужие ключи сохранив; значение `null` удаляет ключ |
| `DELETE` | `/task/{id}` | `PLANNING_CREATE` | удалить **вместе со всей веткой** (каскад по `parent_id`) |
| `POST` | `/task/ai-generate` | `PLANNING_CREATE` | сгенерировать название/описание/цели |
| `GET` | `/task/{id}/pipeline` | `PLANNING_VIEW` | состояние + цели из плана + подзадачи + попытки |
| `POST` | `/task/{id}/pipeline/start` | `PLANNING_UPDATE` | `NULL` → `new` (вернуть отклонённую задачу в работу) |
| `POST` | `/task/{id}/pipeline/approve` | `PLANNING_UPDATE` | `plan_approval` → `approved` |
| `POST` | `/task/{id}/pipeline/reject` | `PLANNING_UPDATE` | `plan_approval` → `NULL` |
| `POST` | `/task/{id}/pipeline/review` | `PLANNING_UPDATE` | «Обновить план»: `NULL`/`plan_approval`/`done`/`failed` → `reviewing` |
| `POST` | `/task/{id}/pipeline/stop` | `PLANNING_UPDATE` | снятый флажок «в разработку»: остановить задачу вместе с подзадачами. `{ok, task_id, released: [{id, state_from, state_to}], roles: [...], task}` |
| `POST` | `/task/{id}/pipeline/resume` | `PLANNING_UPDATE` | кнопка ▶: снять остановку. `{ok, resumed, task}`; `resumed=false` — задача и не была остановлена |
| `POST` | `/task/{id}/worktree/merge` | `PLANNING_UPDATE` | кнопка «mr2master&rm_worktree»: влить ветку подзадачи в главную и снять её рабочий каталог. Только у подзадачи; слияние локальное, без `push`. Отказ git → `400` с его текстом |
| `GET` | `/task/{id}/plan/revisions` | `PLANNING_VIEW` | `{revisions: [...], total}` по убыванию; `?limit=` (по умолчанию `TASK_REVISION_LIMIT = 20`, потолок 500) |
| `GET` | `/task/{id}/plan/revision/{n}` | `PLANNING_VIEW` | одна ревизия целиком |
| `POST` | `/task/{id}/plan/revision/{n}/restore` | `PLANNING_UPDATE` | вернуть план из ревизии |

CRUD — `project_task.py`, конвейер — `project_task_pipeline.py`. Каждый переход сверяет
текущее состояние прямо в `UPDATE`; несовпадение → `409`, чтобы двойной клик не
проскочил гонку.

`review` и `restore` проходят общую проверку `_plan_editable_task()`: `404` — задачи нет;
`409` — состояние не из `_PLAN_EDITABLE_STATES` либо по плану ещё выполняются подзадачи;
`400` — плана нет вовсе (это работа кнопки «В конвейер»). Второе `409` — страховка от
рассинхрона: состояние задачи и состояния её подзадач ведут разные шаги конвейера, и
подменить план под работающими подзадачами хуже, чем лишний раз отказать. Тексты причин
русские и доезжают до пользователя: `taskFetch` вынимает `detail` в `e.message`, а UI
показывает его в `alert`.

`review` **удаляет подзадачи старого плана** — и делает это после захвата состояния, а не
до: проиграв гонку двойному клику, мы бы уже снесли чужую работу. Удаление обязательно,
потому что `_run_plan_split` только добавляет строки, и новый план лёг бы поверх старого.

`restore` пишет `plan_text` + `subtasks` ревизии в `pipeline_plan`, цели **вливает**
(`task_plan_goals_merge`, а не перезаписью — человек мог отметить сделанные цели уже
после той ревизии), создаёт новую ревизию с автором-пользователем и **не трогает**
`pipeline_state`: восстановление — правка плана, а не переход конвейера. В append-only
журнале «отменить» значит «дописать», поэтому откат виден в истории, а не подменяет её.
Ревизия ищется парой `(task_id, revision_no)` — иначе ссылка на чужую ревизию подменила
бы план не той задачи.

## 7. Правила для ролей

Каждая роль живёт в своём файле: Manager — `src/project/task/task_agent_manager.py`,
Developer — `src/project/task/task_agent_developer.py`, QA — `src/project/task/task_agent_qa.py`.
Оркестратор читает только документированные ключи возврата и ничего не знает о том, как
результат получен: роль можно переписать целиком, не трогая машину состояний.

```python
async def task_agent_manager_plan(task, revise: bool = False, role: str = 'manager') -> {'plan_text': str, 'subtasks': [{'title','description'}], 'goals': [{'text','done'}]}
async def task_agent_developer_run(task, subtask, last_error='', role='developer', work_dir='') -> {'ok': bool, 'output': str, 'error': str}
async def task_agent_qa_run(task, subtask, last_error='', role='qa', work_dir='') -> {'ok': bool, 'output': str, 'error': str}
```

Общее для всех трёх: исключение внутри роли — не падение тика. Оркестратор ловит его,
пишет строку в `project_task_attempt` со `status='error'` и двигает состояние по ветке провала.

### Manager — живой Claude Code в shell-оболочке

**Отвечает за:** разобрать описание задачи, найти в проекте относящиеся к ней места и
паттерны, и написать по разведке детальный план, список подзадач и список целей.

Реализован обычным агентом движка: агент **`task_plan_manager`** («Task Plan Manager»,
группа `Проекты/Task`), workflow **#55** — 28 шагов: разведка, план, цели, разбиение и
три судейских цикла
(см. §7.1). Промпт плана просит `plan_text` из 5–15 нумерованных шагов; подзадачи
пишет отдельный шаг разбиения — уже после целей, и решение «дробить или нет»
принимает сам менеджер.
Правится через `/admin/agent` — код при смене формулировок трогать не нужно.

**LLM в workflow больше нет ни на одном шаге.** Планирует не модель, а настоящий
Claude Code — тот, что разработчик держит открытым в терминале и который виден
карточкой роли `manager` на `/admin/team`. Каждый содержательный шаг — это
`tool_invoke claude_shell_call`: инструмент кладёт сообщение в `ai_claude_session`,
ждёт подтверждения доставки, потом ответа, и отдаёт разобранный JSON
(см. `claude_shell.md`). Смысл ровно в этом: менеджеру нужен доступ к коду проекта,
которого у LLM-шага нет, и он же отвечает за судейские проходы — тем же инструментом,
просто другим промптом.

Ключевая деталь: менеджера зовёт **воркер**, отдельным процессом, а не внутри uvicorn,
поэтому job в `task_worker.py` сам поднимает `queue_init([... 'ai_framework_model'])` и
`ai_thread_framework_run([AiFrameworkAgent()])`. Без этого шага workflow отправит
модель в очередь, которую некому разобрать, и job просто повиснет до таймаута.
`timeout_manager_run` (3600s) — верхняя граница на весь workflow; часовой потолок берётся
из того, что живой агент думает минутами, а обращений за прогон до тринадцати (разведка
плюс три судейских цикла: план, цели, разбиение). Она намеренно
ниже `timeout_worker_job` и `timeout_task_lock`, иначе прогон переживал бы свою же
блокировку и задачу успел бы подобрать второй воркер.

Инструменты передаются в модель картой из таблицы `tool` (`_tools_load()`), а не
пустым словарём: шаги счётчиков вызывают `counter_increment` как обычный инструмент,
и без карты workflow падает на первом же цикле («Инструмент не найден»).

**Прогон начинается с перезапуска оболочки.** Перед созданием модели
`task_agent_manager_plan` зовёт `team_session_restart_role(role, work_dir)` — роль пришла
из захвата (см. «Кто планирует»), для задач планирования и исследования это `manager`,
каталог — из проекта задачи, иначе перезапуск попал бы в оболочку соседнего проекта;
дочерний Claude Code
гасится и поднимается заново, то есть разговор предыдущей задачи не остаётся в контексте
следующей. Перезапуск ровно один на прогон и до первого шага — шаги workflow #55 продолжают
один и тот же разговор, и перезапуск между ними снёс бы наполовину готовый план. Через ту же
функцию проходят и `manager_plan`, и `manager_review`: оба ведут в `_manager_plan_write`.
Ожидание (подтверждение маркера, пауза, готовность) добавляет к прогону до ~250с и в
`timeout_manager_run` не входит — механика и таймауты описаны в `claude_shell.md` §4.1.
Живой оболочки может не быть — тогда перезапуск молча пропускается, и шаг упирается в
обычный `no_session`. Тем же вызовом, но со своей ролью, начинают прогон QA (безусловно)
и Developer — у последнего перезапуск стоит под условием «задача сменилась», см. раздел
Developer.

- Срабатывает на **любой** задаче, у которой в плане нет подзадач — `status` при отборе
  не смотрится; заглушка `{"plan_text": "", "subtasks": []}` считается отсутствием плана
- Возвращает `plan_text`, `subtasks` **и** `goals` — первое идёт человеку на утверждение,
  второе после утверждения материализуется в детей задачи (`pipeline_from_plan = 1`), третье сразу
  дописывается в `project_task.goals`
- Пустой `subtasks` = провал: задача уходит в `failed`, а не в бесконечное планирование.
  Ответ агента не «чинится» и не достраивается — плохой план должен быть виден
- Дробить или не дробить — решает менеджер, а не промпт. Отдельный шаг разбиения (см. §7.1)
  сначала спрашивает, делится ли работа вообще, и «не делится» у него выглядит как **одна**
  подзадача на всю задачу. Пустым список не бывает никогда: конвейер гоняет Developer→QA
  только по детям, и задача без единой подзадачи просто не поехала бы дальше
- Подзадача должна быть достаточно мелкой, чтобы Developer закрыл её за один заход, и
  достаточно самостоятельной, чтобы QA мог проверить её отдельно
- **У каждой подзадачи свои план и цели.** Шаг разбиения возвращает объекты
  `{title, description, plan, goals}`, и `task_state_subtasks_create` кладёт `plan` в
  `pipeline_plan` подзадачи (тем же `task_plan_serialize`, с пустым списком детей), а
  `goals` — в её `goals`. Родительский план на трёх разных подзадачах ничего не говорит
  исполнителю, поэтому судья разбиения считает пустой или одинаковый у соседей `plan`
  критической ошибкой. Пустые поля родительскими **не** подставляются: пусто — видимый
  сигнал, что разбиение недоработано, а копия плана родителя выглядела бы как настоящий
  план подзадачи
- **Не материализует подзадачи сам** — только после утверждения человеком

#### Отдельный шаг под JSON

Общее правило всех трёх workflow (#55, #56, #57): **содержательный промпт не просит
JSON**. Агента спрашивают по-человечески и получают текст, а машинный вид забирают
следующей парой шагов — `Промпт JSON: …` (`variable_conversion`, короткий текст «верни
тот же самый ответ в машинном виде, ничего не придумывая заново» плюс схема) и
`Ответ JSON: …` (`tool_invoke claude_shell_call` с `_const_600`).

Так сделано потому, что просьба про формат в конце большого промпта конкурирует с самой
работой: агент либо забывает схему, либо отдаёт текст и JSON вместе, и разбор ломается.
Один шаг — одна задача: сначала подумать, потом записать. Заодно повтор при неразобранном
ответе стал дешёвым — переспрашивают только маленький шаг, а не весь ход заново.

Шаги «Счётчик напоминаний» / «Лимит напоминаний» остались, но работают уже на этой паре:
пустой `payload_json` возвращает прогон на `Промпт JSON`, и так до `max_parse_retries`,
после чего workflow уходит в свою ветку «агент недоступен».

#### 7.1 Workflow #55: разведка → план → судья → цели → судья → разбиение → судья

Каждый артефакт проходит через критика, и все три цикла устроены одинаково — той же
схемой, что `research_loop` (#28) и `design_system` (#35), поэтому движок править
не пришлось. Промпт и вызов разнесены по разным шагам: `variable_conversion`
собирает текст (с ветками `%if plan_critique%` и прочими), `tool_invoke` его

**Ответ и его машинный вид — тоже разные шаги** (см. «Отдельный шаг под JSON» ниже),

Все семь содержательных обращений к менеджеру (423, 406, 410, 413, 417, 425, 429) идут с `timeout: _const_600`.
Раньше на судейских шагах стояло 420с, и настоящий ход судьи в них не укладывался:
инструмент отпускал строку, ход продолжался, а следующий шаг упирался в занятого
менеджера. Окно `timeout_shell_busy` подняли из-за того же (см. `claude_shell.md` §5).

**Шаг разведки (422/423) идёт до планирования и плана не пишет.** Менеджер сначала
разбирает описание задачи на теги — подсистемы, файлы, технологии, действия, — по тегам
определяет тематику, ищет в проекте похожие места и уже используемые паттерны (с путями
к файлам) и формулирует вопросы, ответы на которые нужны для конкретного плана. Ответ —
`{"task_recon": …, "plan_questions": …}`. Смысл в том, что живой Claude Code до этого шага
проект не читал: без разведки первый же план получается «по описанию», общими словами,
и весь судейский цикл уходит на то, чтобы это чинить.

Направление вопросов задаёт **тип задачи**. `task_agent_manager_plan` читает
`project_task_type` по `task.task_type_id` (`_task_type_get`) и кладёт в workflow
`task_type` (`dev`, `bug`, `test`, `research`, `plan`) и `task_type_title`. В промпте
422 под каждое имя стоит своя строка вопросов: у `dev` — точка входа, переиспользуемые
паттерны, изменения схемы БД/API/фронтенда; у `bug` — воспроизведение, настоящая
причина, тест на регресс; у `test` — граничные случаи и место тестов; у `research` —
критерии сравнения вариантов; у `plan` — этапы, зависимости, риски. Тип не обязателен
(`ON DELETE SET NULL`): при пустом `task_type` ветка `%else%` даёт «не указан», и
менеджер выбирает направление по смыслу описания.

**Промпты после разведки задачу не пересказывают.** Оболочка менеджера — это одна живая
сессия Claude Code на весь прогон, она stateful и помнит весь свой контекст: и то, что ей
прислали, и то, что она сама сгенерировала. Поэтому полный текст задачи и целей есть
только в промпте 422; 405 говорит «по задаче, которую ты только что разобрал», 409 —
«план ты только что выдал, не пересказывай его», 416 — то же про список целей, 424 и
428 — про план с целями и про подзадачи. Судьям
больше не пересылается проверяемый артефакт — вместо дублирования они получают **новые
вопросы**: архитектура (в какие модули и файлы ложатся шаги, что меняется в схеме БД,
API и фронтенде), паттерны (что переиспользуется из проекта, а что изобретается заново),
пробелы (миграция, права, обработка ошибок, обратная совместимость, тесты) и риски;
у судьи целей — чем именно проверяется каждая цель и что останется
непроверенным; у судьи разбиения — покрытие плана и целей, самостоятельность подзадач и
их порядок. Это и экономит токены, и повышает шанс, что вторая итерация найдёт
что-то новое, а не перепишет то же самое.

Исключение из правила «не дублировать» одно: `%if task_plan_current%` в шаге 405. Этот
текст пришёл из **прошлого прогона**, в контексте текущей сессии его нет, и передать его
нужно целиком.

**Разбиение (424–430) идёт последним и решение о дроблении принимает сам менеджер.**
Раньше подзадачи писались прямо в шаге плана: промпт требовал «2–7 подзадач», то есть
дробление было обязательным независимо от задачи, и решалось оно до того, как появились
цели. Теперь у разбиения свой шаг, свой судья и свой счётчик, а промпт 424 начинается с
вопроса «делится ли эта работа вообще»: если задача атомарна, правильный ответ — **одна**
подзадача на всю задачу, и это не провал, а осознанный вывод. Иначе — 2–7 подзадач в
порядке выполнения, последняя проверочная. Порядок «план → цели → разбиение» тоже не
случаен: подзадачи должны покрывать и шаги плана, и проверяемые результаты, а на шаге
плана целей ещё нет. Судья 428 проверяет ровно это — покрытие плана и целей,
самостоятельность каждой подзадачи и само решение дробить или не дробить.

Ограничители — переменные `max_plan_iterations`, `max_goals_iterations` и
`max_split_iterations` (по умолчанию `2`), привязанные к workflow через
`agent_workflow_variable_workflow`. Без них судья
мог бы гонять генерацию по кругу до `MAX_WORKFLOW_ITERATIONS = 300`.

Форма ответа вложенная (`{"plan": {...}, "subtasks": [...], "goals": [...]}`), а не
плоская: `plan_text`
содержит переводы строк и в JSON-шаблон голой строкой не подставляется, а инструмент
кладёт в переменную уже сериализованный JSON. Подзадачи лежат в корне, а не внутри
`plan`, — их собирает отдельный шаг. `_plan_parse` понимает и старую вложенную форму
(`subtasks` внутри `plan`), и плоскую — так отвечал workflow раньше.

**Провал инструмента виден, а не проглатывается.** Каждый шаг с `claude_shell_call`
мапит `status → manager_status` и `error → manager_error`, и **первым** переходом идёт
`manager_status != answered`. Ветки разные, потому что цена ошибки разная:

| Шаг | При провале → | Почему |
|-----|---------------|--------|
| 423 разведка | 420 | разведка срывается только вместе с менеджером — без него плана всё равно не будет |
| 406 план (и пустой `task_plan_json`) | 420 | планировать нечем, прогон бессмысленный |
| 410 судья плана | 412 | мёртвый судья не должен выбрасывать хороший план — идём дальше по ветке «принято» |
| 413 цели | 421 | потерянные цели не должны выбрасывать готовый план — идём на выход с пустым списком |
| 417 судья целей | 424 | цели уже есть, недоступный критик их не отменяет |
| 425 разбиение (и пустой `task_subtasks_json`) | 431 | план и цели уже готовы — падаем на одну подзадачу «сделать всё целиком», а не в `failed` |
| 429 судья разбиения | 419 | подзадачи уже есть, недоступный критик их не отменяет |

Без этих guard'ов шаг с недоступной оболочкой просто отдавал бы пустую переменную,
и в трейсе оставалось бы «план есть, целей нет» без причины. Шаг 420 отдаёт тот же
конверт с пустыми `subtasks`, поэтому дальше работает обычное правило §7: пустой список
подзадач = провал, задача уходит в `failed`, а причина видна прямо в `plan_text`.

Шаг 413 раньше уходил туда же, в 420, и это было ошибкой: план к этому моменту уже
построен и отсуждён — терять его из-за того, что не доехали цели, нельзя. Поэтому у
провала целей своя ветка 421: она нормализует `task_goals_json` в `[]` и уходит на
обычный выход 419. Задача доезжает до `plan_approval` с планом и без целей — человек
видит план и решает сам, вместо `failed` с пустым конвертом.

По той же причине у разбиения своя ветка 431, а не 420: к шагу 425 план и цели уже
отсуждены, и терять их из-за недоехавших подзадач нельзя. 431 кладёт в
`task_subtasks_json` одну подзадачу «Выполнить задачу целиком» с явной пометкой, что
разбиение не получено, и уходит на выход 419 — работа поедет одним куском, но поедет.
Проверок у этой ветки три, а не две: кроме `manager_status != answered` и `empty`, стоит
явное сравнение `task_subtasks_json == '[]'`. Пустой список у оператора `empty` **не**
считается пустым (`empty` — это отсутствие, `None` или пустая строка), а `'[]'` — как раз
то значение, которое переменная получает на инициализации в шаге 404 и сохраняет, если
инструмент сорвался.

**Режим пересмотра — тот же workflow, без второй копии.** При `revise=True`
`task_agent_manager_plan` кладёт текущий план в переменную `task_plan_current`, а в
промпте шага 405 (перед блоком `%if plan_critique%`) стоит ветка
`%if task_plan_current% … %endif%`: «это режим доработки: опирайся на существующий план,
не переписывай с нуля».

Регистрировать переменную в `agent_workflow_variable` не нужно — `task_title`,
`task_goals`, `task_type`, `task_type_title` тоже передаются только в рантайме. При
обычном планировании там пустая строка, а `ai_workflow_variable_truthy` считает `''`
ложью, так что блок просто не раскрывается.

Шаг 412 «Промпт: цели» отдельной ветки не требует: актуальные цели вместе с правками
человека приезжают в `%task_goals%` на разведке (422), менеджер их помнит, и 412 просто
требует их не потерять.

**Данные workflow живут только в БД** (`data/seeds` в `.gitignore`), поэтому на прод
шаги и переменные едут отдельно — через `/admin/seed`, а не с коммитом. Шаги разведки
422/423, блок разбиения 424–431 с переменной `max_split_iterations` и ветка
`%if task_plan_current%` — как раз такой случай: без перегенерации seed до прода они
не доедут.

#### 7.2 Цели и ревизии

Цели пишутся в `project_task.goals` **сразу** вместе с планом, не дожидаясь утверждения:
подзадачи без утверждения сломали бы конвейер, а цели — просто чек-лист, и человеку
они нужны как раз в момент разбора плана. Запись идёт тем же `UPDATE`, что и план
(`task_state_plan_save(task_id, plan_json, goals_json)`) — иначе могла бы остаться
задача с планом, но без целей.

Слияние **не перезаписывающее** (`task_plan_goals_merge`): цели человека и их флаги
`done` остаются, цели менеджера дописываются в конец. Список человека был для менеджера
входными данными, а не черновиком на замену.

Копия целей остаётся и в самом плане (`{plan_text, subtasks, goals}`) — в `task.goals`
человек их правит, а в плане видно, что предложил агент; без второй копии расхождение
было бы нечем разбирать. `GET /task/{id}/pipeline` отдаёт версию из плана в ключе
`goals`; на странице она больше не дублируется отдельным списком — её показывает режим
просмотра ревизии (§2.2).

**Ревизия = снимок плана.** Строку в `project_task_plan_revision` создаёт только запись
плана; правка одних целей — ни чекбоксом в таблице, ни через `saveGoals` — ревизию **не**
создаёт. Цели живут своей жизнью в `task.goals`, и версионировать каждую поставленную
галочку значило бы утопить историю плана в шуме.

Точки записи ревизий:

| Кто | Где | `author_kind` |
|-----|-----|---------------|
| Manager | `_run_manager_plan` и `_run_manager_review` — сразу после `task_state_plan_save` | `manager` |
| Человек | ветка `if 'plan_text' in data` в `PUT /task/{id}` | `user` + `author_id`/`author_name` |
| Откат | `POST /plan/revision/{n}/restore` | `user` |

Запись идёт **в шагах конвейера, а не внутри `task_state_plan_save`**: там один `UPDATE`
без побочных таблиц, и подмешивать туда историю значило бы прятать её от читателя машины
состояний.

`task_revision_add` молчком **не пишет** в двух случаях: плана нет и подзадач нет
(версионировать нечего); `plan_text` + `goals` совпадают с самой свежей ревизией. Второе
обязательно, потому что форма отправляет `plan_text` при каждом «Сохранить» — без этой
проверки нажатие без правок плодило бы чипсы.

`task_state_plan_save` пишет при `pipeline_state IN ('planning','reviewing')` — иначе
результат пересмотра молча не сохранился бы.

### Свой рабочий каталог на подзадачу

**Одна подзадача — один каталог, одна ветка, свой сервер.** До этого все роли жили в общем
чекауте проекта и переключали в нём ветки. Ломалось это двумя способами сразу: `git checkout -b`
внутри агента менял ветку **у человека**, который в этот момент писал код, а резалась новая
ветка от текущего HEAD — то есть от чужой ветки (`feature/task_492` в этой установке отрезана
от `feature/task_355`, а не от master). Второе — проверка: QA смотрел на общий `:8011`, где в
этот момент мог работать код вообще другой задачи.

Каталог заводит `task_worktree_ensure(repo_dir, subtask_id)` (`src/project/task/task_worktree.py`),
зовётся он из `_subtask_dir` в `task_pipeline.py` при каждом прогоне Developer и QA:

| Что | Значение |
|-----|----------|
| Каталог | `.claude/worktrees/feature_task_<id>` (в `.gitignore`) |
| Ветка | `feature/task_<id>`, отрезана от главной ветки репозитория (`origin/HEAD`; без сети — от локальной) |
| Сервер | `./task_server.sh up <id>` → сервис `uvicorn_task` на `:8013` поверх этого каталога |

**Идемпотентность — условие работы, а не украшение.** Каждая попытка подзадачи заходит сюда
заново, а между попытками каталог никто не убирает: есть каталог — отдаём как есть; нет
каталога, но есть ветка — подключаем ветку (`-B` вместо `-b` снёс бы уже сделанные коммиты).

**Чего в свежем worktree нет.** `git worktree add` выкладывает только отслеживаемые файлы,
поэтому после него идут две обязательные добивки: `submodule update --init` (иначе `py_modules`
пуст и любой импорт падает) и символьные ссылки на игнорируемое общее — `.env`, `.env.local`,
`.venv`, `.claude-shell` и рабочие каталоги `data/` (логи, бэкапы, сиды пишутся в общие папки,
их потом ищет человек). Ссылки, а не копии: `.env` должен быть один на все каталоги, а `.venv`
весит сотни мегабайт.

Список связываемого **не зашит в код** — его спрашивают у самого репозитория:
`git status --porcelain -z --ignored=traditional` отдаёт игнорируемое, причём целиком
игнорируемый каталог приходит одной записью (`.venv/`, а не десять тысяч файлов). Из ответа
берут записи глубиной до двух (`TASK_WORKTREE_SHARED_DEPTH`: `data/` здесь отслеживается, а
игнорируются её дети), выкидывают кеши (`TASK_WORKTREE_SHARED_SKIP` — общий `__pycache__`
означал бы исполнение байткода чужой ветки) и сам `.claude/worktrees` (иначе каталог задачи
лёг бы внутрь себя). У соседнего проекта в игноре другое — `node_modules`, `vendor` — и
свяжется у него именно оно.

**Абсолютные пути.** git пишет в служебные файлы worktree абсолютные пути хоста. Каталог,
созданный из контейнера по пути `/app/...`, на хосте не открылся бы — а живёт в нём хостовый
Claude Code. Поэтому `uvicorn`, `worker_task` и `uvicorn_task` монтируют репозиторий **вторым**
монтированием по своему же хостовому пути — переменная `PROJECT_HOST_DIR` в `.env`.

**Владелец файлов.** Воркер в контейнере — root, репозиторий примонтирован с хоста и
принадлежит человеку. Root-ом git отказывается работать вовсе («dubious ownership»), а что
успел бы создать — создал бы root-овым, и хостовый Claude Code потом не смог бы туда писать.
`_owner_run_as` роняет права до владельца каталога (`user=`/`group=` у `create_subprocess_exec`,
`HOME=/tmp`); созданные симлинки дополнительно `chown`-ятся. На хосте, где uid уже совпадает,
не подменяется ничего.

**Уборка — руками, не конвейером.** `./task_server.sh clean <id>` гасит сервер (только если он
поднят над этим самым каталогом) и снимает каталог; **ветку оставляет** — merge request живёт
дольше каталога. Автоматической уборки на финале нет намеренно: в каталоге может лежать
непринятая работа. Несохранённые правки останавливают уборку — кроме собственных ссылок
конвейера, они правками не считаются. Отличают их **не по именам** (у каждого проекта они
свои), а по тому, что ссылка — симлинк; статус для этого читают с `-uall`, иначе папка из
одних наших ссылок свернулась бы в одну строку и выглядела бы как чужая работа. Сам
`git worktree remove` зовётся с `--force` всегда, и
это не про правки: каталог с подмодулем он иначе не снимает ни при каких условиях («working
trees containing submodules cannot be moved or removed»).

**Что видит агент.** Каталог едет в промпты переменными, код в них не зашит:

| Переменная | Что | Кому |
|------------|-----|------|
| `subtask_work_dir` | каталог подзадачи (пусто — работаем по-старому, в каталоге проекта) | Developer, QA |
| `subtask_branch` | `feature/task_<id>` — из того же кода, что и ветка каталога | Developer, QA |
| `subtask_server_url` | адрес сервера задачи — свой у каждого проекта, см. ниже | QA |

Адрес оболочки (`task_shell_work_dir`) при этом **не меняется**: живой Claude Code остаётся
там, где его нашли по реестру сессий, и просто получает задание перейти в каталог подзадачи.
Менеджер каталога не получает вовсе — планирование к ветке не привязано.

Формулировки промптов правились миграцией `data/migration_manual/2026-08-14_wf5657_worktree.sql`.

### Много проектов на одной машине

Проектов на установке несколько, и карточка обязана работать **в каталоге своего проекта**:
свой репозиторий, свой git, свои worktree, свой docker и свой тест-сервер. Адресом служит
`project.work_dir` — от него пляшет всё: по нему `task_role_shell_live_by_project` находит
живую оболочку роли (роли повторяются в проектах, а каталог уникален), в нём же
`task_worktree_ensure` режет каталог подзадачи.

Что для этого не должно быть общим на установку:

| Что | Где хранится | Почему не общее |
|-----|--------------|-----------------|
| Каталог проекта | `project.work_dir` | у каждого проекта свой репозиторий |
| Главная ветка | спрашивается у репозитория (`origin/HEAD`) | где-то `master`, где-то `main` |
| Список общих файлов | спрашивается у репозитория (`git status --ignored`) | в игноре у каждого своё |
| Адрес тест-сервера | `project.task_server_url` | у каждого проекта свой порт и своя команда запуска |
| Видимость каталога | монтирования docker | контейнер видит только смонтированное |

**Тест-сервер — по конвенции, а не по конфигу.** Наш `uvicorn_task` умеет поднимать только
наше приложение; чужой проект поднимает своё, своим compose. Поэтому конвейер сервер **не
запускает** — это делает живой Claude Code, уже находясь в каталоге проекта. Конвенция: в
корне каждого проекта лежит свой `./task_server.sh` с теми же командами (`up <id>`, `down`,
`status`, `clean <id>`), а в базе хранится только получившийся **адрес**.
`task_role_project_server_url(project_id)` (`src/project/task/task_role.py`) отдаёт
`project.task_server_url`, а если он пуст — `PROJECT_TASK_QA_SERVER_URL` из `.env`, то есть
адрес проекта самой установки. Пусто и там — QA скажет в отчёте, что проверять негде, но на
общий `:8011` не пойдёт: там код главного чекаута, а не ветки. Правится поле в карточке
проекта на `/admin/project` («Тест-сервер задач»).

**Монтирования.** Каталог проекта должен быть виден контейнеру `worker_task` **по тому же
пути, что и на хосте** — git пишет в служебные файлы worktree абсолютные пути. Свой проект
монтируется через `PROJECT_HOST_DIR`, чужие добавляются в `docker-compose.override.yml` (он в
`.gitignore` — там и так лежат отклонения конкретной машины):

```yaml
services:
  worker_task:
    volumes:
      - /home/user/projects/shop:/home/user/projects/shop
```

Забытое монтирование выглядит изнутри контейнера просто как «каталога нет», поэтому
`_subtask_dir` проверяет это отдельно и пишет в лог, что именно смотреть; круг при этом не
падает — работа идёт без изоляции, в каталоге проекта.

### Developer — живой Claude Code в своей оболочке

**Отвечает за:** выполнить одну подзадачу плана.

Устроен так же, как менеджер, и намеренно: агент **`task_dev_developer`** («Task
Developer», группа `Проекты/Task`), workflow **#56** — 12 шагов, разбор → реализация →
самопроверка с возвратом на доработку (см. §7.2). Все содержательные шаги — это
`tool_invoke claude_shell_call`, LLM в workflow нет ни на одном шаге. Промпты правятся
через `/admin/agent`, код при смене формулировок трогать не нужно.

**Оболочка другая, чем у менеджера.** Адрес — пара «роль + каталог»: роль `developer`
(`TASK_DEVELOPER_ROLE`), каталог — из проекта **родительской** задачи
(`task_role_project_work_dir(task['project_id'])` в `_run_developer`). То есть план писал
один живой Claude Code, а выполняет подзадачу другой — тот, что виден карточкой
`developer` своего проекта на `/admin/team`. Обе половины едут в workflow переменными
`task_shell_role` и `task_shell_work_dir`; пустой каталог (задача без проекта) — не
ошибка, адресация деградирует до одной роли.

**Оболочка перезапускается на смене задачи, а не на каждой подзадаче.** У менеджера
`team_session_restart_role(role, work_dir)` стоит безусловно, у разработчика — под
условием: подзадачи одной задачи идут по одному плану и по одному коду, и контекст
предыдущего круга разработчику нужен — иначе каждая подзадача начинается с повторного
изучения тех же файлов. Новая задача — обратный случай: чужой контекст мешает, и оболочку
поднимаем с нуля.

Какой была прошлая задача, `_shell_task_id_last(role, project_id)` смотрит в журнале
попыток: последняя строка `project_task_attempt` с этой ролью → `parent_id` её подзадачи.
Отдельной колонки «последняя задача сессии» нет намеренно — журнал пишется на каждый круг
(`task_state_attempt_log`), а отдельное поле пришлось бы держать с ним в согласии руками, и
разошлось бы оно на первом же сбое посреди прогона. Выборка ограничена проектом
(`p.project_id <=> %s`, NULL-безопасно): оболочка `developer` у каждого проекта своя, а
задачи без проекта живут в одной общей. Ноль (попыток ещё не было) считается сменой задачи —
чистый контекст в сомнительном случае безопаснее чужого.

Если перезапускаем — то ровно один раз и до первого шага, теми же соображениями, что у
менеджера: шаги #56 продолжают один разговор, и перезапуск между ними снёс бы разбор, на
который опирается реализация. QA перезапускается безусловно: он проверяет чужую работу, и
контекст прошлой проверки ему только мешает.

`timeout_developer_run` (3600s) — потолок на весь прогон, а не сумма шагов. Шаговые таймауты
600 + 1800 + 600 дают 3000s на один круг, но круг доработки (`max_dev_iterations` > 1)
сумму превышает, и обрывать прогон должен именно потолок. Он ниже
`timeout_worker_job` и `timeout_task_lock` — прогон обязан сорваться раньше, чем
блокировку сочтут протухшей.

Зовётся из **воркера** (`task_worker.py`), отдельным процессом, поэтому job сам поднимает
`queue_init([... 'ai_framework_model'])` и `ai_thread_framework_run(...)` — то же условие,
что у менеджера, иначе workflow отправит модель в очередь, которую некому разобрать.
Инструменты передаются картой из таблицы `tool` (`_tools_load()`): счётчик кругов
самопроверки вызывается как обычный инструмент.

- Получает `last_error` — непустой, если предыдущий круг завалил QA. Он кладётся в
  переменную `task_last_error`, и промпты раскрывают блоки `%if task_last_error%`:
  прогон идёт как доработка, а не как работа с нуля
- Получает **весь** контекст родителя (`task_title`, `task_description`, `task_goals`,
  `task_plan_current`), а не одну строку плана: без соседних шагов не видно, где кончается
  своя работа и начинается чужая
- Получает **свои** план и цели подзадачи (`subtask_plan`, `subtask_goals` — из
  `pipeline_plan` и `goals` самой подзадачи). План родителя остаётся контекстом, а сдавать
  разработчик будет вот это. У подзадач, разложенных до этого правила, поля пусты — промпт
  по `%if%` такие блоки просто не раскроет
- **Коммит только в feature-ветку и PR.** Пуш в `main` и самостоятельный merge запрещены —
  это решение, а не рекомендация по умолчанию
- Работает над одной подзадачей за раз; `attempt_count` растёт по кругам Developer→QA,
  лимит — настройка `timeout_attempt_max` (умолчание 3)
- При исчерпании лимита подзадача уходит в `blocked` — дальше её никто не берёт,
  нужен человек
- Подзадача не берётся вовсе, если карточка `developer` её проекта не жива
  (`task_role_project_sql` в `task_claim_subtask_developable`): захват сжёг бы попытку из
  отведённых на прогоне, который заведомо сорвётся

**Два уровня `ok`.** Ответ приходит как `{"ok": bool, "report": {...}, "error": str}`:
внешний `ok` говорит «прогон состоялся», `report.ok` — «подзадача выполнена». Различие не
формальное: оболочка может ответить и честно сказать, что сделать не смогла, — это не сбой
прогона, но и не повод отдавать работу QA. `_result_parse` требует оба и терпимо
относится к мусору: сорванный JSON (обрыв строки в тексте ошибки, лишний markdown) уходит
в `error` как есть, а не роняет воркер исключением — подзадача получает ещё одну попытку.
`report` разворачивается в плоский текст (`summary`, `Файлы:`, `Ветка:`, `Проверки:`) и
оседает в `project_task_attempt`.

| 0 | 432 | Инициализация | `variable_conversion` | обнуляет критику, счётчик, отчёт и поля ответа оболочки |

`max_dev_iterations` (переменная workflow, по умолчанию **1**) — сколько кругов
самопроверки разрешено. Единица значит «одна проверка без доработки»: замечания
самопроверки при лимите 1 всё равно попадут в отчёт, но круг 435→440 не повторится.
Поднимать её стоит осознанно — каждый лишний круг это ещё 1800 + 600 секунд, а потолок
прогона всего 3600.

Самопроверка **не заменяет QA**: разработчик проверяет собственную работу и заведомо
пристрастен. Её смысл в другом — поймать очевидное (не тот файл, забытый шаг плана,
незапущенная проверка) до того, как круг Developer→QA сожжёт попытку из трёх.

Обрыв связи с оболочкой (`dev_status != answered`) на разборе и реализации уводит на 443,
а на самопроверке — на 442: разбор и реализация без ответа означают, что работы не было,
а сорвавшаяся самопроверка не отменяет уже сделанного, и отчёт лучше отдать QA, чем
выбросить.

### QA

**Отвечает за:** проверить результат подзадачи.

- **Не исполняет произвольный сгенерированный код.** Только прогон существующего набора
  тестов — `pytest tests/`. Это осознанное ограничение: исполнение LLM-авторского кода в
  процессе с доступом к `.env`, БД и сети — главный риск схемы, и без песочницы этот шаг
  не открывается
- Проверяет **свой** сервер, а не общий: `./task_server.sh up <id>` поднимает `uvicorn_task`
  на `:8013` поверх каталога подзадачи, адрес приезжает переменной `subtask_server_url`.
  Общий `:8011` доказательством не считается — там код основного чекаута, а не проверяемой
  ветки. Перезапускать свой сервер QA можно и нужно: он больше не тот, в котором работает
  сам QA (см. «Свой рабочий каталог на подзадачу»)
- Возвращает `ok=False` с внятным `error` — он попадёт в `subtask.last_error` и дальше в
  `last_error` следующего вызова Developer. Полный вывод кладётся в `output` и оседает
  в `project_task_attempt`
- Принимает работу **по целям подзадачи** (`subtask_goals`), а не по целям задачи целиком:
  цели родителя проверяются на финале, круг QA закрывает только то, что обещала эта
  подзадача. План подзадачи приходит той же парой переменных (`subtask_plan`)
- На проде QA **строго наблюдательный**: не правит код, не перезапускает сервисы, не
  трогает состояние — только пишет отчёты и заводит задачи

#### 7.3 Workflow #57: разбор → прогон → цели по одной → вердикт

| 1 | 445 | Промпт: разбор изменений | `variable_conversion` | контекст: задача, подзадача, её план и цели, отчёт Developer; требует заранее выбрать, чем каждая цель будет воспроизведена |

подзадачи по одной: инструмент выдаёт формулировку, агента спрашивают ровно про неё, и

Галочка в колонке «Цели» ставится **только здесь** — то есть только у цели, по которой

что не проверено. Это защита от того, ради чего всё и переделывалось: агент склонен
называть проверкой чтение кода.

## 9. Проверка

```bash
.venv/bin/python3 -m pytest tests/test_task_pipeline.py tests/test_task_tree.py -v
```

`test_task_tree.py` (~12 с) покрывает: создание подзадачи и нумерацию позиций внутри
родителя, отказ на несуществующем родителе, «сам себе родитель», цикл, лимит глубины,
отцепление в корень, каскадное удаление ветки и то, что родителя конвейер не планирует.

`test_task_pipeline.py` покрывает: автопланирование задачи без плана, ручная правка `plan_text` с сохранением
подзадач, конфликт повторного старта, план без подзадач до утверждения, отклонение,
полный проход до `done`, параллельные тики (задачу забирает ровно один воркер).

`TestTaskPlanRevision` — ревизии и пересмотр: ручная правка даёт ревизию с
`author_kind='user'`; повторное «Сохранить» без изменений второй не даёт; правка плана не
вытирает `goals`; `review` при `approved` → `409`, при `plan_approval` → `200`;
двойной `review` → `409`; полный прогон пересмотра переписывает план, обнуляет подзадачи
и добавляет ревизию менеджера; `restore` возвращает текст и создаёт новую ревизию; чужая
ревизия → `404`.

> **Тестам нужна живая оболочка менеджера.** План пишет Claude Code, зарегистрированный
> на `/admin/team` в роли `manager`; тестовая задача заводится без типа, а значит
> достаётся роли по умолчанию. Без живой оболочки задача теперь не берётся вовсе (см.
> «Кто планирует»), и тест упрётся в таймаут ожидания состояния, а не в `failed`. Один прогон планирования — до восьми обращений к
> оболочке, это минуты, поэтому тесты ждут состояние, а не время. Содержимое плана
> не проверяется — только что он непустой и подзадачи появились; утверждать что-то о
> формулировках живого агента было бы флаки-тестом.

> Тик больше не ждёт менеджера — он лишь ставит сообщение в очередь, поэтому
> `TICK_TIMEOUT = 60` хватает с запасом (реально ~1 с). Долгое ожидание живёт в
> `_tick_until()` с `WAIT_TIMEOUT = 900`: столько тест даёт воркеру на прогон,
> опрашивая состояние раз в `POLL_INTERVAL = 5` с.

> База общая, а тик теперь берёт **любую** задачу без плана — значит, один вызов
> `/cronjob` может уйти на чужую строку. Поэтому тесты ждут своё состояние через
> `_tick_until()`, а не «один тик = один ожидаемый переход».

Ручной прогон по шагам — дёргать `/cronjob` (§4) и смотреть, как состояние двигается
на один шаг за вызов.

## 10. Известные ограничения

- **`POST /cronjob` без авторизации** (`src/uvicorn/routers/cronjob/cronjob.py`): любой,
  кто дотянется до порта, запустит любой файл из `src/cronjob/`. Было и раньше, но теперь
  за этим эндпоинтом стоит джоб, меняющий состояние задач
- `project_task.project_id` без FK и без NOT NULL — «Без проекта» приходится матчить как
  `project_id = 0 OR project_id IS NULL`
- **Каталоги задач требуют двух переменных в `.env`:** `PROJECT_HOST_DIR` (хостовый путь
  репозитория — без него `docker compose` не поднимется вовсе) и
  `PROJECT_TASK_QA_SERVER_URL`. На проде обе добавляются **только** через секрет
  `ENV_FILE` в GitHub, иначе следующий деплой их сотрёт
- **Ветка подзадачи режется от главной ветки** — значит, каталог получает тот `.gitignore`,
  который лежит в ней. Пока правка игнора не смержена, в свежем каталоге видно лишний
  `?? .venv` (символьная ссылка): шаблон `.venv/` со слэшем ссылку не ловит. Уборке это не
  мешает — ссылки она отличает по симлинку, а не по имени
- Порт `:8013` один на **проект**: `up` с другим номером переносит сервер на другой каталог.
  Проверяющая роль в каждый момент одна, и это принято сознательно. У другого проекта машины
  свой `./task_server.sh` и свой порт — пересечения нет, но следить за занятостью портов
  между проектами приходится человеку: общего реестра нет
- **Прод: изменения схемы не приедут сами.** `migrations/0001.sql` там помечен
  применённым (19.07.2026), yoyo повторно его не гоняет — всё, что дописано в файл
  после этой даты, доезжает только руками. Как подключаться — `database.md`,
  раздел «Connecting to Prod MySQL».

  **07.08.2026 применено:** `task` (0 строк, без входящих FK) заменена на
  `project_task` + `project_task_subtask` + `project_task_attempt` по DDL из `0001.sql`;
  заодно доехали 4 колонки в `llm` (`input_type`, `output_type`, `chunk_size`,
  `chunk_size_refresh_at`) — без них `src/ai/ai_llm.py:231` падал с ошибкой 1054.
  Вариант с `RENAME TABLE` не годился: `task_subtask`/`task_attempt` на проде не
  существовало вовсе.

  Расхождения, оставленные сознательно: `node.migration_file` и таблица
  `detective_case` — наследие удалённых фич, в `0001.sql` их нет; `tinyint(4)` против
  `tinyint` — MySQL 8.0.19+ просто не хранит display width, это не дрейф.

  **Ещё не на проде** (появилось в `0001.sql` после 07.08): переименованные значения
  ENUM `pipeline_state` (`pending_approval` → `plan_approval`, `review` → `reviewing`,
  `split` → `processing`), таблица `project_task_plan_revision`, слияние
  `project_task_subtask` в `project_task` и колонка `metadata`.

  Переименование значений ENUM одним `MODIFY` не сделать: старые строки в снятых
  значениях превратились бы в `''`. На проде — сначала ENUM с обоими наборами,
  потом `UPDATE` строк, и только потом ENUM ниже:

  ```sql
  ALTER TABLE `project_task`
      MODIFY `pipeline_state` ENUM('new','planning','pending_approval','plan_approval',
                                   'review','reviewing','approved','split','processing',
                                   'planned','developing','qa_pending','failed_qa',
                                   'blocked','done','failed') DEFAULT NULL;
  UPDATE `project_task` SET `pipeline_state` = 'plan_approval' WHERE `pipeline_state` = 'pending_approval';
  UPDATE `project_task` SET `pipeline_state` = 'reviewing'     WHERE `pipeline_state` = 'review';
  UPDATE `project_task` SET `pipeline_state` = 'processing'    WHERE `pipeline_state` = 'split';
  ```

  Остальное — перед следующим деплоем:

  ```sql
  ALTER TABLE `project_task`
      MODIFY `pipeline_state` ENUM('new','planning','plan_approval','reviewing','approved','processing',
                                   'testing','planned','developing','qa_pending','failed_qa','blocked',
                                   'done','failed') DEFAULT NULL,
      ADD COLUMN `pipeline_attempt_count` INT NOT NULL DEFAULT '0',
      ADD COLUMN `pipeline_from_plan` TINYINT(1) NOT NULL DEFAULT '0',
      ADD COLUMN `metadata` JSON NULL COMMENT 'Произвольные данные задачи: {ключ: значение}' AFTER `trace_meta`;
  -- project_task_attempt: subtask_id -> task_id с FK на project_task (DDL см. в 0001.sql)
  DROP TABLE IF EXISTS `project_task_subtask`;
  -- + CREATE TABLE `project_task_plan_revision` (DDL см. в migrations/0001.sql)
  ```

  Перед `DROP` проверить `SELECT COUNT(*) FROM project_task_subtask` на проде: если
  строки есть, их сначала переносят в `project_task` детьми (`pipeline_from_plan = 1`),
  а `project_task_attempt.subtask_id` перенацеливают на новые id.

  При переименовании таблиц не забыть значение `seed_table_config` в `setting` —
  таблицы там перечислены по имени
- **Пересмотр плана теряет историю попыток.** `POST /pipeline/review` удаляет подзадачи
  старого плана, а `project_task_attempt` уезжает за ними по `ON DELETE CASCADE`. Осознанно:
  подзадачи и попытки принадлежали плану, которого больше нет. Сам план и его подзадачи
  сохранены в ревизии, но отчёты разработчика — нет: с настоящим Developer пересмотр плана
  стирает уже сделанную по нему работу из журнала. Правки в репозитории при этом остаются —
  их сносить некому
- Порядок задач внутри уровня — по статусу и дате (`taskCompare`), а не по `position`:
  колонка есть, но drag-and-drop строк пока нет
- Порядок шагов в тике breadth-first: Developer разбирает все `planned`, прежде чем дойдёт
  очередь до QA. На корректность не влияет, но подзадачи завершаются пачками
