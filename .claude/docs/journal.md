# Journal — журнал установки, страница «Журнал» и подвкладка «Ошибки»

> Всё, что пишется в логи уровнем ERROR в любом процессе установки, попадает в таблицу
> `journal` и видно на `/admin/journal`, подвкладка «Ошибки». Пишет не код по месту, а
> обработчик корневого логгера — новый код попадает в журнал сам. Строка одна на
> отпечаток ошибки, повторы считаются в `hits`.

⚠ **«Журнал» — раздел, а не список ошибок.** Он отвечает на вопрос «что происходило на
установке», и ошибки — первая его подвкладка, а не весь смысл. Отсюда имена: namespace
`src/journal/`, таблица `journal`, ручки `/api/journal`, права `journal:*`. Соседняя
подвкладка с другим предметом приносит свой модуль `journal_<предмет>.py` и свои ручки —
общей «дай журнал» нет намеренно: у разных предметов разные поля и отборы.

## 1. Зачем он есть

Страница трасс отвечает на вопрос «что делал движок workflow»: запуски, шаги, токены.
Всё, что ломалось **вне** движка, там не видно вовсе — и ответ лежал в `docker logs`
четырёх контейнеров плюс `data/log/app.log` внутри них. Воркер упал ночью, кронджоб
сорвался, роутер отдал 500 — узнавали от человека со словами «что-то не работает».

Форма взята у соседнего проекта **DatingAi**: там «Журналы» — отдельная страница с
подвкладками (`data/uvicorn/template/admin/dating/log.html`), а хранение отказов со
счётчиком повторов — `src/dating/error.py`. Оба приёма проверены там живым трафиком.
Отличие одно и оно принципиальное — см. §5.

## 2. Как ошибка попадает в журнал

```
любой logger_exception / logging.error   →  корневой логгер
                                         →  JournalHandler (уровень ERROR)
                                         →  journal_write()  →  таблица journal
```

| Файл | Обязанность |
|------|-------------|
| `src/journal/journal.py` | таблица: запись, чтение страницами, отпечаток, чистка |
| `src/journal/journal_handler.py` | обработчик логгера и его установка в процессе |
| `src/uvicorn/routers/journal/journal.py` | `/api/journal`: список, удаление, чистка |
| `data/uvicorn/template/admin/journal.html` | страница «Журнал» и её подвкладки |
| `src/uvicorn/routers/dashboard.py` | маршрут `/admin/journal` |
| `data/uvicorn/template/base.html` | пункт меню «📋 Журнал» (вкладка «Логи», за Opensearch) |
| `migrations/20260926101937_error_log.sql` | заводит таблицу (под прежним именем `error_log`) |
| `migrations/20260926121818_journal_rename.sql` | переименование в `journal` вслед за кодом |

**Писать в журнал вручную не надо.** Код журналит как журналил; если запись идёт уровнем
ERROR — она в журнале. Отсюда единственное требование к новому коду: сбой сообщать
`logger_exception`, а не `logger_info`. Уровнем INFO сбой в журнал не попадёт — так и было
с 500-ми роутеров: `catch_exceptions_middleware` писал их `logger_info`, и в журнал они не
попадали вовсе.

## 3. Где обработчик ставится

Обработчик не появляется сам: `logging_init()` живёт в общем слое и про таблицы проекта не
знает. Каждая точка входа зовёт `journal_handler_install(<источник>)` рядом со своим
`logging_init()`.

| Точка входа | Источник |
|-------------|----------|
| `main_uvicorn.py` (lifespan) | `uvicorn` |
| `main_telegram.py` | `telegram` |
| `src/worker/project/task_worker.py`, `planning_worker.py` | `worker` |
| `src/cronjob/*.py` (все шесть) | `cronjob` |

`main_browser.py` в списке **нет**: у контейнера-браузера базы нет и не будет — по той же
причине ошибки живого окна пишет `uvicorn` (`.claude/docs/browser.md`).

Новая точка входа, где забыли вызов, не ломается — она просто молчит в журнале.

⚠ Uvicorn настраивает свой логгер `uvicorn.error` с `propagate = False`: до корня он не
доходит. Установка проверяет `propagate` у логгеров из `JOURNAL_HANDLER_LOGGERS` и
подвешивается только к оторванным — иначе запись задвоилась бы.

## 4. Строка одна на отпечаток

Сломавшийся цикл даёт одну ошибку каждую секунду: строка на каждую — десятки тысяч
одинаковых записей за ночь. Поэтому на `fingerprint` стоит `UNIQUE`, а повтор увеличивает
счётчик:

| Колонка | Смысл |
|---------|-------|
| `hits` | сколько раз всего; в ленте это оранжевый чип `×7` |
| `first_at` | когда сломалось впервые — видно, идёт это час или неделю |
| `last_at` | последний раз; по нему лента и сортируется |

Отпечаток — `md5(источник, логгер, первая строка сообщения)`, где из текста вычеркнуты
меняющиеся куски: uuid, адреса в памяти, числа от трёх знаков. Без этого «задача 5219 не
найдена» и «задача 5220 не найдена» были бы разными ошибками.

✅ одна строка `×7` с последним текстом и трассировкой
❌ семь строк, отличающихся номером задачи

## 5. ⚠ Удача строку не стирает — в отличие от DatingAi

Там журнал отвечает на вопрос «что сломано **прямо сейчас**», и успешный повтор запись
удаляет (`error_clear`). Здесь предмет другой — «что ломалось на установке»: ошибка
воркера, случившаяся ночью, интересна утром, даже если следующий заход прошёл.

Чистит журнал:

* время — записи старше `JOURNAL_KEEP_DAYS` (30) убираются при показе подвкладки, как
  чистится трасса workflow;
* человек — кнопка «Очистить» (по выбранному процессу либо весь журнал).

## 6. Ручки

| Метод | Путь | Право | Что делает |
|-------|------|-------|-----------|
| GET | `/api/journal` | `journal:view` | страница журнала; `source`, `level`, `q`, `page`, `per_page` |
| DELETE | `/api/journal/{id}` | `journal:delete` | убрать одну запись |
| DELETE | `/api/journal?source=…` | `journal:delete` | чистка: по процессу либо вся |

Ответ списка: `rows`, `total`, `page`, `pages`, `sources`. **`sources` — подписи процессов
для человека**, страница своей копии не держит: переименуют процесс в `JOURNAL_SOURCES` —
страница подхватит молча.

Право `journal:view` входит в базовый набор любой не-админской роли: страница соседняя с
трассами, под тем же пунктом меню, и «одна открылась, вторая отвечает 403» читается как
поломка.

## 7. Где именно сломалось

В строке журнала показывается **последний свой кадр трассировки**, а не последний вообще.
Последний почти всегда чужой: у ошибки базы это `pymysql/err.py:154 raise_mysql_exception`,
одинаковое у всех запросов. Предпочтение трёхступенчатое:

```
код проекта  →  общий слой (py_modules/)  →  чужая библиотека
```

Общий слой тоже отодвинут, хотя код наш: он почти весь тонкие обёртки, и кадр останавливался
бы на `mysql_.py:111 execute`, одинаковом у всех запросов проекта. Трассировка при этом
хранится целиком и раскрывается щелчком по тексту ошибки.

## 8. Проверка

```bash
.venv/bin/python3 -m pytest tests/test_journal.py -q      # группа core

# живая запись: ошибка из контейнера должна появиться в журнале
docker exec uvicorn python3 -c "
from logging_.logging_ import logging_init, logger_exception
from src.journal.journal_handler import journal_handler_install
logging_init(); journal_handler_install('cronjob')
try: {}['нет']
except Exception as e: logger_exception(f'проверка журнала: {e}')
"
PYTHONPATH=py_modules python3 -m mysql_.mysql_query sql \
  "SELECT source, hits, LEFT(message,60) FROM journal ORDER BY last_at DESC LIMIT 5"
```

## Грабли

1. **Сбой, записанный `logger_info`, в журнал не попадает.** Обработчик слушает ERROR.
   Именно так молчали 500-е роутеров: `catch_exceptions_middleware` писал их уровнем INFO
   вместе с приклеенной руками трассировкой.
2. **Место в строке журнала — не `record.pathname`.** Логгер зовут через обёртку общего
   слоя, и поле записи показывало бы `logging_.py:49 logger_exception` у каждой второй
   ошибки. Берётся кадр трассировки (§7).
3. **`logger_exception` вне `except` кладёт в запись `(None, None, None)`.** Форматирование
   такой «трассировки» даёт строку `NoneType: None` — проверять надо `exc_info[1]`, а не
   сам `exc_info`.
4. **Запись синхронная, и это не недосмотр.** Логгер зовут из потоков `rq` и из кронджобов,
   где цикл событий закрывается через секунду: фоновая задача не успевает, и запись
   теряется молча. Соединение pymysql одно на процесс, под замком — потоков много.
5. **Журнал не жалуется на себя уровнем ERROR.** О своих неудачах `journal_write`
   сообщает `logger_info`: жалоба на недоступную базу пошла бы записываться в ту же
   недоступную базу. Плюс флаг «мы внутри записи» на поток — от рекурсии.
6. **`ON DUPLICATE KEY UPDATE` не двигает `ON UPDATE`-колонку, когда значения совпали.**
   Поэтому `last_at` ставится явно `NOW(3)`: иначе у зациклившейся ошибки время замерло бы
   на первом падении.
7. **Прямой вызов `journal_rows` из теста падает на втором тесте.** Пул aiomysql привязан
   к циклу событий, а pytest-asyncio даёт каждому тесту новый. Тесты читают журнал через
   ручку; синхронная `journal_write` этим не страдает.
