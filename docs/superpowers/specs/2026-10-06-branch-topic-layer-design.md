# Ветки и темы: открытый слой управления разговором поверх workflow

> Спека от 2026-10-06. Над `dating_talk` появляется открытый слой: **ветка** —
> род разговора со своим контрактом и (необязательно) своим subflow, **тема** —
> запись внутри ветки с метками и тремя текстами: что разрешено, куда вести, что
> запрещено. Тему выбирает арифметика по меткам, а не код и не зашитый в промпт
> перечень. Новая тема стоит одной записи на вкладке; новый род разговора — одного
> шага в workflow.

⚠⚠ Архитектурные решения этой спеки приняты владельцем в сессии 06.10.2026 —
правило `workflow.md` «архитектуру workflow придумывает только человек» соблюдено.
Каждое решение ниже помечено, когда оно спорное, и несёт причину отказа от
альтернативы.

## 1. Зачем

Сегодня особая тема разговора заведена ровно одна — `photo_mail`, — и устроена так:

- перечень тем лежит **текстом в промпте** шага «Тема разговора» (`dating_talk`, pos 10);
- инструкции темы лежат **текстом в промпте** subflow `dating_talk_about_photo`;
- у родителя под неё стоят два шага (`workflow_invoke` и «Ответ ветки») и переход.

Цена второй темы — subflow из трёх шагов, два шага у родителя, строка в промпте
развилки, переход и сдвиг позиций. Всё миграцией SQL, то есть выкладкой. Миграция,
которой это заведено, сама предупреждает: «⚠ ТЕМА — СТРОКА, А НЕ ФЛАГ. Их будет
больше одной: встречи, деньги, контакты».

Вторая беда крупнее первой. Нынешняя ветка **заменяет** генерацию ответа: у неё свой
промпт, и в `inputs_map` намеренно нет ни фактов о девушке, ни фактов о собеседнике,
ни краткой выдержки истории. Для «договориться про фото» это верно, а для «увести
разговор к встрече» — нет: такой ответ обязан остаться спонтанным и на истории.

Слой закрывает обе: тему заводят записью, а исполнять её можно двумя способами —
сужением общего ответа либо своей дорогой.

⚠ Цель слоя — не ответ, а **направление**. Модель и сейчас поддерживает разговор,
но горизонт у неё одна реплика. Ветка задаёт, куда беседа движется.

## 3. Две сущности

### 3.1 Ветка — род разговора

```sql
CREATE TABLE `agent_workflow_branch` (
  `id`          INT AUTO_INCREMENT PRIMARY KEY,
  `node_id`     INT NOT NULL,
  `name`        VARCHAR(64)  NOT NULL,     -- 'deal', 'dodge'
  `title`       VARCHAR(255) NOT NULL,     -- «Договориться»
  `description` TEXT NULL,
  `workflow_id` INT NULL,                  -- subflow ветки; NULL — «сужает общий ответ»
  `match_min`   TINYINT NOT NULL DEFAULT 1,
  `is_enabled`  TINYINT NOT NULL DEFAULT 1,
  `position`    INT NOT NULL DEFAULT 0,
  UNIQUE KEY `uq_agent_workflow_branch_node_name` (`node_id`, `name`)
);
```

**Контракт ветки** отдельной таблицей **не заводится**: он и есть `input`-переменные
её subflow, уже объявляемые и уже проверяемые движком при вызове
(`ai_framework_manager.py:924` — не передали объявленный вход, прогон падает с именем
переменной).

⚠⚠ Второе объявление того же в проекте уже было и обошлось дорого: таблица
`agent_workflow_variable_workflow` держала одну строку переменной на два workflow, и
переименование в подпотоке переименовывало её у родителя. 51 общая строка,
разбиралось двумя выкладками (`workflow.md` §2.1). Повторять нельзя.

У ветки без subflow контракт пуст: её выход — поля темы, а они приезжают сквозными
переменными (§5.2).

### 3.2 Тема — содержание разговора

```sql
CREATE TABLE `agent_workflow_branch_topic` (
  `id`          INT AUTO_INCREMENT PRIMARY KEY,
  `branch_id`   INT NOT NULL,
  `name`        VARCHAR(64)  NOT NULL,     -- 'photo_mail'
  `title`       VARCHAR(255) NOT NULL,     -- «Письма и фотографии»
  `tags`        TEXT NOT NULL,             -- метки через запятую
  `acceptance`  TEXT NULL,                 -- что разрешено и как отвечать
  `direction`   TEXT NULL,                 -- куда вести разговор
  `restriction` TEXT NULL,                 -- о чём нельзя
  `is_enabled`  TINYINT NOT NULL DEFAULT 1,
  `position`    INT NOT NULL DEFAULT 0,
  UNIQUE KEY `uq_agent_workflow_branch_topic_name` (`branch_id`, `name`),
  CONSTRAINT `fk_agent_workflow_branch_topic_branch` FOREIGN KEY (`branch_id`)
    REFERENCES `agent_workflow_branch` (`id`) ON DELETE CASCADE
);
```

⚠ Набор полей темы **одинаков во всех ветках**. Дать ветке объявлять свои поля темы
значило бы превратить вкладку в конструктор форм, а смысл слоя — ровно в этих трёх
текстах: разрешено, желательно, запрещено.

⚠ Код темы уникален в пределах ветки ключом, и **в пределах ноды — проверкой на
сохранении**: по коду тема называется в промптах и в журнале, и два `money` в разных
ветках сделали бы журнал нечитаемым.

## 4. Выбор темы: метки, словарь, арифметика

### 4.1 Метки из двух слов и закрытый словарь

Метка — не одно слово, а словосочетание: `обмен письмами`, `интимное письмо`,
`пришли письмо`. Односложные метки не различают близкие темы: слово «письмо» ровно
так же стоит в рассказе про письмо от деда, как и в просьбе прислать фотографии.

⚠⚠ Словарь меток **закрытый**: развилке показывается плоский список всех меток, и
модель выбирает из него, своих не выдумывая. Это не предосторожность, а дважды
измеренная цена:

- **Галерея.** «Теги — закрытый словарь, 42 слова шестью группами: свободные модель
  выдумывала каждый раз заново — `lace dress`, `silver dress`, `white sweater`, — и
  по таким снимок не отберёшь, а отбор это всё, ради чего теги есть.»
- **Факты.** `dating_talk.md` §4: «теги генерирует LLM на лету («машина» vs «авто») →
  отсечение релевантных фактов».

⚠ Список даётся **плоским, без группировки по темам**. Увидев группировку, модель
выберет тему сама, и выбор перестанет быть детерминированным. Модель размечает —
выбирает арифметика.

⚠ Выдуманную метку отбрасывать не нужно: она ни с чем не совпадёт. Отказ выходит
мягким — тема не выбрана, разговор идёт обычным путём.

### 4.2 Правило выбора

1. Разобрать `topic_tags` по запятым; привести к нижнему регистру, схлопнуть пробелы.
2. Для каждой включённой темы включённой ветки ноды: **счёт** — число её меток,
   попавших в набор (точное совпадение после приведения).
3. Отбросить темы со счётом ниже `match_min` **их собственной ветки**.
4. Победитель — наибольший счёт. При равенстве — большая **доля** (счёт / число меток
   темы). При равенстве доли — темы нет.
5. Шаг сравнивает победителя со своей веткой: моя — работает, не моя — не делает
   ничего.

⚠⚠ Счёт считается **по всему реестру**, а не по темам своей ветки. Иначе цепочка
шагов берёт первую прошедшую порог, а не лучшую, и промахивается ровно там, ради
чего заведены двухсловные метки: «почта как служба» со счётом 2 у ветки, стоящей
выше, уводит поток мимо «обмена письмами» со счётом 4.

⚠ Общая арифметика даёт ещё одно свойство: **порядок шагов веток перестаёт значить
что-либо**. Победитель у всех шагов один и тот же, сработает тот, кому тема
принадлежит. Грабля с позициями, на которую наступали при заведении ветки про фото,
здесь не действует.

⚠ Порог живёт **в записи ветки**, а не на шаге. На шаге он глушил бы и чужие темы:
победила тема со счётом 2 при пороге строгой ветки 3 — и разговор остался без темы,
хотя у соседней ветки была годная тройка. В реестре же темы ниже своего порога
выбывают **до** подсчёта максимума.

⚠ Перекос: тема с двадцатью метками набирает совпадений чаще темы с тремя просто
потому, что меток больше. Правило ничьей по доле лечит это частично; число меток
показывается в списке тем на вкладке, чтобы перекос было видно глазами.

## 5. Тип шага `branch`

### 5.1 Метаданные

```json
{"branch": {
   "branch_id":   3,
   "tags":        "topic_tags",
   "inputs_map":  {"prompt_user": "prompt_user", "talk_history": "talk_history",
                   "companion_title": "companion_title", "user_language": "user_language"},
   "outputs_map": {"branch_result": "branch_result"}},
 "transitions_after": [...], "transitions_before": []}
```

- `branch_id` — **статически**, селектом в редакторе. Только так редактор покажет
  контракт, а граф сможет нарисовать стрелку к subflow.
- `tags` — **имя переменной** со строкой меток, по правилам `inputs_map` у
  `tool_invoke`: короткое имя, не текст. Приставка `_const_` работает и здесь.
- `inputs_map` / `outputs_map` — только то, что передаёт вызывающий; читаются из
  объявленного контракта subflow.

### 5.2 Что шаг кладёт сам

Победив, шаг кладёт в переменные родителя семь значений — **карты для них нет**:

`topic_name`, `topic_title`, `topic_tags`, `topic_accept`, `topic_direction`,
`topic_restrict`, `topic_score`

⚠⚠ Карты быть не должно: с ней каждый шаг переписывал бы одно и то же, а один
забытый маппинг выключал бы тему **молча** — ветка отработала, промпт собрался, в
нём просто нет инструкций. Такой отказ не виден ни в журнале, ни в ответе.

⚠ Устройство для этого в движке есть, изобретать нечего: `workflow_invoke` так же
протаскивает `user_language` и `node_languages` — «сквозные служебные, язык должен
быть одинаковым во всех вложенных workflow без ручного `inputs_map` на каждом шаге»
(`ai_framework_manager.py:903`). Темовые переменные — тот же случай, только источник
у них реестр.

Те же семь передаются и внутрь subflow ветки, и объявлять их в контракте ребёнка не
требуется.

### 5.3 ⚠⚠ Шаг, который не выиграл, не пишет ничего

Проигравший шаг обязан **не трогать** переменные, а не класть пустые строки. Иначе
ветка, стоящая ниже победителя, затрёт его значения, и «Генерация ответа» увидит
пустоту при верно выбранной теме. Отказ был бы молчаливым и плавающим — зависел бы
от порядка шагов.

⚠ Отсюда требование: `topic_*` объявляются в реестре переменных workflow (`type`
`workflow`, умолчание — пустая строка). Это документированное лекарство из
`workflow.md` §4a-bis: шаг, который можно пропустить, перестаёт заводить свою
переменную, а сторож меток `ai_workflow_marks_check` роняет промпт, где метка
осталась без значения.

### 5.4 Исполнение

- **Ветка без `workflow_id`** — шаг кладёт `topic_*` и завершается. Поток падает по
  порядку дальше и доходит до «Генерации ответа», где блоки
  `%if topic_direction%…%endif%` раскрываются. Ответ сочиняет общий шаг — при фактах,
  при истории, при всей механике тишины.
- **Ветка с `workflow_id`** — шаг вызывает subflow **той же подпрограммой**, что и
  `workflow_invoke`: защита от рекурсии, вложенная трассировка
  (`parent_run_id`/`parent_step_id`/`depth`), `repeat`, алиас
  `branch_{step_id}_result_str`. Повторять эти 180 строк нельзя. Уводит дальше
  переход шага — на «Ответ ветки», как сегодня.

## 6. Служебная переменная `%topic_catalog%`

Плоский список меток всех включённых тем включённых веток ноды, с удалением
повторов. Заполняется движком **на старте прогона**, рядом со сборкой переменных
запроса, — тем же приёмом, каким протаскиваются `user_language` и `node_languages`.

⚠ Без неё развилке «Тема разговора» словарь взять негде: она стоит **до** шагов
веток. Вариант «шаг `branch` с пустым селектом» отвергнут — форма шага вела бы себя
по-разному в зависимости от того, заполнено ли поле ветки. Вариант «инструмент»
отвергнут владельцем: слой обязан быть открытым.

⚠⚠ Это новый источник значений, а `workflow.md` §3.0 запрещает значения, приходящие
мимо объявленных источников. Решение принято владельцем явно; при заведении
переменная **обязана** попасть в список служебных рядом с `user_language`, а не
появиться молча.

## 7. Объявленные выходы workflow

`agent_workflow_variable.type` сегодня знает `global` / `input` / `workflow`.
Добавляется **`output`**.

Зачем: «прикрепить subflow можно, только если контракты совпадают» без объявленных
выходов непроверяемо. Побочная выгода крупнее повода — сейчас `outputs_map` у
tool-шагов движок игнорирует **молча**, и в базе лежат тринадцать мёртвых карт в
шести workflow (`workflow.md` §4a-bis).

⚠ Оживлять старые карты эта спека не берётся: «оживут все разом, и те из них, чья
цель уже заполняется откуда-то ещё, начнут её перетирать». Здесь только объявление и
проверка на сохранении ветки.

## 8. Кнопка «Создать subflow»

Создаёт пустую ветку-дорогу с гарантированно совпадающим контрактом:

1. `agent_workflow` с `subflow = 1`, именем от ветки;
2. переменные: `input` — по контракту ветки, `output` — туда же;
3. шаг `llm_to_json`, в промпте которого уже стоят `%topic_accept%`,
   `%topic_direction%`, `%topic_restrict%`;
4. **шаг `return_response_text`**.

⚠⚠ Шага отдачи хватает одного, но он обязателен. Движок отдаёт результат родителю
только на `return_response_text` / `return_response_llm`; дойдя до конца списка без
них, `_workflow_steps_run` возвращает `None`, родитель кладёт в результат пустую
строку — и **без ошибки**. Скелет из одного `llm_to_json` молча возвращал бы пустоту.

## 9. Вкладка «Branch»

Две колонки. Слева список веток с постраничной навигацией: название, код серым,
точка «включена», число тем. Справа — карточка выбранной ветки: название, код,
`match_min`, селект subflow с кнопкой «Создать subflow», и под ними список тем.
Тема правится формой из шести полей: код, название, метки чипсами, разрешено,
желательно, запрещено.

⚠ Число меток темы показывается в строке списка — им виден перекос из §4.2.

⚠ Выкройка списка и формы берётся с существующей страницы переменных ноды, своей не
рисуется.

## 10. Что меняется в `dating_talk`

```
pos 10  llm_to_json «Тема разговора»   ← %topic_catalog%  → topic_tags
pos 11  branch «Договориться»          → победитель мой? да → topic_* + subflow → «Ответ ветки»
pos 12  branch «Уклониться»            → нет → ничего не делает, поток идёт дальше
pos 13  llm_to_json «Генерация ответа» ← %if topic_direction%…%endif%, %if topic_accept%…
pos 14  llm_to_json «Валидация»        ← %if topic_restrict%…%endif%
```

Шаг «Тема разговора» уже стоит на pos 10 — меняется только его промпт: перечень тем
заменяется словарём меток, а ответом вместо `talk_topic` становится `topic_tags`.

**Перевод ветки про фото.** `dating_talk_about_photo` остаётся живой как
ветка-дорога. Её тексты-критерии переезжают в запись темы `photo_mail` ветки
«Договориться», а промпты subflow начинают читать `%topic_accept%` и
`%topic_restrict%` вместо зашитых списков. Её итог `photo_deal` переименовывается в
общий выход ветки; что означают `his` / `mine` / `both` / `mail`, описывает сама
запись темы.

⚠ Два прежних шага родителя (`workflow_invoke` «Ветка: письма и фото» и его переход
от `photo_deal`) заменяются одним шагом `branch`. «Ответ ветки» остаётся.

⚠⚠ Но его промпт переписывается: сегодня там стоит `%workflow_invoke_{id}_result_str%`,
а результат ветки приедет под алиасом `branch_{step_id}_result_str` — имя шага в
автоимени другое. Не переписать — шаг отдаст **пустую строку**, молча: метка с
пустым значением промпт не роняет, она просто ничего не подставит. Номер шага в
каждой установке свой, поэтому миграция обязана подставить его после вставки, а не
зашивать числом (`workflow.md` §4a-bis).

## 11. Чего в этой работе нет

- **Память пары** — «какую тему этой паре поднимали и чем кончилось». У неё есть
  нерешённый вопрос: шаг `branch` исполняется **до** ответа и итог писать не может.
- **Своя инициатива** — девушка поднимает тему сама. Память нужна именно ей, и
  решать их надо вместе, вторым заходом.
- **Правка `graph.js`** — он рисует сплошную стрелку «следующий по номеру» каждому
  нетерминальному шагу и о переходах не спрашивает. С ростом числа веток врать он
