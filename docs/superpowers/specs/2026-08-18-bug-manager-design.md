# Вкладка «Баги» и агент-багфиксер

> Спека от 2026-08-18. Четвёртая вкладка на `/admin/task`, четвёртая роль в команде и
> новый агент, который берёт баг в работу и сам доводит его до `done` или `blocked`.

## 1. Зачем

Сейчас баги живут на вкладке «Тестирование/Баги» вперемешку с тестовыми задачами, а
владеет ими роль `qa`: тип `bug` стоит в `TASK_ROLE_TYPES['qa']` рядом с `test`. Для QA
это чужая работа — проверять сделанное и чинить сломанное разные занятия, и попадая к
одной карточке они конкурируют за одну живую оболочку.

Баг отличается от задачи разработки тем, что план ему не нужен: у него есть текст ошибки
и есть проект, а вся работа — воспроизвести, найти причину, починить, проверить. Прогон
через `Manager → человек → Developer → QA` для этого избыточен: четыре шага и утверждение
плана человеком там, где хватает одного круга.

Отсюда две вещи в этой спеке: своя вкладка у багов и своя роль, которая ведёт баг от
начала до конца одним прогоном.

## 2. Что меняется по именам

| Что | Имя | Примечание |
|---|---|---|
| Роль карточки | `bugfixer` | четвёртая в блоке проекта на `/admin/team` |
| Тип задачи | `bug` | уже есть (`project_task_type.id = 2`), меняется только владелец |

| Действие конвейера | `bugfix` | `kind` в сообщении очереди |
| Агент и workflow | `task_bug_fixer` | по образцу `task_dev_developer` (#56) |
| Модуль прогона | `src/project/task/task_agent_bugfixer.py` | функции с префиксом `task_agent_bugfixer_` |
| Ключ пометки | `to_bugfix` | в `project_task.metadata` |
| Настройка таймаута | `timeout_bugfix_run` | 3600s, группа «Агент» |

## 3. Страница `/admin/task`

### 3.1 Вкладки

Было три, стало четыре:

```
Планирование | Разработка | Тестирование | Баги
```

`PHASE_TYPE_NAMES` в `data/uvicorn/template/admin/project/task.html`:

```js
const PHASE_TYPE_NAMES = {
    planning:    ['research', 'plan'],
    development: ['dev'],
    testing:     ['test'],
    bugs:        ['bug'],
};
```

Кнопка «Тестирование/Баги» становится «Тестирование»; рядом добавляется «Баги» со своим
счётчиком `tabCount-bugs`.

`PHASE_NEW_TYPE_NAME.bugs = 'bug'` — задача, заведённая кнопкой «+ Добавить» на вкладке
«Баги», сразу получает тип `bug`. Полей «Статус» и «Тип» в форме нет, тип решает вкладка.

Набор колонок не меняется, поэтому версию ключа `task_col_pct_v3` поднимать **не** нужно.

### 3.2 Готовый баг остаётся на «Багах»

Сейчас правило одно на все типы: закрытая задача видна только на «Тестировании», потому
что там её принимают — смотрят `diff` и вливают ветку. Для багов оно перестаёт работать:
вкладка «Баги» — полный жизненный цикл бага, и уводить закрытый баг на чужую вкладку
значит прятать его от того, кто его завёл.

`taskMatchesPhase`:

```js
if (taskIsDone(t)) return typeName === 'bug' ? _phaseFilter === 'bugs'
                                             : _phaseFilter === 'testing';
```

То же исключение — в `phaseTabsCount`. Разойдись счётчик с отбором, вкладка звала бы на
пустое место.

Кнопки `diff` и `mr2master&rm_worktree` (`renderPipeDiff` / `renderPipeMerge`) правок не
требуют: они смотрят только на `parent_id` и `pipeline_state === 'done'`, вкладка им
безразлична. Комментарии над ними, где сказано «готовая задача видна только на
Тестировании, поэтому обе кнопки живут там же», обновляются по факту.

### 3.3 Флажок «в багфикс»

Один флажок в колонке прогресса, только на вкладке «Баги», только у корневой задачи и
только в статусах `active` / `queued` / `pending` (`TASK_RUN_FLAG_STATUS`).

Умолчание — **включено**: заведённый баг должен попадать в работу сам, решением человека
является отказ. Значит, хранится отклонение от умолчания: ключа нет — флажок стоит,
снятый пишется явным `false`. Читатель обязан отличать «ключа нет» от `false` —
`!== false`, а не `!!`.

Снятие не только запрещает будущий захват, но и гасит идущий прогон: за флажком стоит
существующий `_taskPhaseSwitch(id, TASK_META_KEY_BUGFIX, checked, el)` — сперва патч
пометки, потом `/pipeline/stop`. Обратный порядок дал бы тику подобрать задачу в тот же
миг.

Второго флажка у вкладки нет: после фикса баг идёт к человеку, а не к следующему агенту.

### 3.4 Справка

В модальное окно `showHelpModal` добавляется состояние `bugfixing` — «баг у багфиксера,
идёт разбор и починка» — рядом с остальными состояниями конвейера.

## 4. Роль `bugfixer`

### 4.1 Владение типами

`src/project/task/task_role.py`:

```python
TASK_ROLE_TYPES = {
    'manager':   ('plan', 'research'),
    'developer': ('dev',),
    'qa':        ('test',),
    'bugfixer':  ('bug',),
}
TASK_ROLE_TITLE['bugfixer'] = 'Багфиксер'
```

Тип `bug` уезжает от `qa` к `bugfixer`. Роль по умолчанию остаётся `manager`: ей
достаётся всё, чего нет в карте.

### 4.2 Багфиксер не планирует

`TASK_ROLE_TYPES` читают оба захвата — и работа роли, и написание плана
(`task_claim_task_unplanned` через `task_role_type_sql`). Оставь мы карту как есть,
`_claim_manager_plan` увидел бы живую карточку `bugfixer`, её тип `bug` и отправил бы баг
писать план менеджерским workflow #55 — ровно то, от чего эта спека уходит.

Поэтому в `task_role.py` появляется отбор ролей-планировщиков:

```python
# Роли, которые пишут план. Багфиксер работает по багу сразу, плана ему не нужно,
# и в менеджерский захват он попадать не должен.
TASK_ROLE_PLANNERS = ('manager', 'developer', 'qa')

def task_role_planners_only(roles_by_project: dict) -> dict:
    """`roles_by_project` без ролей, которые план не пишут."""
```

`_claim_manager_plan` и `_claim_manager_review` зовут захват через этот фильтр.

Очередь на карточке (`team_queue._planner_rows`) фильтра не получает: карточка багфиксера
должна показывать очередь своих багов, и `task_role_type_sql('bugfixer')` даёт ровно её.

### 4.3 Карточка команды

| Файл | Правка |
|---|---|
| `src/project/team/team_project.py` | `TEAM_PROJECT_ROLE_BASE += ('bugfixer',)`; `TEAM_PROJECT_ROLE_ORDER['bugfixer'] = 2`; `TEAM_PROJECT_ROLE_TITLE['bugfixer'] = 'Багфиксер'` |

## 5. Конвейер

### 5.1 Машина состояний

```
баг (project_task, task_type = 'bug', parent_id = NULL) — pipeline_state:

  NULL | new  --(захват)-->  bugfixing  --+--> done    (status = done)
                                          |
                                          +--> failed  (status = blocked)

  failed  --(«Повторить»)-->  new
```

Ни `plan_approval`, ни `approved`, ни подзадач: у бага нет плана, вся работа идёт в самой
строке. Кругов «не сошлось» тоже нет — один прогон, один ответ.

`_TASK_STATE_KANBAN['bugfixing'] = 'active'`. Строки `failed → blocked` и `done → done`
в карте уже есть, править их не нужно.

### 5.2 Захват

`task_claim.py` — новая `task_claim_task_bug(worker, roles_by_project)`:

```
UPDATE project_task
   SET pipeline_state = 'bugfixing', pipeline_locked_at = NOW(), pipeline_locked_by = %s
 WHERE id = %s
   AND parent_id IS NULL
   AND (pipeline_state IS NULL OR pipeline_state = 'new')
   AND status <> 'cancelled'
   AND task_type_id = (SELECT id FROM project_task_type WHERE name = 'bug')
   AND <task_role_project_sql(roles_by_project, 'bugfixer')>
   AND <task_metadata_bugfix_free_sql()>
```

Пометку `stopped` дописывает общий `_task_claim` — это единственное место, где её нельзя
забыть, и своего условия отборам не нужно. Оттуда же и защита от гонки: условие
повторяется в самом `UPDATE`, а результат сверяется по `rowcount`, иначе два тика утащили
бы один баг.

`status <> 'cancelled'` в отборе стоит **явно**, в отличие от остальных шагов. Те смотрят
только на `pipeline_state`, и отменённая задача им не попадается по другой причине: у неё
либо есть план, либо человек её в конвейер не заводил. У бага вход в работу автоматический
и никакого утверждения человеком по пути нет — без этого условия отменённый баг ушёл бы
чиниться молча. `task_state_kanban_sql` тут не спасает: он лишь не перебивает `cancelled`
в колонке `status`, работу же он не останавливает.

Тип отбирается **по имени** через подзапрос, а не по id: id зависят от установки. Живая
карточка проверяется через `task_role_project_sql` (проект, без оглядки на тип) — тип уже
задан явным условием, и `task_role_project_type_sql` дал бы то же самое дважды.

`failed` в отбор не попадает намеренно: без этого фильтра тик подбирал бы заблокированный
баг вечно. Возврат — существующая кнопка «Повторить» (`POST /task/{id}/pipeline/retry`),
которая уводит задачу в `new` и снимает `stopped`.

### 5.3 Реклейм

`TASK_CLAIM_STATE_RECLAIM['bugfixing'] = 'new'` — умер воркер, `task_claim_locks_reclaim()`
вернёт строку в очередь по `timeout_task_lock`. Состояние в карте — источник и списка
«работа в полёте» (`TASK_CLAIM_INFLIGHT_STATES`), поэтому багфикс автоматически начинает
считаться в предел «Parallel LLM» проекта. Так и надо: прогон занимает живую оболочку и
ходит в LLM наравне с остальными.

### 5.4 Место в порядке захвата

`_action_claim`:

```
_claim_qa → _claim_developer → _claim_bugfix → _claim_plan_split
          → _claim_manager_review → _claim_manager_plan
```

Работа роли идёт раньше нового планирования: закрыть начатое важнее, чем добавить
незакрытого. Багфикс встаёт после разработки — подзадачи идущего плана ближе к
завершению, чем баг, который ещё не начинали.

### 5.5 Выполнение

`_run_bugfix(action)` в `task_pipeline.py`:

```
перечитать строку (task_state_task_get) — нет строки, тихо выходим
        │
work_dir  = task_role_project_work_dir(task['project_id'])
task_dir  = task_worktree_ensure(work_dir, task['id'])     ветка feature/task_<id>
        │
task_agent_bugfixer_run(task, role='bugfixer', work_dir=work_dir, task_dir=task_dir)
        │
   ok:true  → task_state_task_done(task_id, отчёт)      pipeline_state=done,   status=done
   ok:false → task_state_task_fail(task_id, error)      pipeline_state=failed, status=blocked
   срыв     → task_retry (см. 5.6)
```

`task_state_task_fail` уже есть. `task_state_task_done` — **новая**: существующая
`task_state_task_finalize()` закрывает задачу по терминальности её подзадач, а у бага
подзадач нет вовсе, и она его не увидит. Пишем одним UPDATE с `task_state_kanban_sql('done')`
— тем же приёмом, что и `task_state_task_fail`, включая защиту от перебивания
`cancelled` и остановленных строк.

Ветка и рабочий каталог берутся существующими `task_worktree_branch` / `task_worktree_path`
/ `task_worktree_ensure` по **id самой задачи**. Их шаблоны говорят `subtask_id`, но
ключ — просто номер строки `project_task`, а он глобально уникален; переименование
параметра в спеку не входит.

Страница разницы и слияние работают без правок: `_diff_target` уже разбирает случай
«корневая задача без подзадач — ветка своя» и возвращает `subtask_ids == [task_id]`.

### 5.6 Срывы и повторы

Кругов «не сошлось» у багфиксера нет: `ok: false` — это ответ, а не сбой, и он ведёт в
`blocked` сразу.

Технический срыв — другое дело: оболочка не ответила, Claude Code мёртв, вернулся не-JSON.
Работы не было, хоронить баг не за что. Такой прогон идёт через существующий
`src/project/task/task_retry.py`: счётчик `metadata.retry`, потолок `timeout_retry_max`
(3), перезапуск оболочки `team_session_restart_role('bugfixer', work_dir)`, возврат строки
в `new`. Исчерпаны повторы — `failed` с текстом, сколько прогонов сорвалось подряд.

Порядок обязателен и тот же, что у остальных ролей: счётчик → отчёт → перезапуск оболочки
→ возврат строки. Отпусти строку первой — её успел бы забрать соседний воркер и отправить
в оболочку, которую в этот момент гасим.

### 5.7 Остановка

`task_stop.py` правок почти не требует: пометка `stopped` проверяется в общем `_task_claim`,
а возврат строки «в полёте» идёт по `TASK_CLAIM_STATE_RECLAIM`, куда `bugfixing` уже
добавлен пунктом 5.3. Добавить нужно только снятие флажка своей вкладки — на «Багах» это
`to_bugfix`, по тому же правилу, по которому остановка снимает «в разработку» у задачи
менеджера и «в тестирование» у задачи разработчика. Иначе снятая остановка сработала бы
повторно.

## 6. Агент и workflow

### 6.1 Модуль прогона

`src/project/task/task_agent_bugfixer.py` — по образцу `task_agent_qa.py`:

```python
TASK_BUGFIXER_AGENT_NAME = 'task_bug_fixer'
TASK_BUGFIXER_ROLE = 'bugfixer'

async def task_agent_bugfixer_run(task, role=TASK_BUGFIXER_ROLE,
                                  work_dir='', task_dir='') -> dict
```

Возвращает `{'ok': bool, 'output': str, 'error': str}`. Один перезапуск оболочки на прогон
и до первого шага — контекст прошлого бага в этот не попадает. Между шагами перезапускать
нельзя: они продолжают один разговор.

Переменные workflow:

| Переменная | Что |
|---|---|
| `task_id`, `task_title`, `task_description` | по ним карточка команды находит прогон в трейсе |
| `task_goals` | цели, если человек их завёл |
| `task_trace_meta` | `trace_meta` бага: workflow, агент, шаг, текст ошибки — у автозаведённых багов это и есть вся фактура |
| `task_shell_role`, `task_shell_work_dir` | адрес оболочки: роль + каталог проекта |
| `task_work_dir` | рабочий каталог бага (worktree) |
| `task_branch` | `feature/task_<id>` |
| `task_server_url` | адрес сервера проекта для проверки фикса (`task_role_project_server_url`) |

Разбор ответа — та же терпимая к мусору схема, что у QA: `json:`-префикс,
`{"ok", "report", "error"}`, сорванный JSON уходит в `error`, а не роняет воркер.

Промпт разбора отвечает на вопрос «воспроизводится ли»: не воспроизвёлся — это законный

### 6.3 Как workflow попадает в базу

Агент и workflow — данные, а не схема: их место в seed, не в `migrations/0001.sql`.
Порядок такой:

1. одноразовым скриптом в scratchpad завести строки `agent_workflow`,
   `agent_workflow_step`, `agent_workflow_variable(_workflow)` и `agent` в локальной БД;
2. проверить прогон на живом баге;
3. `/admin/seed` → сгенерировать seed по таблицам агентов и workflow;
4. файл `data/seeds/seed_*.sql` — в коммит. Это и есть перенос на прод.

### 6.4 Таймаут

`task_setting_timeout.py`: `TASK_SETTING_TIMEOUT_BUGFIX_RUN = 'timeout_bugfix_run'`,
умолчание 3600s, группа «Агент», роль `bugfixer`. Лестница остаётся прежней:

```
timeout_bugfix_run (3600) < timeout_worker_job (3900) < timeout_task_lock (4200)
```

Прогон обязан сорваться раньше, чем блокировку сочтут протухшей, иначе второй воркер
возьмёт ещё живую работу. Проверку лестницы (`task_setting_timeout_ladder_problem`) новая
строка проходит наравне с остальными агентскими.

## 7. Что не меняется

- **Сканер трейса.** `task_bug_create` как вставлял задачи с `task_type_id = 2`, так и
  вставляет. Они просто попадают теперь на вкладку «Баги» и к своему агенту.
- **Существующие баги в базе.** У кого уже есть план от QA — план остаётся, задача
  доигрывает по старому пути; в отбор багфиксера она не попадёт, потому что её
  `pipeline_state` не `NULL` и не `new`.
- **Схема БД — почти.** Новых колонок нет: пометка живёт ключом в `metadata`, роль —
  строкой в `project_team`. Но `pipeline_state` оказался **ENUM**, и значение `bugfixing`
  пришлось в него добавить: `migrations/0001.sql` плюс ручная миграция
  `data/migration_manual/2026-08-18_task_pipeline_state_bugfixing.sql` для накопленных баз
  (прод в том числе).

  Найдено проверкой на живой базе, уже после реализации. MySQL в нестрогом режиме на
  неизвестное значение ENUM не ругается, а молча пишет пустую строку: захват выглядел
  удачным (rowcount = 1, человеческий статус менялся), но строка залипала навсегда —
  реклейм ищет `bugfixing`, следующий тик ищет NULL или `new`, и пустую строку не видит
  ни один. Расхождение кода и схемы теперь ловит `TestPipelineStateEnum`.

## 8. Проверка

`tests/test_task_pipeline.py` — четыре случая:

1. баг типа `bug` при живой карточке `bugfixer` захватывается в `bugfixing`;
2. `ok: true` уводит баг в `done` / `done`, `ok: false` — в `failed` / `blocked` с текстом
   в `pipeline_error`;
3. менеджерский захват баг **не** берёт (`task_role_planners_only`);
4. снятый флажок `to_bugfix = false` убирает баг из отбора.

Плюс `tests/test_team_task_pages.py` — страница `/admin/task` отдаёт четыре вкладки, а
`/admin/team` — карточку `bugfixer`.

Ручная проверка под учёткой QA (`.env.local`): завести баг на вкладке, дождаться тика
оркестратора, увидеть `bugfixing` на карточке багфиксера, дождаться `done`, посмотреть
`diff`, влить ветку.
