# Архитектура технического планирования (фаза: tech)

## Концепция

Техническое планирование — это последовательное **конкретизирование системы**: от "что должна делать" до "как именно устроена каждая часть". Хорошая архитектура не та, что сложнее всего придумана, а та, которая решает задачу с минимальной случайной сложностью и максимальной предсказуемостью изменений.

Всего **10 уровней**: от требований до управления техническим долгом.

**Связь с другими планами:** питается из `planning_product.md` (фичи, deliverables) и `planning_research.md` (конкурентные решения, технологические тренды). Выходы питают `planning_experiments.md` (что тестируем технически) и `planning_launch.md` (readiness).

## Уровни технического планирования

### Уровень 0 — Требования (Requirements)

**Что это:** что система должна делать и каковы ограничения. Ещё нет архитектуры — только "что".

**Формат:** Requirements document, 2–4 страницы.

**Ключевые вопросы:**
- Какие функции должна поддерживать система (functional requirements)?
- Каковы нефункциональные требования (производительность, надёжность, безопасность)?
- Каковы ограничения (бюджет, сроки, команда, legacy)?
- Что критично, а что nice-to-have?

**Структура документа:**
```
Requirements
├── Functional Requirements
│   ├── FR-01: [описание] | Приоритет: Must/Should/Could
│   ├── FR-02: ...
│   └── ...
├── Non-Functional Requirements (NFR)
│   ├── Performance: p99 latency < X ms при Y RPS
│   ├── Availability: SLA X% (uptime)
│   ├── Scalability: до X пользователей / X req/sec
│   ├── Security: compliance требования, auth модель
│   ├── Data: retention, GDPR, backup
│   └── Cost: бюджет на инфраструктуру
├── Constraints (ограничения)
│   ├── Технологические (существующий стек, legacy)
│   ├── Команда (что умеем, что нет)
│   └── Бюджет и сроки
├── Assumptions
└── Out of Scope (что явно НЕ делаем)
```

**✓ Готов к переходу на уровень 1, если:**
- Каждый FR имеет приоритет (MoSCoW)
- NFR содержат числа, а не "быстро" и "надёжно"
- Out of Scope явно написан — это предотвращает scope creep

### Уровень 1 — Концептуальная архитектура (Conceptual Architecture)

**Что это:** высокоуровневая схема без деталей. Главные блоки системы и как они взаимодействуют. Понятна нетехническому стейкхолдеру.

**Формат:** 1 диаграмма + 1 страница описания.

**Ключевые вопросы:**
- Из каких крупных блоков состоит система?
- Как данные текут между блоками?
- Где граница системы (что внутри, что снаружи)?
- Какие внешние системы/сервисы используются?

**Структура документа:**
```
Концептуальная архитектура
├── Context Diagram (C4 Level 1)
│   ├── Система как единый блок
│   ├── Пользователи / роли
│   └── Внешние системы
├── Container Diagram (C4 Level 2)
│   ├── Основные блоки (frontend, backend, DB, queue, AI)
│   └── Протоколы взаимодействия (HTTP, gRPC, events)
├── Ключевые решения (ADR — Architecture Decision Records)
│   └── ADR-001: [решение] | Причина | Альтернативы | Trade-offs
└── Архитектурные принципы для этой системы
    └── (напр. "API-first", "event-driven", "stateless services")
```

**Инструменты:**
- draw.io, Miro, Excalidraw — диаграммы
- C4 Model (c4model.com) — стандарт уровней абстракции
- ADR (Architecture Decision Records) — фиксация решений

**✓ Готов к переходу на уровень 2, если:**
- Диаграмма понятна человеку без технического бэкграунда
- Все внешние зависимости явно показаны
- Ключевые архитектурные решения зафиксированы в ADR

### Уровень 2 — Системная архитектура (System Architecture)

**Что это:** детальная схема компонентов системы, их взаимодействий, протоколов и границ.

**Формат:** архитектурный документ, 3–5 страниц + диаграммы.

**Ключевые вопросы:**
- Какие сервисы/модули существуют и за что отвечают?
- Как сервисы общаются (sync/async, какие протоколы)?
- Где хранятся данные (какие БД, для чего)?
- Как обеспечивается отказоустойчивость?

**Структура документа:**
```
System Architecture
├── Component Diagram (C4 Level 3)
│   ├── Каждый сервис / модуль
│   ├── Интерфейсы (API endpoints, events, queues)
│   └── Зависимости между компонентами
├── Data Flow Diagrams
│   ├── Основные user journeys через систему
│   └── Где данные трансформируются
├── Integration Map
│   ├── Внешний сервис | Протокол | Назначение | SLA
│   └── Fallback при недоступности
├── Deployment Topology (где что запускается)
│   ├── Сервисы | Инстансы | Ресурсы
│   └── Network topology (VPC, subnets, CDN)
├── Failover & Resilience
│   ├── Single points of failure (SPOF)
│   └── Стратегия при падении каждого компонента
└── ADR (обновлённые + новые)
```

**✓ Готов к переходу на уровень 3, если:**
- Каждый компонент имеет чёткую зону ответственности (SRP)
- SPOF идентифицированы и задокументированы (даже если не устранены)

### Уровень 3 — Технологический стек (Tech Stack)

**Что это:** конкретный выбор технологий, фреймворков, инструментов. С обоснованием каждого выбора.

**Формат:** таблица + ADR для ключевых решений.

**Ключевые вопросы:**
- Почему именно этот язык / фреймворк / БД?
- Какие альтернативы рассматривались?
- Каковы trade-offs выбранного стека?
- Что команда умеет, что нужно учить?

**Структура документа:**
```
Tech Stack
├── Backend
│   ├── Язык: [Python / Go / ...] | Версия | Причина выбора
│   ├── Фреймворк: [FastAPI / ...] | Версия | Причина
│   └── Ключевые библиотеки
├── Frontend
│   ├── Фреймворк: [...] | Версия
│   ├── State management: [...]
│   └── Инструменты сборки
├── Данные
│   ├── Primary DB: [PostgreSQL / MySQL / ...] | Версия | Причина
│   ├── Cache: [Redis / ...] | Назначение
│   ├── Search / Vector DB: [Qdrant / ...] | Назначение
│   └── Message Queue: [Kafka / RabbitMQ / ...]
├── AI / ML
│   ├── LLM Provider: [Anthropic / OpenAI / ...] | Модели
│   ├── Embedding Model: [...]
│   ├── Orchestration: [LangChain / custom / ...]
│   └── Model serving (если self-hosted)
├── Infrastructure
│   ├── Cloud: [AWS / GCP / ...] | Регион
│   ├── Контейнеризация: [Docker / ...]
│   ├── Оркестрация: [Kubernetes / docker-compose / ...]
│   └── CI/CD: [GitHub Actions / ...]
├── Observability
│   ├── Logging: [...]
│   ├── Metrics: [...]
│   └── Tracing: [...]
└── Стек-матрица рисков
    └── Технология | Зрелость | Team expertise | Lock-in risk | Альтернатива
```

**✓ Готов к переходу на уровень 4, если:**
- Каждый ключевой выбор задокументирован в ADR
- Команда имеет необходимый уровень знаний или план обучения

### Уровень 4 — API Design (API Contracts)

**Что это:** контракты между компонентами. Что и как передаётся между сервисами, клиентами и внешними системами.

**Формат:** OpenAPI/AsyncAPI спецификации + design guide.

**Ключевые вопросы:**
- Какие endpoints нужны (REST / gRPC / GraphQL)?
- Какова модель данных запросов и ответов?
- Как обрабатываются ошибки?
- Как версионируется API?

**Структура документа:**
```
API Design
├── API Design Principles
│   ├── Стиль (REST / RPC / GraphQL)
│   ├── Naming conventions
│   ├── Error format (структура ошибок)
│   ├── Pagination pattern
│   └── Versioning strategy
├── Endpoint Registry
│   ├── GET /resource — описание, параметры, response
│   ├── POST /resource — body schema, response
│   └── ...
├── Data Models (schemas)
│   ├── Entity: [название]
│   │   ├── Поле | Тип | Required | Описание
│   │   └── ...
│   └── ...
├── Authentication & Authorization
│   ├── Auth механизм (JWT / OAuth / API key)
│   └── Permission model
├── Event Schema (если async)
│   ├── Event: [название] | Topic | Producer | Consumer
│   └── Payload schema
└── Changelog API версий
```

**✓ Готов к переходу на уровень 5, если:**
- API задокументирован в machine-readable формате (OpenAPI spec)
- Контракты согласованы между командами frontend/backend

### Уровень 5 — Архитектура данных (Data Architecture)

**Что это:** как данные хранятся, организуются, трансформируются и защищаются.

**Ключевые вопросы:**
- Какова схема данных (таблицы, коллекции, индексы)?
- Как данные текут через систему (ETL / event-driven)?
- Как обеспечивается консистентность?
- Каков lifecycle данных (retention, archiving, deletion)?

**Структура документа:**
```
Data Architecture
├── Data Model
│   ├── ER-диаграмма (Entity-Relationship)
│   ├── Таблица: [название]
│   │   ├── Поле | Тип | Constraints | Индексы
│   │   └── Связи (FK, cascade rules)
│   └── ...
├── Data Flow
│   ├── Как данные создаются (write path)
│   ├── Как данные читаются (read path)
│   └── Трансформации (если есть ETL/ELT)
├── Consistency Model
│   ├── Транзакционные границы
│   └── Eventual consistency где применима
├── Data Lifecycle
│   ├── Retention policy (сколько хранить)
│   ├── Archiving strategy
│   └── Deletion (GDPR right-to-erasure)
├── Backup & Recovery
│   ├── RPO (Recovery Point Objective)
│   └── RTO (Recovery Time Objective)
├── Migrations
│   ├── Инструмент (Alembic, Flyway, yoyo)
│   └── Zero-downtime migration strategy
└── Sensitive Data Map
    └── Где хранятся PII / secrets / credentials
```

**✓ Готов к переходу на уровень 6, если:**
- ER-диаграмма актуальна и включает все сущности
- RPO и RTO определены и backup настроен

### Уровень 6 — Инфраструктура и деплой (Infrastructure & Deployment)

**Что это:** как система запускается, деплоится и масштабируется в production.

**Ключевые вопросы:**
- Как устроена среда (dev / staging / production)?
- Как происходит деплой (CI/CD pipeline)?
- Как масштабируется при росте нагрузки?
- Что происходит при деплое — zero-downtime?

**Структура документа:**
```
Infrastructure & Deployment
├── Environments
│   ├── Development (локальная разработка)
│   ├── Staging (pre-production)
│   └── Production
├── Infrastructure as Code
│   ├── Инструмент: [Terraform / Pulumi / ...]
│   └── Ключевые ресурсы
├── CI/CD Pipeline
│   ├── Trigger → Build → Test → Deploy → Verify
│   ├── Время pipeline (цель)
│   └── Rollback стратегия
├── Deployment Strategy
│   ├── Blue-Green / Canary / Rolling
│   └── Zero-downtime гарантии
├── Scaling Strategy
│   ├── Horizontal scaling (когда и как)
│   ├── Auto-scaling rules (метрики-триггеры)
│   └── Capacity planning (сколько нужно при N пользователях)
├── Secrets Management
│   └── Как хранятся и ротируются ключи
└── Disaster Recovery
    ├── Runbook при падении production
    └── Контакты и эскалация
```

### Уровень 7 — Безопасность (Security Architecture)

**Что это:** как система защищена от угроз. Threat model, контроли, compliance.

**Ключевые вопросы:**
- Каковы главные угрозы для системы?
- Какие данные наиболее чувствительны?
- Как обеспечивается аутентификация и авторизация?
- Каков план при security incident?

**Структура документа:**
```
Security Architecture
├── Threat Model
│   ├── Assets (что защищаем)
│   ├── Threat actors (кто может атаковать)
│   └── Attack vectors (STRIDE / OWASP Top 10)
├── Authentication & Authorization
│   ├── Auth механизм
│   ├── Token lifecycle (expiry, rotation)
│   └── Permission model (RBAC / ABAC)
├── Data Security
│   ├── Encryption at rest
│   ├── Encryption in transit (TLS)
│   └── Sensitive data handling
├── Network Security
│   ├── Firewall rules
│   ├── API rate limiting
│   └── DDoS protection
├── Application Security
│   ├── Input validation
│   ├── SQL injection prevention
│   ├── XSS / CSRF protection
│   └── Dependency vulnerability scanning
├── Compliance
│   ├── GDPR (если применимо)
│   ├── SOC2 / ISO27001 (если требуется)
│   └── Отраслевые требования
└── Incident Response
    ├── Playbook при breach
    ├── Notification обязательства
    └── Post-mortem процесс
```

### Уровень 8 — Наблюдаемость (Observability)

**Что это:** как мы понимаем, что происходит в системе в реальном времени.

**Ключевые вопросы:**
- Как узнать, что система работает нормально (golden signals)?
- Как найти причину проблемы за минуты, а не часы?
- Как настроены алерты (не слишком шумно, не слишком тихо)?

**Структура документа:**
```
Observability
├── Logging
│   ├── Log levels и что логируем
│   ├── Structured logging format (JSON)
│   ├── Log aggregation (ELK / CloudWatch / ...)
│   └── Log retention policy
├── Metrics (Four Golden Signals)
│   ├── Latency (p50, p95, p99)
│   ├── Traffic (RPS)
│   ├── Errors (error rate %)
│   └── Saturation (CPU, memory, queue depth)
├── Distributed Tracing
│   ├── Инструмент: [Jaeger / Zipkin / ...]
│   └── Что трейсируем (critical paths)
├── Dashboards
│   ├── Operations Dashboard (oncall)
│   ├── Business Dashboard (продуктовые метрики)
│   └── AI/LLM Dashboard (token usage, latency, costs)
├── Alerting
│   ├── Alert | Условие | Severity | Кому | Действие
│   └── On-call rotation
└── SLO / SLA
    ├── SLO определения (error budget)
    └── SLA обязательства перед клиентами
```

### Уровень 9 — Техдолг и эволюция (Tech Debt & Evolution)

**Что это:** управление накопленным техническим долгом и планирование развития архитектуры.

**Ключевые вопросы:**
- Что является техническим долгом и насколько он дорог?
- Как приоритизировать рефакторинг против новых фич?
- Когда архитектура требует пересмотра?

**Структура документа:**
```
Tech Debt & Evolution
├── Tech Debt Registry
│   ├── Долг | Причина | Влияние (1–5) | Усилие (1–5) | Приоритет
│   └── ...
├── Критерии приоритизации долга
│   ├── Impact on velocity (замедляет разработку)
│   ├── Risk (может привести к инциденту)
│   └── Cost of delay (дорожает с каждым месяцем)
├── Архитектурные ревью
│   ├── Частота: [ежеквартально]
│   └── Чеклист ревью
├── Architectural Fitness Functions
│   ├── Automated проверки архитектурных принципов
│   └── Метрики качества кода (coupling, cohesion)
├── Roadmap рефакторинга
│   └── Квартал | Что рефакторим | Ожидаемый эффект
└── "Strangler Fig" план
    └── Если нужна замена крупного компонента — инкрементальный план
```

## Антипаттерны технического планирования

| Уровень | Антипаттерн | Симптом | Исправление |
|---------|------------|---------|-------------|
| 0→1 | NFR без чисел | "Система должна быть быстрой" | Добавить: "p99 < 200ms при 1000 RPS" |
| 1→2 | Big Design Up Front | 3 месяца архитектуры до первой строки кода | Итеративная архитектура: минимум для MVP, уточняем по мере роста |
| 2→3 | Cargo cult технологий | "Используем Kubernetes, потому что все используют" | Выбирать стек под масштаб задачи, не под тренды |
| 3→4 | API без версионирования | Breaking changes ломают клиентов | Versioning с первого дня (/v1/, header-based) |
| 4→5 | Схема данных без миграционного плана | ALTER TABLE на 50M строк в prod в пятницу | Zero-downtime migrations как стандарт |
| 5→6 | Manual deploy | Деплой = stress event | CI/CD с первого дня, даже простой |
| 6→7 | Security "потом" | Переписывать auth архитектуру на зрелом продукте | Threat model до написания первой строки API |
| 7→8 | Алерты на всё | Alert fatigue, oncall игнорирует | Алерты только на actionable события |
| 8→9 | Накопленный долг без реестра | "Мы не успеваем рефакторить" | Visible долг → включать в каждый спринт 20% времени |

## Принципы технического планирования

1. **Архитектура следует за требованиями, не наоборот.** Сначала понять, что нужно решить — потом выбирать технологии.

2. **Простота как цель.** Самая сложная часть — удержать систему простой. Добавить сложность легко; убрать — дорого.

3. **Эволюционная архитектура.** Планируй для текущего масштаба × 10. Не для × 1000 — это преждевременная оптимизация.

4. **ADR как живая документация.** Каждое важное архитектурное решение требует ADR: что решили, почему, какие альтернативы отклонили. Без этого через 6 месяцев никто не помнит.

5. **Observability — не опция.** Система без логов, метрик и трейсов — чёрный ящик. Строй наблюдаемость параллельно с функциональностью.

6. **Security by design.** Добавлять безопасность в существующую систему в 10 раз дороже, чем закладывать с начала.

7. **Tech debt — инвестиция с процентами.** Накопленный долг не исчезает. Чем дольше ждёшь, тем дороже стоит и тем больше замедляет команду.

8. **Interfaces over implementations.** Проектируй границы компонентов (контракты, API) более тщательно, чем внутреннюю реализацию. Реализацию можно переписать; изменение интерфейса — breaking change.
