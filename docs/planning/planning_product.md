# Агентный плейбук продуктового планирования (фаза: product)

## Концепция

Этот документ — пошаговый плейбук для фазы **product** AI-планировщика. Продуктовый план строится **на данных из исследования рынка** (`planning_research.md`). Агент не придумывает фичи — он извлекает их из реальных жалоб, отзывов и запросов пользователей конкурентов. Каждое решение должно быть обоснованы данными.

**Предусловие:** фаза `market` выполнена — есть таблица конкурентов и данные о рынке.

---

## Уровень 0 — Извлечение боли пользователей (Pain Mining)

**Цель:** собрать реальные боли целевых пользователей из публичных источников — не придумывать их.

**Действия агента:**

### Шаг 0.1 — Анализ негативных отзывов конкурентов
Для каждого конкурента из `planning_research.md` (фаза 3) выполнить WebFetch страницы отзывов:

```
g2.com/products/{slug}/reviews?filters[review_type]=negative
capterra.com/reviews/{slug}/?overall=1,2
trustpilot.com/review/{domain}?stars=1,2,3
```

Из каждого отзыва извлечь:
- Конкретную жалобу (цитата)
- Роль рецензента
- Как долго использовал продукт

### Шаг 0.2 — Анализ форумных обсуждений
WebSearch (адаптировать `{ниша}` из исследования):
```
"{ниша}" problems site:reddit.com
"{ниша}" frustrating site:reddit.com
"I wish {название конкурента}" site:reddit.com
"switched from {конкурент}" site:reddit.com
"{конкурент}" alternative site:reddit.com
"{ниша}" pain points site:quora.com
"{ниша}" challenges site:ycombinator.com
```

WebFetch топ-5 тредов. Извлечь:
- Конкретные жалобы (цитаты)
- Что ищут в альтернативах
- Workflow-проблемы ("мне приходится делать X вручную, потому что...")

### Шаг 0.3 — Анализ запросов на функции
WebSearch:
```
"{конкурент}" feature request
"{конкурент}" "can you add"
"{конкурент}" wishlist
site:reddit.com "{конкурент}" "would be great if"
```

**Выходной артефакт — Pain Registry:**
```
| Боль | Частота упоминаний | Интенсивность (1–5) | Цитата | Источник URL |
|------|--------------------|--------------------|---------|----|
| ...  | ...                | ...                 | "..."   | ... |
```

**✓ Переход на уровень 1:** задокументированы ≥ 15 болей с источниками.

## Уровень 1 — Определение видения продукта (Product Vision)

**Цель:** сформулировать видение на основе найденных болей — не абстрактно, а с привязкой к данным.

**Действия агента:**

### Шаг 1.1 — Анализ "table stakes" и gaps
Из матрицы функций (фаза 5 `planning_research.md`):
- Что есть у всех конкурентов (table stakes — обязательно строить)
- Что не делает никто (gap — потенциальная дифференциация)

### Шаг 1.2 — Проверка видения на реальных примерах
WebSearch:
```
"{предполагаемое решение}" app OR platform OR tool
"{предполагаемое решение}" exist OR available
"there is no tool that" "{ниша}"
"I haven't found anything that" "{ниша}"
```

Найти: существует ли уже что-то похожее на то, что хотим построить?

### Шаг 1.3 — Анализ успешных аналогов в других нишах
WebSearch:
```
"{аналогичная проблема в другой нише}" solution product
"{механизм решения}" product case study
"{аналог}" how it works
```

**Выходной артефакт:**
```
## Видение продукта

Для [ICP из plan_research, фаза 6], кто страдает от [топ-боль #1 из Pain Registry],
[Название] — это [категория],
которая решает проблему через [механизм].

В отличие от [конкурент #1], мы [конкретный gap из матрицы функций].

Доказательство спроса: {N} упоминаний "{боль}" на Reddit/G2 — источники: {URL}

Table Stakes (строим обязательно): {список из матрицы функций}
Дифференциатор (наш gap): {что не делает никто}
Anti-goals (не строим): {что намеренно исключаем}
```

## Уровень 3 — Стратегия продукта (Product Strategy)

**Цель:** определить позиционирование и MVP-scope через данные, а не интуицию.

**Действия агента:**

### Шаг 3.1 — Карта позиционирования конкурентов
Из данных `planning_research.md` (фазы 3–5) построить карту:
- Ось X: простота vs. мощность
- Ось Y: цена (низкая vs. высокая)

Найти пустой квадрант — туда позиционируемся.

### Шаг 3.2 — Анализ позиционирования конкурентов
Для топ-3 конкурентов WebFetch главной страницы. Извлечь точный tagline.

WebSearch:
```
"{конкурент}" positioning strategy
"{конкурент}" target market
"{конкурент}" vs {другой конкурент}
```

### Шаг 3.3 — Проверить MVP scope через "минимальный" пример
WebSearch:
```
"{ниша}" MVP features
"{ниша}" minimum viable product
"built {ниша} in" days OR weeks OR weekend
"{конкурент}" early version OR v1 OR initial
```

Найти: что было в v1 у успешных конкурентов?

**Выходной артефакт:**
```
MVP Scope (обоснованный данными):

Включаем:
- {фича 1} — потому что: {N} жалоб на её отсутствие у конкурентов (источник)
- {фича 2} — table stakes: есть у 90% игроков (источник: матрица функций)

НЕ включаем в MVP:
- {фича X} — есть только у 20% игроков, не упоминается в жалобах

Позиционирование: {quadrant на карте}
Конкурентное преимущество: {gap из матрицы + боль из Pain Registry}
```

## Уровень 4 — Бизнес-требования (Business Requirements)

**Цель:** задокументировать требования с обоснованием из данных.

**Действия агента:**

### Шаг 4.1 — Извлечь требования из болей
Каждая боль из Pain Registry → functional requirement:
```
Боль: "невозможно экспортировать данные в CSV"
FR-01: Экспорт данных в CSV и Excel | Приоритет: Must | Источник: {N} упоминаний на Reddit (URL)
```

### Шаг 4.2 — Найти non-functional требования из отзывов
WebSearch:
```
"{конкурент}" slow OR performance
"{конкурент}" downtime OR outage
"{конкурент}" security concerns
"{конкурент}" GDPR OR compliance
```

Из найденного — NFR для нашего продукта.

### Шаг 4.3 — Найти интеграции, которые ожидают пользователи
WebSearch:
```
"{конкурент}" integration site:reddit.com
"{конкурент}" "works with" OR "integrates with"
"{ниша}" integrations must-have
"{ниша}" Zapier OR Make OR n8n
```

**Выходной артефакт:**
```
Functional Requirements (приоритизированные данными):
| FR-# | Требование | Приоритет | Источник жалобы | URL |
|------|-----------|-----------|----------------|-----|

| NFR-# | Требование | Метрика | Источник |

```

## Уровень 5 — Операционный roadmap (Quarterly Roadmap)

**Цель:** расставить приоритеты по кварталам на основе данных.

**Действия агента:**

### Шаг 5.1 — Приоритизация по данным (ICE scoring)
Для каждой фичи из уровня 4:
- **Impact** (влияние): сколько раз упоминается в болях (1–10)
- **Confidence** (уверенность): есть ли аналог у конкурентов (1–10)
- **Ease** (сложность): оценка трудозатрат (1–10)
- ICE = (Impact × Confidence × Ease) / 3

### Шаг 5.2 — Найти примеры roadmap от конкурентов
WebSearch:
```
"{конкурент}" roadmap 2024 OR 2025
"{конкурент}" changelog
"{конкурент}" upcoming features
site:producthunt.com "{конкурент}" ship
```

WebFetch: страницы changelog/roadmap конкурентов. Что они строили в каком порядке?

### Шаг 5.3 — Проверить сезонность спроса
WebFetch Google Trends для ключевых слов ниши — есть ли пики? Если да, запуск привязать к пику.

**Выходной артефакт:**
```
Roadmap (обоснованный ICE):

Q1 (MVP):
- {фича} ICE: {X} | Боль: "{цитата}" | Источник: {URL}

Q2 (Growth):
- {фича} ICE: {X} | Запрошена: {N} раз | Источник: {URL}

Q3–Q4 (Scale):
- {фича} ICE: {X} | Аналог у конкурента: {кто}
```

## Уровень 8 — Спринт-план (Sprint Planning)

**Цель:** конкретный список задач на ближайшие 2 недели с обоснованием.

**Действия агента:**

Из бэклога (уровень 6) взять топ-N фич по ICE.

Для каждой фичи:
1. WebSearch: `"{технология} {фича}" tutorial implementation` — оценить сложность
2. Декомпозировать на задачи ≤ 2 дней
3. Назначить исполнителей

**Выходной артефакт:**
```
Sprint [N] — Даты: {от} – {до}
Цель: {одно предложение}

| Задача | Исполнитель | Оценка (ч) | Источник приоритета | DoD |
|--------|------------|-----------|--------------------|----|

Capacity команды: {X часов суммарно}
Загрузка: {Y часов / X часов = Z%} (цель ≤ 80%)
```

## Карта уровней

```
[0] Pain Mining — реальные боли из G2/Reddit/форумов
    ↓
[1] Product Vision — видение на основе gaps
    ↓
[2] Product Goals — цели с реальными бенчмарками
    ↓
[3] Product Strategy — позиционирование через карту конкурентов
    ↓
[4] Business Requirements — FR/NFR из болей пользователей
    ↓
[5] Quarterly Roadmap — приоритеты по ICE + пример конкурентов
    ↓
[6] Feature Backlog — полный список с обоснованием
    ↓
[7] UX Research — реальные примеры из индустрии
    ↓
[8] Sprint Plan — конкретные задачи ≤ 2 дней
    ↓
[9] Product Ops — инструменты сбора данных
```

## Правила качества

1. **Каждая фича — из данных.** Нет источника (отзыв/форум/конкурент) — нет фичи в MVP.

2. **Боль важнее фичи.** Строим решение боли, не фичу ради фичи.

3. **Конкуренты уже провели UX-исследования.** Анализ их жалоб = бесплатное user research.

4. **ICE без данных = мнение.** Только Impact, Confidence и Ease из реальных источников.

5. **Table stakes — обязательны.** Без них никто не будет рассматривать продукт всерьёз.
